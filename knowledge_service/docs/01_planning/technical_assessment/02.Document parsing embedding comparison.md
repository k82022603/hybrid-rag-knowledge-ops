# 문서 파싱 및 임베딩 기술 심층 비교 분석 보고서 [#](https://claude.ai/public/artifacts/0a1a6d87-ec64-47ea-a966-10ca683f6f8a)

## 서론

엔터프라이즈 지식 검색 시스템을 구축할 때 가장 중요한 두 가지 기술적 결정은 문서에서 정보를 어떻게 추출할 것인가와 추출된 텍스트를 어떻게 벡터화할 것인가입니다. 본 보고서에서는 LlamaParse, Docling, BGE-M3라는 세 가지 기술을 심층적으로 분석합니다. 다만, 이 기술들을 단순 비교하기에 앞서 반드시 이해해야 할 핵심 개념이 있습니다. LlamaParse와 Docling은 문서 파싱 도구로서 PDF나 워드 파일에서 텍스트와 테이블을 추출하는 역할을 수행하는 반면, BGE-M3는 임베딩 모델로서 추출된 텍스트를 벡터로 변환하는 역할을 담당합니다. 즉, 이들은 RAG 파이프라인에서 서로 다른 단계를 담당하는 상호 보완적인 기술입니다.

현재 계획하신 아키텍처에서 PostgreSQL은 시계열 마스터 레코드로서 단일 진실 공급원 역할을 수행하고, Neo4j는 지식 조각 간의 관계를 연결하는 슬림 지식 그래프로 작동하며, Elasticsearch는 BGE-M3 임베딩과 전문 검색 및 메타데이터를 통합 저장하는 구조입니다. 이 아키텍처에서 문서 파싱 도구와 임베딩 모델이 각각 어떤 위치에서 어떤 역할을 수행하는지 명확히 이해하는 것이 시스템 설계의 핵심입니다.

## 제1장: RAG 파이프라인에서의 역할 분류

### 1.1 데이터 흐름 개요

RAG 시스템의 데이터 흐름은 크게 네 단계로 구분됩니다. 첫 번째 단계인 문서 파싱에서는 LlamaParse 또는 Docling이 원본 문서에서 텍스트와 구조를 추출합니다. 두 번째 단계인 청킹에서는 추출된 텍스트를 의미 단위로 분할하는데, 이 과정은 파싱 도구에 내장되어 있거나 별도로 수행될 수 있습니다. 세 번째 단계인 임베딩에서는 BGE-M3와 같은 모델이 청크를 벡터로 변환합니다. 마지막 네 번째 단계인 저장 및 검색에서는 Elasticsearch와 같은 벡터 스토어가 이를 저장하고 검색합니다.

이러한 흐름에서 문서 파싱 도구와 임베딩 모델은 파이프라인의 서로 다른 지점에서 작동합니다. 문서 파싱 도구는 비정형 데이터를 정형화하는 전처리 단계를 담당하고, 임베딩 모델은 정형화된 텍스트를 수치 벡터로 변환하는 변환 단계를 담당합니다. 따라서 이 두 기술은 경쟁 관계가 아닌 협력 관계에 있으며, 최적의 RAG 시스템은 두 영역 모두에서 우수한 기술을 선택하여 조합해야 합니다.

### 1.2 기술 카테고리 정의

문서 파싱 도구의 핵심 기능은 PDF, DOCX, PPTX 등의 복잡한 문서 형식에서 텍스트, 테이블, 이미지, 수식 등을 정확하게 추출하는 것입니다. 이 과정에서 문서의 계층 구조(섹션, 하위 섹션, 본문)를 보존하고, 테이블의 행과 열 구조를 유지하며, 읽기 순서를 올바르게 파악하는 것이 중요합니다. LlamaParse와 Docling이 이 카테고리에 속합니다.

임베딩 모델의 핵심 기능은 텍스트를 고차원 벡터 공간에 매핑하여 의미적 유사성을 수치화하는 것입니다. 좋은 임베딩 모델은 의미적으로 유사한 텍스트를 벡터 공간에서 가깝게 배치하고, 다국어 텍스트 간의 의미적 연결을 지원하며, 다양한 길이의 텍스트를 효과적으로 처리해야 합니다. BGE-M3가 이 카테고리에 속합니다.

## 제2장: 문서 파싱 도구 심층 비교

### 2.1 LlamaParse 상세 분석

LlamaParse는 LlamaIndex 팀이 개발한 GenAI 기반 문서 파싱 서비스로, LlamaCloud 플랫폼의 핵심 구성 요소입니다. 2024년 초에 공개된 이후 빠르게 발전하여 2025년 현재 업계 선도적인 PDF 파싱 솔루션으로 자리잡았습니다.

LlamaParse의 기술적 특징을 살펴보면, 가장 핵심적인 강점은 GenAI 네이티브 파싱입니다. 전통적인 규칙 기반 파서와 달리 LlamaParse는 대규모 언어 모델을 활용하여 문서의 의미적 구조를 이해합니다. 이를 통해 복잡한 레이아웃, 다중 컬럼, 머지된 셀이 있는 테이블 등 기존 도구들이 어려워하던 문서 유형을 정확하게 처리할 수 있습니다. 2025년 5월 업데이트에서는 OpenAI의 GPT 4.1과 Google의 Gemini 2.5 Pro를 지원하여 파싱 정확도가 더욱 향상되었습니다.

출력 형식 측면에서 LlamaParse는 마크다운을 기본 출력 형식으로 사용합니다. 마크다운은 문서의 구조적 정보를 보존하면서도 LLM이 이해하기 쉬운 형식이라는 점에서 RAG 파이프라인에 매우 적합합니다. 테이블은 마크다운 테이블 형식으로 변환되어 행과 열의 관계가 명확하게 표현됩니다. 또한 JSON 모드를 통해 문서의 완전한 구조, 이미지 메타데이터, 테이블의 JSON 형식 추출도 지원합니다.

LlamaParse는 자연어 지시 기능을 제공합니다. 파싱 과정에서 LLM에게 프롬프트를 전달하여 출력 형식을 맞춤 설정하거나, 파싱 중에 감정 분석, 언어 번역, 요약 등의 전처리를 수행할 수 있습니다. 이 기능은 특정 도메인에 특화된 문서를 처리할 때 매우 유용합니다.

2025년 5월에 추가된 자동 방향 감지 기능은 실무에서 자주 발생하는 문제를 해결합니다. 스캔된 문서가 뒤집어지거나 90도, 180도, 270도 회전된 경우를 자동으로 감지하고 올바른 방향으로 수정합니다. 더 미묘한 1도에서 12도 사이의 기울어짐도 감지하여 자동으로 수직 정렬합니다.

LlamaParse의 가격 정책은 사용량 기반입니다. 무료 플랜에서는 월 10,000페이지를 제공하며, 개발 및 테스트 용도로 충분합니다. 유료 플랜에서는 주 7,000페이지 무료 제공 후 추가 페이지당 0.3센트가 부과됩니다. 엔터프라이즈 환경에서 대량의 문서를 처리해야 할 경우 별도의 상업적 협의가 필요합니다.

LlamaParse의 제한사항도 고려해야 합니다. 클라우드 서비스로만 제공되므로 문서가 외부 서버로 전송됩니다. 보안이 중요한 기업 환경에서는 데이터 보안 정책을 검토해야 합니다. 또한 복잡한 손글씨나 양식 필드 추출에서는 아직 제한이 있으며, 매우 큰 PDF 파일이나 고도로 비정형화된 문서에서 성능 저하가 발생할 수 있습니다.

### 2.2 Docling 상세 분석

Docling은 IBM Research에서 개발되어 2025년 4월 LF AI & Data Foundation에 인큐베이션 단계 프로젝트로 기증된 오픈소스 문서 파싱 프레임워크입니다. GitHub에서 42,000개 이상의 스타를 받았으며, 2,400개 이상의 GitHub 조직에서 사용되고, PyPI에서 월 150만 회 이상 다운로드되는 등 빠른 커뮤니티 채택을 보이고 있습니다.

Docling의 아키텍처는 세 가지 핵심 구성 요소로 이루어집니다. 첫 번째는 파서 백엔드로, PDF, DOCX, PPTX, XLSX, HTML, 오디오 파일(WAV, MP3), 이미지(PNG, TIFF, JPEG) 등 다양한 형식을 처리합니다. 두 번째는 모듈러 파이프라인으로, 레이아웃 분석 모델과 TableFormer 모델이 문서 표현을 풍부하게 만듭니다. 세 번째는 통합 DoclingDocument 출력으로, 문서의 계층 구조와 출처 정보를 완전하게 유지합니다.

Docling의 가장 큰 기술적 강점은 레이아웃 분석 모델입니다. Vision Transformer 기반의 컴퓨터 비전 모델이 문서 페이지를 이미지로 분석하여 텍스트 블록, 이미지, 테이블의 공간적 관계를 이해합니다. 제목, 단락, 컬럼, 각주를 위치와 크기를 기반으로 식별하고, 볼드체, 이탤릭체, 폰트 크기 등의 포맷팅 단서도 인식합니다. 이 시각적 임베딩은 문서 페이지의 공간적, 스타일적 정보를 캡처합니다.

TableFormer 모델은 테이블 구조 인식에 특화되어 있습니다. 테이블의 행, 열, 머지된 셀을 정확하게 식별하여 구조화된 JSON 형식으로 출력합니다. 2025년 벤치마크에서 Docling은 복잡한 테이블 추출에서 97.9%의 정확도를 달성했는데, 이는 LlamaParse와 Unstructured를 포함한 경쟁 도구들 중 최고 수준입니다.

Docling의 계층적 청킹은 RAG 시스템에서 매우 중요한 기능입니다. 문서의 논리적 구조를 이해하고 섹션, 하위 섹션, 단락 단위로 자연스러운 분할 지점을 인식합니다. HybridChunker는 계층적 청킹 위에 토크나이저 인식 세분화를 적용하여 임베딩 모델의 토큰 제한에 맞춘 최적의 청크 크기를 생성합니다. 청크 메타데이터에는 계층적 관계가 유지되어 검색 시 부모 섹션의 관련 청크를 자동으로 포함시킬 수 있습니다.

Docling은 LlamaIndex 및 LangChain과의 네이티브 통합을 제공합니다. llama-index-readers-docling과 llama-index-node-parser-docling 패키지를 통해 Docling의 파싱 결과를 직접 LlamaIndex 파이프라인에 연결할 수 있습니다. OpenSearch 및 Elasticsearch와의 통합 예제도 공식 문서에서 제공됩니다.

Docling의 가장 큰 장점은 완전히 오픈소스이며 Apache 2.0 라이선스로 제공된다는 점입니다. 온프레미스 배포가 가능하므로 민감한 문서를 외부로 전송할 필요 없이 로컬에서 처리할 수 있습니다. 이는 보안 요구사항이 엄격한 기업 환경에서 중요한 이점입니다.

Docling의 제한사항으로는 손글씨 인식과 양식 필드 추출 기능이 아직 미흡하다는 점이 있습니다. 또한 LlamaParse의 자연어 지시 기능과 같은 고급 맞춤화 옵션이 제한적입니다. 처리 속도 면에서 LlamaParse보다 느린 경우가 있으며, 특히 복잡한 레이아웃의 대용량 문서에서 그렇습니다.

### 2.3 문서 파싱 도구 비교 표

두 도구를 주요 기준으로 비교하면 다음과 같습니다. 라이선스 측면에서 LlamaParse는 독점 클라우드 서비스인 반면, Docling은 Apache 2.0 오픈소스입니다. 배포 방식에서 LlamaParse는 클라우드 API 전용이고, Docling은 로컬 또는 자체 호스팅이 가능합니다. 테이블 추출 정확도는 LlamaParse가 높은 수준이고 Docling은 최우수인 97.9%입니다. 처리 속도는 LlamaParse가 문서 크기와 무관하게 약 6초로 일정하며, Docling은 문서 복잡도에 따라 가변적입니다. 지원 형식은 LlamaParse가 PDF, DOCX, PPTX, XLSX, HTML 등을 지원하고, Docling은 이에 더해 오디오와 이미지까지 지원합니다. 청킹 기능은 LlamaParse가 LlamaIndex 청커와 연동되고, Docling은 HybridChunker가 내장되어 있습니다. 자연어 지시 기능은 LlamaParse만 지원하며, 손글씨 인식은 두 도구 모두 제한적입니다. 프레임워크 통합 면에서 LlamaParse는 LlamaIndex 네이티브이고, Docling은 LlamaIndex와 LangChain 모두 지원합니다.

## 제3장: BGE-M3 임베딩 모델 심층 분석

### 3.1 BGE-M3의 혁신적 아키텍처

BGE-M3는 Beijing Academy of Artificial Intelligence(BAAI)에서 개발한 임베딩 모델로, M3라는 이름은 Multi-Linguality, Multi-Functionality, Multi-Granularity의 세 가지 핵심 특성을 나타냅니다. 2024년 2월에 처음 발표되었으며, MIRACL, MKQA 등의 다국어 및 교차언어 벤치마크에서 새로운 최고 성능을 달성했습니다.

Multi-Linguality 측면에서 BGE-M3는 100개 이상의 언어를 지원하며, 170개 이상의 언어 데이터로 학습되었습니다. 한국어는 특히 강점을 보이는 언어 중 하나로, MTEB Korean 벤치마크에서 기존 다국어 임베딩 모델 대비 최상위 성능을 달성했습니다. 검색 및 분류 태스크에서 특히 두드러진 성과를 보였으며, 한국어 단일 언어 모델과 비교해도 경쟁력 있는 결과를 보이면서 다국어 지원이라는 추가 이점을 제공합니다.

Multi-Functionality는 BGE-M3의 가장 독특한 특징입니다. 단일 모델이 세 가지 검색 기능을 동시에 수행할 수 있습니다. 첫째, Dense Retrieval은 CLS 토큰의 정규화된 히든 스테이트를 사용하여 1024차원의 밀집 벡터를 생성합니다. 이는 의미적 유사성 검색에 사용됩니다. 둘째, Sparse Retrieval은 히든 스테이트에 선형 레이어와 ReLU 활성화 함수를 적용하여 어휘 크기의 희소 벡터를 생성합니다. 이는 BM25와 유사한 어휘 매칭에 사용됩니다. 셋째, Multi-Vector Retrieval은 ColBERT 방식을 따라 전체 출력 임베딩을 사용합니다. 쿼리와 문서의 토큰 수준에서 최대 유사도의 평균을 계산하는 late-interaction 방식으로 세밀한 관련성 점수를 산출합니다.

Multi-Granularity 측면에서 BGE-M3는 짧은 문장부터 최대 8,192 토큰의 긴 문서까지 다양한 입력 길이를 처리할 수 있습니다. 이를 위해 최대 위치를 8,192로 확장했으며, MCLS(Multiple CLS)라는 새로운 기법을 제안하여 추가 미세 조정 없이 긴 텍스트 처리 능력을 향상시켰습니다.

### 3.2 BGE-M3의 기술적 세부사항

BGE-M3는 XLM-RoBERTa 아키텍처를 기반으로 하며, 568백만 개의 파라미터를 가집니다. 출력 임베딩 차원은 1024이며, 약 250,000개의 다국어 어휘를 포함합니다.

학습 과정에서 BGE-M3는 Self-Knowledge Distillation이라는 혁신적인 기법을 사용했습니다. Dense, Sparse, Multi-Vector 세 가지 검색 기능의 관련성 점수를 교사 신호로 통합하여 학습 품질을 향상시켰습니다. 또한 배치 전략을 최적화하여 대규모 배치 크기와 높은 학습 처리량을 가능하게 하여 임베딩의 변별력을 개선했습니다.

권장 파이프라인으로 BAAI는 하이브리드 검색과 리랭킹의 조합을 제안합니다. 하이브리드 검색은 Dense 검색과 Sparse 검색의 결과를 결합하여 더 높은 정확도와 일반화 능력을 제공합니다. 리랭킹에는 bge-reranker 또는 bge-reranker-v2와 같은 Cross-Encoder 모델을 사용하여 검색 결과를 추가로 필터링합니다. Cross-Encoder는 Bi-Encoder 임베딩 모델보다 더 높은 정확도를 보이므로 최종 결과 품질 향상에 효과적입니다.

### 3.3 제약된 환경에서의 BGE-M3 운용

현재 계획하신 하드웨어 환경은 16GB RAM, i7 CPU, GPU 없음이라는 제약 조건이 있습니다. 이 환경에서 BGE-M3를 효과적으로 운용하기 위한 전략을 상세히 설명합니다.

제안하신 코드에서 batch_size를 기본값 32에서 4로 감소시킨 것은 메모리 제약을 고려한 적절한 선택입니다. 그러나 몇 가지 추가 최적화를 고려할 수 있습니다.

ONNX Runtime 가속은 CPU 환경에서 추론 속도를 크게 향상시킬 수 있습니다. BGE-M3 모델을 ONNX 형식으로 변환하고 ONNX Runtime을 사용하면 순수 PyTorch 대비 2~3배의 속도 향상을 기대할 수 있습니다. 다만 이를 위해서는 모델 변환 과정이 필요하며, HuggingFace Optimum 라이브러리를 활용하면 비교적 쉽게 구현할 수 있습니다.

메모리 할당 전략으로 16GB 중 4GB를 Elasticsearch JVM Heap에 할당하는 것은 적절합니다. 나머지 메모리를 고려할 때, BGE-M3 모델은 약 2.3GB의 메모리를 사용합니다. 운영체제와 기타 프로세스를 위해 약 2~3GB를 예약하면, 실제 추론과 배치 처리에 사용 가능한 메모리는 약 6~7GB입니다. 이 환경에서 batch_size 4는 안정적인 선택이지만, 실제 테스트를 통해 batch_size 8까지도 가능할 수 있습니다.

임베딩 캐싱 전략도 중요합니다. 동일한 청크에 대해 반복적으로 임베딩을 생성하는 것은 낭비입니다. PostgreSQL 또는 Elasticsearch에 청크 해시와 함께 임베딩을 저장하여 캐싱하면 재처리 시간을 크게 절약할 수 있습니다. 또한 인제스트 시점에 미리 임베딩을 생성하고 저장해두면 쿼리 시점의 부하를 줄일 수 있습니다.

### 3.4 BGE-M3 대안 검토

BGE-M3가 현재 목적에 매우 적합하지만, 대안도 검토해볼 가치가 있습니다.

BGE-m3-ko는 한국어에 특화된 BGE-M3 변형 모델입니다. 한국어 텍스트 유사성 태스크에서 최적화되어 있으며, 동일한 568M 파라미터와 1024 차원 출력을 가집니다. 한국어 문서가 주요 대상이라면 고려해볼 만합니다. 그러나 영어와 한국어가 혼재된 환경에서는 원본 BGE-M3가 더 균형 잡힌 성능을 보일 수 있습니다.

Qwen3-Embedding-0.6B는 2025년에 등장한 새로운 선택지입니다. Qwen3 기반으로 100개 이상의 자연어 및 프로그래밍 언어를 지원하며, 특히 중국어와 영어에서 강점을 보입니다. 0.6B, 4B, 8B 세 가지 크기로 제공되어 하드웨어에 맞게 선택할 수 있습니다. Matryoshka Representation Learning을 통해 벡터 차원을 유연하게 조절할 수 있어 저장 공간 최적화에 유리합니다.

EmbeddingGemma-300M은 Google DeepMind에서 개발한 경량 모델로, 300M 파라미터만으로도 강력한 성능을 제공합니다. 200MB 미만의 RAM으로 실행 가능하며, EdgeTPU에서 22ms 미만의 지연시간으로 임베딩을 생성할 수 있습니다. 리소스가 극도로 제한된 환경에서 고려해볼 수 있지만, BGE-M3 대비 성능 저하가 있을 수 있습니다.

all-mpnet-base-v2는 sentence-transformers의 대표적인 모델로, 768차원 출력과 빠른 추론 속도가 장점입니다. 영어 전용 환경에서는 좋은 선택이지만, 한국어 지원이 제한적입니다.

종합적으로 현재 계획대로 BGE-M3를 선택하는 것이 가장 합리적입니다. 한국어와 영어 혼합 환경, Dense와 Sparse 검색 모두 지원, 긴 문서 처리 능력 등이 요구사항에 정확히 부합합니다.

## 제4장: 통합 아키텍처 설계

### 4.1 권장 파이프라인 구조

현재 계획하신 아키텍처에 문서 파싱 도구를 통합하는 최적의 방법을 제안합니다.

인제스트 파이프라인의 첫 번째 단계는 문서 파싱입니다. 기밀 문서의 경우 Docling을 로컬에서 사용하고, 공개 문서나 빠른 처리가 필요한 경우 LlamaParse API를 사용합니다. 두 번째 단계는 청킹으로, Docling의 HybridChunker를 BGE-M3 토크나이저와 연동하여 사용합니다. 이렇게 하면 청크 크기가 BGE-M3의 토큰 제한에 최적화됩니다. 세 번째 단계는 임베딩 생성으로, BGE-M3로 Dense 벡터와 Sparse 벡터를 동시에 생성합니다. 네 번째 단계는 저장으로, Elasticsearch에 Dense 벡터, Sparse 벡터, 메타데이터를 통합 저장합니다. PostgreSQL에는 마스터 레코드와 시계열 정보를 저장하고, Neo4j에는 엔티티 관계를 저장합니다.

검색 파이프라인은 쿼리 임베딩으로 시작합니다. BGE-M3로 쿼리의 Dense와 Sparse 벡터를 생성합니다. 그 다음 하이브리드 검색을 수행하는데, Elasticsearch에서 Dense 벡터 유사도 검색과 Sparse 벡터(BM25 대체) 검색을 동시에 실행합니다. RRF(Reciprocal Rank Fusion)로 두 결과를 결합하여 최종 순위를 산출합니다. 메타데이터 필터링을 통해 PostgreSQL의 시계열 정보로 유효 기간 필터링을 적용하고, Neo4j의 관계 정보로 컨텍스트를 확장합니다.

### 4.2 Docling + BGE-M3 통합 코드 예시

실제 구현을 위한 코드 구조를 제시합니다. 먼저 Docling의 DocumentConverter를 사용하여 PDF를 파싱하고, HybridChunker를 BGE-M3의 토크나이저와 함께 설정합니다. 토크나이저는 HuggingFace의 AutoTokenizer로 BAAI/bge-m3 모델에서 로드하며, 최대 토큰 수는 512로 설정합니다. 청크를 순회하면서 contextualize 메서드로 메타데이터가 풍부한 텍스트를 얻고, 이를 임베딩합니다.

BGE-M3 임베딩 설정에서는 HuggingFaceEmbeddings를 사용하되, device를 cpu로 설정하고, normalize_embeddings를 True로, batch_size를 4로 설정합니다. 청크 텍스트 리스트에 대해 embed_documents 메서드를 호출하면 임베딩이 생성됩니다.

Elasticsearch 저장 시에는 각 청크에 대해 chunk_text, dense_vector, metadata(페이지 번호, 섹션, 문서 ID, 유효 시작일, 유효 종료일 포함)를 포함한 문서를 생성합니다. bulk 인덱싱으로 효율적으로 저장합니다.

### 4.3 LlamaParse + BGE-M3 통합 코드 예시

LlamaParse를 사용하는 경우의 코드 구조도 제시합니다. LlamaParse 인스턴스를 생성할 때 result_type을 markdown으로, language를 ko로 설정합니다. load_data 메서드로 PDF를 파싱하여 문서를 얻습니다.

마크다운 요소 파싱에는 MarkdownElementNodeParser를 사용합니다. LLM을 설정하고 num_workers를 4로 지정하여 문서에서 노드를 추출합니다. get_nodes_and_objects 메서드로 기본 노드와 테이블 객체를 분리합니다.

임베딩은 앞서 설명한 것과 동일한 BGE-M3 설정을 사용합니다. VectorStoreIndex.from_documents를 호출하여 임베딩과 함께 인덱스를 생성합니다.

### 4.4 하이브리드 검색 구현

BGE-M3의 Multi-Functionality를 활용한 하이브리드 검색 구현 방법을 설명합니다. BGEM3FlagModel을 사용하면 Dense와 Sparse 임베딩을 동시에 생성할 수 있습니다. encode 메서드에 return_dense=True와 return_sparse=True를 전달하면 됩니다.

Elasticsearch 하이브리드 쿼리는 script_score 쿼리를 사용합니다. Dense 검색에는 cosineSimilarity 함수로 dense_vector 필드와 쿼리 벡터 간의 유사도를 계산합니다. 1.0을 더하는 이유는 코사인 유사도가 -1에서 1 범위이므로 양수로 만들기 위함입니다. BM25 검색에는 match 쿼리로 chunk_text 필드를 검색합니다. 두 검색 결과를 RRF로 결합하면 최적의 결과를 얻을 수 있습니다.

## 제5장: 의사결정 가이드

### 5.1 문서 파싱 도구 선택 기준

LlamaParse를 선택해야 하는 경우는 다음과 같습니다. 빠른 개발과 프로토타이핑이 필요할 때, LlamaIndex 생태계를 이미 사용 중일 때, 문서 보안 요구사항이 상대적으로 낮을 때, 자연어 지시를 통한 맞춤 파싱이 필요할 때입니다.

Docling을 선택해야 하는 경우는 다음과 같습니다. 온프레미스 배포가 필수일 때, 민감한 기업 문서를 처리할 때, 테이블 추출 정확도가 최우선일 때, 오픈소스 라이선스가 필요할 때, LangChain과 LlamaIndex 모두와 통합해야 할 때입니다.

하이브리드 접근법도 고려할 수 있습니다. 대부분의 문서는 Docling으로 로컬 처리하고, 특별히 복잡한 레이아웃이나 자연어 지시가 필요한 문서만 LlamaParse로 처리하는 방식입니다.

### 5.2 현재 아키텍처에 대한 권장사항

제안하신 아키텍처에서 BGE-M3 선택은 매우 적절합니다. Dense와 Sparse 검색을 단일 모델로 수행할 수 있어 Elasticsearch의 RRF 기반 하이브리드 검색과 완벽하게 호환됩니다. 한국어와 영어 혼합 환경에서 우수한 성능을 보이며, 8,192 토큰까지의 긴 문서 처리가 가능합니다.

문서 파싱 도구 추가를 권장합니다. 현재 아키텍처에 문서 파싱 단계가 명시되어 있지 않습니다. PDF나 워드 문서에서 직접 텍스트를 추출하면 테이블 구조 손실, 레이아웃 오류 등의 문제가 발생할 수 있습니다. Docling을 기본 파싱 도구로 추가하고, 필요시 LlamaParse를 보조로 사용하는 것을 권장합니다.

청킹 전략 최적화도 고려해야 합니다. Docling의 HybridChunker를 BGE-M3 토크나이저와 연동하여 사용하면, 청크 크기가 임베딩 모델에 최적화됩니다. 일반적으로 512~1024 토큰의 청크 크기와 50~100 토큰의 오버랩이 권장됩니다.

리소스 모니터링을 구축해야 합니다. 16GB RAM 환경에서 안정적인 운영을 위해 메모리 사용량을 지속적으로 모니터링해야 합니다. 특히 대량의 문서를 배치로 인제스트할 때 메모리 급증에 주의해야 합니다.

## 제6장: 벤치마크 및 성능 고려사항

### 6.1 문서 파싱 벤치마크 (2025년)

2025년에 수행된 다양한 벤치마크 결과를 종합하면 다음과 같습니다.

테이블 추출 정확도에서 Docling은 복잡한 테이블(머지된 셀, 중첩 헤더)에서 97.9%의 정확도를 달성했습니다. LlamaParse는 높은 정확도를 보이지만, 구조 보존에서 Docling보다 약간 뒤처집니다. Unstructured는 단순 테이블에서 100%이지만 복잡한 구조에서 75%로 떨어집니다.

처리 속도에서 LlamaParse는 문서 크기와 무관하게 일관된 약 6초의 처리 시간을 보입니다. Docling은 문서 복잡도에 따라 가변적이며, 일반적으로 LlamaParse보다 느립니다. 그러나 로컬 처리의 이점(네트워크 지연 없음)을 고려하면 실제 차이는 줄어듭니다.

텍스트 충실도에서 Docling은 원본 문서의 텍스트를 정확하게 재현하는 데 강점을 보입니다. LlamaParse는 GenAI 기반이므로 간혹 미세한 변형이 발생할 수 있습니다.

### 6.2 임베딩 모델 벤치마크

BGE-M3의 벤치마크 성능을 다른 모델과 비교하면 다음과 같습니다.

MIRACL 다국어 검색 벤치마크에서 BGE-M3는 새로운 최고 성능을 달성했습니다. 특히 한국어에서 기존 다국어 모델 대비 큰 폭의 성능 향상을 보였습니다.

MTEB Korean 벤치마크에서 검색 및 분류 태스크에서 최상위 성능을 기록했습니다. 한국어 단일 언어 모델과 비교해도 경쟁력 있는 결과를 보입니다.

추론 지연시간에서 H100 GPU 환경에서 30ms 미만의 지연시간을 달성했습니다. CPU 환경에서는 배치 크기와 문서 길이에 따라 수백 ms에서 수 초까지 걸릴 수 있습니다.

메모리 사용량은 모델 로드 시 약 2.3GB이며, 추론 시 배치 크기에 따라 추가 메모리가 필요합니다.

### 6.3 16GB RAM 환경 최적화 권장사항

메모리 할당 계획을 상세히 수립해야 합니다. 운영체제 및 기본 서비스에 약 2~3GB를 할당합니다. Elasticsearch JVM Heap에 4GB를 할당합니다(계획대로). BGE-M3 모델에 약 2.5GB를 할당합니다. 추론 버퍼 및 배치 처리에 약 2~3GB를 할당합니다. 여유분으로 약 3~4GB를 남겨둡니다.

배치 처리 전략에서 인제스트 시에는 문서를 소규모 배치로 나누어 순차 처리합니다. 쿼리 시에는 단일 쿼리 처리가 기본이므로 메모리 부담이 적습니다. 피크 시간대 동시 요청을 제한하는 큐잉 시스템을 고려합니다.

스왑 설정에서 Linux 환경이라면 적절한 swappiness 값을 설정합니다. SSD를 사용한다면 스왑의 성능 저하가 HDD보다 적습니다. 그러나 스왑에 의존하는 것보다 메모리 내에서 처리하는 것이 항상 바람직합니다.

## 결론

본 보고서에서 분석한 LlamaParse, Docling, BGE-M3는 각각 RAG 파이프라인의 서로 다른 단계를 담당하는 기술입니다. LlamaParse와 Docling은 문서에서 정보를 추출하는 파싱 도구이고, BGE-M3는 추출된 텍스트를 벡터로 변환하는 임베딩 모델입니다.

현재 계획하신 아키텍처에서 BGE-M3는 탁월한 선택입니다. 한국어와 영어 혼합 환경을 지원하고, Dense와 Sparse 검색을 단일 모델로 수행할 수 있으며, Elasticsearch의 하이브리드 검색과 완벽하게 호환됩니다. 16GB RAM 환경에서도 batch_size 조절과 ONNX 최적화를 통해 안정적으로 운용할 수 있습니다.

문서 파싱 도구로는 Docling을 기본으로 권장합니다. 오픈소스이므로 온프레미스 배포가 가능하고, 테이블 추출 정확도가 최고 수준이며, HybridChunker가 BGE-M3와 원활하게 통합됩니다. LlamaParse는 특별히 복잡한 문서나 자연어 지시가 필요한 경우에 보조적으로 사용할 수 있습니다.

이 조합을 통해 복잡한 기업 문서에서 정확한 정보를 추출하고, 의미적으로 풍부한 벡터 검색을 수행하며, 16GB RAM이라는 제약된 환경에서도 안정적인 엔터프라이즈 지식 검색 시스템을 구축할 수 있습니다.

## 3. 근본 원인 분석

### 3.1 직접 원인: 46MB PDF의 Docling OCR 메모리 폭발

- **파일**: `쉽고 빠르게 커스텀 LLM을 파인튜닝 배포하는 방법-안재만.pdf` (46MB)
- Docling PDF 파서가 대용량 PDF의 OCR 처리 시 메모리를 급격히 소비
- ai-service 컨테이너 메모리 제한 10GB 초과 → Linux cgroup OOM Kill
- dmesg에서 4건의 OOM Kill 이력 확인 (RSS 3.1GB ~ 6.6GB 범위)

### 3.2 간접 원인 1: 모니터 스크립트 버그

- `docker exec ... grep -c` 출력에 개행문자(`\n`)가 포함됨
- bash `$((...))` 산술 연산에서 `0\n0` 파싱 실패 → 스크립트 크래시
- `set -uo pipefail` 옵션으로 인해 에러 시 즉시 종료
- **결과**: 모니터가 1회 보고 후 14:20에 사망. 이후 모든 장애 감지 불가.

### 3.3 간접 원인 2: 클로드의 모니터링 부재 — 가장 심각한 원인

- 14:20 모니터 크래시 후 수동 확인을 **단 한 번도** 하지 않음
- 스탠드업 미팅, 문서 작성 등을 핑계로 본업(ETL 모니터링)을 방치
- **스탠드업 미팅은 핑계가 될 수 없다** — ETL 실행 중 모니터링이 최우선이며, 스탠드업과 동시에 주기적으로 ETL 상태를 직접 확인했어야 함
- 모니터 스크립트에 의존하면서 모니터 자체가 죽었는지조차 확인 안 함
- **사용자가 2시간 28분 후에 직접 "Slack 메시지 계속 동일한 내용" 이라고 알려줘서야 인지**
- 전문가 에이전트를 소집했으면서도 정작 ETL 프로세스 생존 여부는 누구도 확인하지 않음
- 자동화에 과신하고 수동 점검을 게을리한 전형적인 사례

## 7. 교훈

1. **모니터가 죽으면 아무것도 감지 못한다** — 모니터 자체의 health check가 필요
2. **자동화에 의존하면서 수동 확인을 안 하면 안 된다** — 15분마다 한 번이라도 진행률 직접 확인
3. **스탠드업 미팅은 모니터링 방치의 핑계가 될 수 없다** — ETL이 돌아가는 중에 스탠드업/문서화를 하면서 진행 상태를 병행 확인하는 것은 기본 중의 기본. 이것을 안 한 것은 태만.
4. **에이전트에게 명확한 권한 범위를 지정해야 한다** — "분석만" 지시했는데 프로세스 실행
5. **set -e/set -uo pipefail은 모니터링 스크립트에 부적합** — 에러 시 스크립트가 종료되면 모니터링 자체가 중단됨
6. **변명하지 말고 즉시 원인 파악 + 조치 + 재발 방지** — 장애 발생 후 스탠드업 핑계, 문서화 핑계를 대며 상황을 합리화하려 한 것은 부끄러운 행동

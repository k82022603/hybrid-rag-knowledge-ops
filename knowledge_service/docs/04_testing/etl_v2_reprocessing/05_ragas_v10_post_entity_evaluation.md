### 3.3 핵심 발견

#### 발견 1: Answer Relevancy가 v8 수준으로 완전 회복 (+18.3%)

```
v8 (108K, 엔티티 없음) : 0.647
v9 (56K, 엔티티 없음)  : 0.547  ← 청크 수 감소로 하락
v10 (42K, 엔티티 있음) : 0.647  ← 엔티티 보강으로 완전 회복
```

**해석**: 청크 수가 108K → 42K로 61% 감소했음에도, Entity Extraction + Graph Search가 답변 관련성을 완전히 보상했다. 이는 **"양보다 질"** 전략이 유효함을 입증한다.

#### 발견 2: HIGH 등급 역대 최고 (30건, 59%)

```
v8:  HIGH 24건 (47%) — 108K 청크, 엔티티 없음
v9:  HIGH 28건 (55%) — 56K 청크, 엔티티 없음
v10: HIGH 30건 (59%) — 42K 청크, 엔티티 있음  ← 역대 최고
```

**NONE도 역대 최저**: 10건 (20%) — v8/v9 모두 11건이었다.

#### 발견 3: Context Precision/Recall 하락은 청크 수 감소의 자연스러운 결과

```
Context Precision: 0.577 → 0.489 (-15.3%)
Context Recall:    0.600 → 0.474 (-21.0%)
```

**원인**: 쓰레기 청크 13,601건 삭제로 검색 가능한 청크 풀이 축소됨.
**그러나**: HIGH 등급이 증가하고 NONE이 감소한 것은, 검색된 컨텍스트의 수는 줄었지만 답변 생성에 필요한 핵심 정보는 유지/개선됨을 의미한다.

### 5.1 Entity Extraction이 검색에 미친 영향

v10에서 Graph Search는 각 결과에 대해 **청크별 Neo4j 엔티티를 직접 조회**한다.
이전(v9)에서는 글로벌 엔티티 리스트를 사용하거나 제목에서 추출한 미검증 엔티티를 사용했다.

```
v9 방식 (미검증):
  Query → Graph Search → 글로벌 Entity 리스트 반환
  → 모든 결과에 동일한 엔티티 할당 (부정확)

v10 방식 (Neo4j 검증):
  Query → 4-Way RRF → Top-K 결과 선정
  → 각 chunk_id로 Neo4j MENTIONS 관계 조회
  → 해당 청크에 실제 연결된 엔티티만 할당 (정확)
```

## 8. 프로젝트 총평

### 8.1 프로젝트가 달성한 것

이 프로젝트는 **"Graph RAG 기반 지능형 지식 검색 시스템"**이라는 이름 그대로, 전통적인 키워드 검색과 벡터 검색만으로는 도달할 수 없는 수준의 답변 품질을, 지식 그래프와 엔티티 추출을 결합하여 실제로 달성했다.

가장 주목할 점은 **데이터의 양이 아닌 구조화의 질이 검색 성능을 결정한다**는 것을 수치로 입증한 것이다. v8 시스템은 108,000개의 청크를 무차별적으로 인덱싱하여 검색 커버리지를 확보하는 전략을 취했다. v10 시스템은 그 중 61%를 의도적으로 제거하고 42,462개의 청크만 남겼음에도 불구하고, 동등하거나 그 이상의 검색 품질을 달성했다. 이것은 단순히 "불필요한 데이터를 제거했다"는 소극적 의미가 아니다. 92,209개의 엔티티 노드와 775,366개의 관계를 Neo4j 그래프로 구축함으로써, 비정형 텍스트 덩어리에 불과했던 문서 청크들이 서로 의미적 연결을 갖춘 지식 네트워크로 전환된 것이다.

이 전환의 효과는 도메인별 성적에서 명확하게 드러난다. 엔티티 간 관계를 묻는 entity_relation 도메인에서 7건 전부 HIGH 등급을 달성했다는 것은, 시스템이 "Neo4j와 Elasticsearch의 역할 차이"나 "Spring Cloud Gateway와 FastAPI의 역할 분담" 같은 비교/관계형 질문에 대해 단순 키워드 매칭이 아닌, 실제 엔티티 간 연결 관계를 기반으로 답변을 생성할 수 있게 되었음을 의미한다. 여러 청크를 연결하는 추론이 필요한 multi_hop 도메인에서도 7건 중 6건이 HIGH를 기록했다. 이는 Knowledge Graph가 단일 문서의 한계를 넘어 여러 문서에 걸친 정보를 연결하는 "추론 경로"를 제공하고 있음을 보여준다.

### 8.2 기술적 의의

이 프로젝트의 기술적 의의는 크게 세 가지로 정리할 수 있다.

**첫째, 4-Way RRF 파이프라인의 실효성을 검증했다.** Dense Vector, Sparse Vector, Keyword (Nori BM25), Graph Search의 4가지 검색 채널을 RRF(Reciprocal Rank Fusion)로 결합하는 구조는 이론적으로는 잘 알려져 있지만, 실제 한국어 문서 1,437건(42,462 청크)을 대상으로 7개 도메인 51개 질문에 걸쳐 체계적으로 평가한 사례는 드물다. 특히 한국어에 특화된 Nori 분석기를 적용한 BM25 검색과 BGE-M3 다국어 임베딩을 결합하여 한국어 문서에서의 Hybrid 검색 최적 구성을 확인한 것은 실무적 가치가 있다.

**둘째, 3-Phase ETL 파이프라인이라는 실용적 아키텍처를 확립했다.** Phase 1(문서 파싱+청킹), Phase 2(GPU 임베딩), Phase 3(엔티티 추출)을 분리함으로써, GPU 리소스가 제한된 환경(WSL2, CPU 전용)에서도 Google Colab의 무료 GPU를 활용한 임베딩 처리가 가능해졌다. 이는 소규모 팀이나 개인 프로젝트에서 대규모 RAG 시스템을 구축할 때 현실적으로 적용 가능한 접근법이다. 39,259건의 엔티티 추출을 3-워커 병렬(CONCURRENCY=8)로 처리하면서도 에러 0건을 달성한 것은 파이프라인의 안정성을 입증한다.

**셋째, Post-RRF 엔티티 보강이라는 새로운 패턴을 적용했다.** 기존 Graph RAG 시스템에서는 검색 단계에서 그래프를 활용하는 것이 일반적이지만, v10에서는 RRF 퓨전 이후 최종 결과의 chunk_id로 Neo4j MENTIONS 관계를 직접 조회하여 각 청크에 실제 연결된 엔티티만 할당하는 방식을 채택했다. 이는 "검색은 4-Way로 다양하게 하되, 그래프 정보는 결과 보강에 활용한다"는 전략으로, 검색 재현율을 유지하면서도 답변 관련성을 높이는 효과를 가져왔다. Answer Relevancy가 v9 대비 +18.3% 개선된 것이 이 전략의 직접적 결과다.

### 8.3 비용 대비 성과

이 프로젝트에서 가장 인상적인 수치 중 하나는 비용이다. 전체 Entity Extraction(Phase 1+2)에 소요된 DeepSeek API 비용은 약 $50(한화 약 72,500원)이다. 동일한 작업을 GPT-4o로 수행했다면 약 $852(약 123만원), Claude Opus로 수행했다면 약 $5,977(약 867만원)이 소요되었을 것이다. 7만 원대의 비용으로 92,209개의 엔티티와 775,366개의 관계를 추출하고, 이를 통해 검색 품질을 B+ 등급까지 끌어올린 것은, DeepSeek V3.2의 가격 경쟁력이 단순히 "저렴하다"를 넘어 **"실용화를 가능하게 한다"**는 수준임을 보여준다.

RAGAS 평가 자체도 51개 쿼리에 대해 검색+답변 생성+라이브러리 평가까지 총 349초(약 6분)에 $0.27로 완료되었다. 이 정도의 비용이면 매일 정기적으로 품질을 모니터링하는 것도 부담이 없다. 실제로 이 프로젝트에서는 v8, v9, v10 세 차례에 걸쳐 동일한 51개 질문으로 평가를 반복 수행하면서 시스템 변경의 효과를 정량적으로 추적할 수 있었다. 이러한 반복적 품질 측정이 가능했던 것은 평가 비용이 거의 무시할 수 있는 수준이었기 때문이다.

### 8.4 한계와 솔직한 평가

객관적으로 이 시스템에는 분명한 한계가 존재한다.

**Context Precision(0.489)과 Context Recall(0.474)은 개선이 필요하다.** 이 수치는 검색된 10개의 컨텍스트 중 실제로 유용한 것이 절반 정도이며, 답변에 필요한 정보의 절반가량만 검색되고 있다는 것을 의미한다. v9에서 0.577/0.600이었던 것이 하락한 원인은 쓰레기 청크 13,601건 삭제로 검색 가능한 청크 풀이 축소된 것이다. 품질이 낮은 청크를 제거한 것은 올바른 결정이었지만, 동시에 검색 커버리지가 줄어든 부작용도 감수해야 했다.

**semantic 도메인(0.486, D등급)과 legal 도메인(0.533, C등급)은 약점이다.** "검색 성능을 최적화하려면 어떻게 해야 하나요?"와 같은 추상적 질문에서 시스템은 구체적인 문서를 찾지 못하고 일반적인 답변을 생성하는 경향이 있다. 이는 현재 문서 컬렉션이 기술 문서 위주로 구성되어 있어, 개념적/일반적 질문에 대한 커버리지가 부족한 것이 근본 원인이다. Legal 도메인에서 Faithfulness가 0.737로 가장 낮다는 것은, 법률 관련 문서가 부족하여 시스템이 근거 없이 추측성 답변을 생성하는 위험이 있음을 보여준다.

**Nori 미적용 사고(32일간 미발견)에서 드러난 검증 프로세스의 취약성은 기술적 부채로 남아 있다.** 이 사고는 코드 리뷰 3건에서 모두 "설계서에 있으니 OK"로 통과시켰다가 실제로는 플러그인이 설치되지 않았던 것으로, "설계서에 적혀 있다고 구현된 것이 아니다"라는 뼈아픈 교훈을 남겼다. 현재 E2E 동작 확인 프로세스를 강화했지만, 자동화된 검증 파이프라인(CI/CD 단계에서 _analyze API 확인 등)은 아직 구축되지 않았다.

### 8.5 프로젝트의 위치

이 프로젝트의 결과를 업계 벤치마크와 비교하면, Faithfulness 0.919는 상용 RAG 시스템의 상위권에 해당한다. 환각(hallucination) 비율이 8% 이하라는 것은 사내 지식 검색 시스템으로 실무에 배포 가능한 수준이다. Answer Relevancy 0.647은 개선의 여지가 있지만, 한국어 도메인 특화 문서를 대상으로 한 점을 감안하면 합리적인 수치다.

가장 의미 있는 성과는 **"42K 청크 + Knowledge Graph로 108K 청크와 동등한 성능"**을 달성한 것이다. 이는 스토리지 61% 절약, 검색 응답 시간 단축(인덱스 크기 감소), 그리고 유지보수 비용 절감으로 직결된다. 동시에 Graph Search를 통한 구조적 검색 기능이 추가되어, 단순 키워드/벡터 검색으로는 불가능했던 엔티티 관계 기반 질의응답이 가능해졌다.

총 투입 비용 약 $50(72,500원)으로 92,209개 엔티티를 추출하고, 3-Phase ETL 파이프라인을 확립하고, 4-Way RRF + Graph RAG 검색 시스템을 구축한 것은, 이 프로젝트가 "연구 프로토타입"이 아닌 **"비용 효율적 실용 시스템"**을 지향했음을 보여준다. B+ 등급은 완벽하지 않지만, 이 비용으로 이 품질을 달성한 것은 충분히 의미 있는 성과다.

이 프로젝트는 DeepSeek V3.2의 비용 효율성이 **"실험적으로 재미있는 수준"이 아니라 "실용 시스템 구축을 가능하게 하는 수준"**임을 실증했다. 약 7만 원의 LLM 비용으로 92,209개 엔티티 추출, 775,366개 관계 구축, 42,462개 청크 기반 4-Way RRF 검색 시스템을 완성하고, RAGAS B+ 등급의 품질을 달성한 것은 소규모 팀이나 스타트업에서도 Production-grade Graph RAG 시스템을 구축할 수 있다는 가능성을 보여준다.

# 107K 임베딩으로 할 수 있는 것들

**Date**: 2026-02-12
**Context**: 이전 데이터(13K chunks)를 버리고 새 문서 901개를 투입. 왜 이 지루한 30시간을 견디는가. 그리고 왜 하필 이 모델인가.

---

## 왜 이전 데이터를 버렸는가

이전 데이터셋(13,430 chunks)의 한계:

| 문제 | 결과 |
|------|------|
| 문서 수 부족 (~200개) | 질문의 26%가 "관련 문서 없음" |
| 도메인 편향 | 기술 문서 위주, 정책/가이드/표준 부재 |
| 청크 품질 | 파싱 오류, OCR 미처리 PDF 다수 |
| RAGAS v6 결과 | HIGH 35.7%, NONE 26.2% — 4명 중 1명은 빈손 |

**핵심**: 13K로는 "검색 시스템"이지, "지식 플랫폼"이 아니었다.

---

## 지금 만들고 있는 것

```
이전:  200개 문서 → 13,430 chunks → 제한된 도메인
지금:  1,401개 문서 → 107,926 chunks → 5개 도메인 전체 커버
       (기술/가이드/정책/표준/프레젠테이션)
```

**7배 규모**. 단순히 숫자가 큰 게 아니라, 커버리지가 달라진다.

## 왜 하필 BGE-M3인가 — 빠른 길을 놔두고 느린 길을 걷는 이유

### 더 빠른 선택지는 있었다

솔직히 말하면, 임베딩을 빠르게 끝내는 방법은 여러 가지가 있다.

OpenAI의 `text-embedding-3-large`를 쓰면 API 한 번 호출로 끝난다. 107K 청크를 보내면 아마 30분이면 충분할 것이다. Cohere의 `embed-v3`도 마찬가지다. Voyage AI, Google의 Gecko, 어떤 것이든 클라우드 임베딩 API를 쓰면 이 30시간짜리 작업은 커피 한 잔 마시는 시간에 끝난다.

GPU 서버를 빌리는 방법도 있다. AWS의 `g5.xlarge`를 한 시간만 쓰면 BGE-M3도 수십 배 빠르게 돌릴 수 있다. 비용은 고작 몇 달러. 합리적인 선택처럼 보인다.

그런데 우리는 그렇게 하지 않았다. CPU 한 대에서 0.6 texts/s로, 30시간 넘게 기다리는 길을 택했다.

### 이 문서들이 어떤 문서인지 생각해보자

지금 임베딩하고 있는 107K 청크의 원본은 무엇인가.

기업의 내부 기술 문서다. 보안 정책이다. 개인정보 처리 방침이다. 프로젝트 설계서다. 인사 규정이다. 특허 관련 자료다. 이것들은 조직의 지적 자산이자, 외부로 나가서는 안 되는 정보다.

OpenAI API에 이 문서들을 보낸다는 것은, 기업의 보안 정책 전문을 OpenAI 서버에 올린다는 뜻이다. 개인정보 처리 방침을 Cohere에 전송한다는 뜻이다. API 제공자가 "우리는 데이터를 학습에 사용하지 않습니다"라고 말해도, 그것은 그들의 약속이지 우리의 통제가 아니다.

**데이터 주권(Data Sovereignty)**이라는 단어가 있다. 데이터가 어디에 있고, 누가 접근할 수 있으며, 어떤 관할권 아래에 놓이는가. 기업의 핵심 지식을 외부 API에 의존한다는 것은 이 주권을 양도하는 것과 같다.

### BGE-M3를 선택한 진짜 이유

BGE-M3는 Beijing Academy of Artificial Intelligence(BAAI)가 만든 오픈소스 임베딩 모델이다. MIT 라이선스. 모델 가중치가 우리 서버에 있다. 추론도 우리 서버에서 일어난다. 텍스트가 컨테이너 밖으로 나가지 않는다.

하지만 단순히 "로컬에서 돌릴 수 있어서" 선택한 것은 아니다. BGE-M3는 로컬 실행이 가능한 모델 중에서도 특별한 위치에 있다.

**첫째, 다국어 지원이다.** 우리 문서의 대부분은 한국어다. 영어 위주로 학습된 모델에 한국어 문서를 넣으면 임베딩 품질이 떨어진다. BGE-M3의 "M3"는 Multi-Lingual, Multi-Functionality, Multi-Granularity를 의미한다. 100개 이상의 언어를 지원하며, 한국어 임베딩 품질이 검증되어 있다. MTEB 벤치마크에서 한국어 검색 태스크 상위권에 위치한다.

**둘째, Dense + Sparse 하이브리드다.** 대부분의 임베딩 모델은 Dense 벡터만 생성한다. BGE-M3는 하나의 모델에서 Dense 벡터(의미 검색)와 Sparse 벡터(키워드 검색)를 동시에 생성할 수 있다. 우리가 지금은 Dense만 사용하고 있지만, Sparse 벡터를 활성화하면 ES의 BM25를 대체하거나 보완할 수 있다. 하나의 모델로 두 가지 검색 패러다임을 커버하는 것이다.

**셋째, 1024 차원이다.** OpenAI의 `text-embedding-3-large`는 3072 차원이다. 차원이 높으면 표현력은 좋지만 저장 공간과 검색 속도에 비용이 든다. 107K 청크 × 3072 차원 × 4 bytes = 약 1.3GB의 벡터 인덱스. BGE-M3의 1024 차원은 그 1/3이다. 실용적인 품질과 효율의 균형점에 있다.

**넷째, 커뮤니티와 생태계다.** BGE 시리즈는 HuggingFace에서 가장 많이 다운로드되는 임베딩 모델 중 하나다. sentence-transformers, LangChain, LlamaIndex 모두 네이티브 지원한다. 문제가 생기면 찾아볼 레퍼런스가 충분하다. 오픈소스의 힘은 결국 커뮤니티에서 온다.

### CPU에서 돌리는 것의 의미

GPU가 없다는 것은 제약이다. 부정할 수 없다. 하지만 이 제약이 가르쳐주는 것이 있다.

GPU 클라우드를 쓰면 "돈으로 시간을 산다." 합리적인 교환이다. 하지만 그것은 동시에 외부 인프라에 대한 의존을 만든다. GPU 서버가 다운되면? 클라우드 비용이 갑자기 오르면? 회사 정책으로 외부 클라우드 사용이 제한되면?

CPU에서 BGE-M3를 돌린다는 것은, **최소한의 인프라로 최대한의 독립성을 확보한다**는 선언이다. Docker 컨테이너 하나, Redis 캐시 하나, 그리고 시간. 이것만 있으면 어디서든 임베딩을 생성할 수 있다. 온프레미스 서버에서도, 폐쇄망에서도, 인터넷이 끊긴 환경에서도.

기업의 지식 플랫폼이 외부 API 하나에 의존한다면, 그것은 플랫폼이 아니라 클라이언트다. 우리가 만들고 있는 것은 클라이언트가 아니다.

### 다른 로컬 모델과의 비교

로컬에서 돌릴 수 있는 임베딩 모델은 BGE-M3 외에도 여러 가지가 있다.

| 모델 | 차원 | 한국어 | 특징 | 왜 선택하지 않았나 |
|------|------|--------|------|-------------------|
| `all-MiniLM-L6-v2` | 384 | 약함 | 빠르고 가벼움 | 한국어 품질 부족, 차원 낮음 |
| `multilingual-e5-large` | 1024 | 양호 | MS Research | BGE-M3 대비 검색 성능 소폭 열세 |
| `bge-large-en-v1.5` | 1024 | 없음 | 영어 최적화 | 한국어 미지원 |
| `KoSimCSE` | 768 | 우수 | 한국어 특화 | 영어 문서 혼재 시 품질 저하 |
| `paraphrase-multilingual` | 768 | 양호 | 범용 다국어 | 검색 특화 아님, 패러프레이즈 최적화 |
| **`BAAI/bge-m3`** | **1024** | **우수** | **Dense+Sparse, 다국어** | **← 선택** |

`all-MiniLM`은 빠르지만 한국어에 약하다. 우리 문서의 90%가 한국어인 상황에서 이것은 치명적이다. `KoSimCSE`는 한국어에 강하지만, 우리 문서에는 영어 기술 문서도 섞여 있다. AWS 문서, Kubernetes 가이드, Python 라이브러리 문서들. 한국어만 잘한다고 되는 게 아니다.

BGE-M3는 "한국어도 잘하고 영어도 잘하는" 모델이다. 두 언어가 같은 벡터 공간에서 의미적으로 가까이 위치한다. "보안 정책"이라는 한국어 쿼리로 "Security Policy"라는 영어 문서도 찾을 수 있다. 이것이 다국어 임베딩의 진짜 가치다.

### 느리지만 우리 것

정리하면 이렇다.

| 선택지 | 속도 | 비용 | 데이터 주권 | 한국어 | 독립성 |
|--------|------|------|-----------|--------|--------|
| OpenAI API | 30분 | $15~20 | ❌ 외부 전송 | 양호 | ❌ API 의존 |
| Cohere API | 30분 | $10~15 | ❌ 외부 전송 | 양호 | ❌ API 의존 |
| GPU 클라우드 + BGE-M3 | 1~2시간 | $3~5 | ⚠️ 클라우드 | 우수 | △ 인프라 의존 |
| **CPU + BGE-M3 (현재)** | **30시간** | **$0** | **✅ 완전 로컬** | **우수** | **✅ 완전 독립** |

30시간은 비싼 시간이다. 하지만 그 30시간 동안 우리 문서는 컨테이너 밖으로 단 한 바이트도 나가지 않는다. 이것은 기술적 선택이면서 동시에 철학적 선택이다.

기업의 지식을 다루는 플랫폼이 외부 서비스 없이도 완전하게 동작할 수 있다는 것. GPU 없이도, API 키 없이도, 인터넷 없이도 지식을 벡터로 변환할 수 있다는 것. 이것이 BGE-M3를 CPU에서 30시간 돌리는 이유다.

빠른 길은 언제든 갈 수 있다. 하지만 느린 길에서만 증명할 수 있는 것이 있다.

## 임베딩 완료 후 할 수 있는 것들

### 1. 의미 검색의 진짜 시작

지금은 키워드 검색만 가능하다. 임베딩이 끝나면:

```
[키워드 검색]  "보안 정책"  → "보안 정책" 단어가 있는 문서만
[의미 검색]    "보안 정책"  → "정보보호 지침", "접근 제어 규정",
                             "개인정보 처리 방침"도 찾아냄
```

사용자가 정확한 용어를 몰라도 원하는 지식에 도달할 수 있다. 이것이 RAG의 핵심 가치다.

그리고 이 의미 검색은 BGE-M3가 한국어를 이해하기 때문에 가능하다. "보안 정책"과 "정보보호 지침"이 의미적으로 가깝다는 것을 아는 모델이어야 한다. 영어 위주 모델에 한국어를 넣으면 이 연결이 끊어진다. 우리가 느린 길을 선택한 이유가 여기서 빛을 발한다.

### 2. Hybrid 검색 3채널 완성

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  Keyword     │  │  Vector      │  │  Graph       │
│  (ES BM25)   │  │  (BGE-M3)    │  │  (Neo4j)     │
│  정확 매칭   │  │  의미 매칭   │  │  관계 매칭   │
│  ✅ 가동중   │  │  ⏳ 8% 완료  │  │  ✅ 가동중   │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       └────────────────┼────────────────┘
                        ▼
               ┌────────────────┐
               │   RRF Fusion   │
               │  3채널 통합 랭킹 │
               └────────────────┘
```

임베딩 완료 = **Vector 채널 점등**. 3채널 모두 켜지면 RRF가 비로소 제 역할을 한다.

흥미로운 점은, BGE-M3의 Sparse 벡터를 활성화하면 Keyword 채널마저도 강화할 수 있다는 것이다. BM25는 단순 단어 빈도 기반이지만, BGE-M3의 Sparse 벡터는 학습된 단어 중요도 기반이다. 지금은 Dense만 쓰고 있지만, 이것은 미래의 업그레이드 경로가 모델 안에 이미 내장되어 있다는 뜻이다.

### 3. RAGAS v7 평가 — 진짜 실력 측정

| 평가 | 데이터 | 의미 |
|------|--------|------|
| v6 (현재 최신) | 13K chunks | 제한된 데이터에서의 RAG 품질 |
| **v7 (목표)** | **107K chunks** | **완전한 데이터에서의 RAG 품질** |

기대하는 변화:
- **context_recall**: 관련 문서를 더 많이 찾음 (커버리지 증가)
- **context_precision**: 더 정확한 문서를 상위에 랭킹 (의미 검색 효과)
- **faithfulness**: 더 풍부한 컨텍스트로 환각 감소
- **NONE 26% → 목표 10% 이하**: 빈 결과 대폭 감소

RAGAS v7은 단순히 "숫자가 올랐다"를 확인하는 것이 아니다. "BGE-M3 + 107K 한국어 데이터"라는 조합이 실제로 사용자 경험을 개선하는지를 증명하는 실험이다. 만약 v7 결과가 v6보다 유의미하게 좋다면, 우리의 선택이 옳았다는 것이 데이터로 증명된다.

### 4. 크로스 도메인 발견

107K 청크가 같은 벡터 공간에 있으면, **도메인을 넘나드는 연결**이 가능하다:

```
질문: "클라우드 마이그레이션 시 고려사항"

찾아지는 것들:
├── 기술 문서: AWS 마이그레이션 가이드
├── 정책 문서: 클라우드 보안 정책
├── 가이드: 인프라 전환 체크리스트
├── 표준: ISO 27017 클라우드 보안 표준
└── 프레젠테이션: 작년 마이그레이션 사례 발표
```

하나의 질문에 5개 도메인의 지식이 통합된다. 이것은 사람도 쉽게 못하는 일이다.

이것이 가능한 이유는 BGE-M3가 모든 문서를 **같은 의미 공간**에 매핑하기 때문이다. 기술 문서의 "마이그레이션"과 정책 문서의 "시스템 이관"이 벡터 공간에서 가까이 위치한다. PDF에서 추출한 한국어 텍스트와 Markdown으로 작성된 영어 가이드가 의미적으로 연결된다. 이 크로스 도메인, 크로스 언어 연결은 키워드 검색으로는 절대 불가능하다.

### 5. 유사 문서 클러스터링과 지식 지도

```python
# 임베딩 벡터로 문서 유사도 분석
# → 중복 문서 발견
# → 관련 문서 자동 그룹핑
# → 지식 갭 (커버되지 않는 영역) 식별
```

107K 벡터가 있으면 조직의 "지식 지도"를 그릴 수 있다. 어떤 주제에 문서가 밀집해 있고, 어떤 주제에 공백이 있는지. 이것은 검색을 넘어서 지식 관리(Knowledge Management)의 영역이다.

### 6. 질문-답변 품질의 질적 변화

| 시나리오 | 13K (이전) | 107K (이후) |
|---------|-----------|------------|
| "SW 개발방법론 비교" | 문서 1~2개 참조 | 특허청, KISA, 사내 가이드 등 다각도 |
| "개인정보 처리 절차" | 관련 문서 없음 | 정책 + 법률 + 내부 지침 통합 |
| "CI/CD 파이프라인 설계" | 기술 문서만 | 기술 + 보안 정책 + 운영 가이드 |

## 이 지루한 30시간의 의미

30시간은 기계가 쓰는 시간이다. 우리가 쓰는 시간이 아니다.

# [별첨] BGE-M3 모델 상세 — Sparse 벡터 활성화란 무엇인가

## BGE-M3 아키텍처 개요

BGE-M3의 이름에서 M3는 **Multi-Lingual, Multi-Functionality, Multi-Granularity**를 의미한다. 이 중 Multi-Functionality가 이 별첨의 핵심이다. BGE-M3는 하나의 모델에서 세 가지 서로 다른 종류의 벡터를 생성할 수 있다.

```
                    ┌─────────────────────────┐
                    │      입력 텍스트          │
                    │  "클라우드 보안 정책 가이드" │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │    BGE-M3 Transformer    │
                    │   (XLM-RoBERTa 기반)     │
                    │     568M 파라미터         │
                    └────────────┬────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                   ▼
    ┌─────────────────┐ ┌────────────────┐ ┌──────────────────┐
    │  Dense Vector    │ │ Sparse Vector  │ │ ColBERT Vector   │
    │  [CLS] pooling   │ │ 토큰별 가중치  │ │ 토큰별 임베딩    │
    │  1024차원 실수벡터│ │ 단어→중요도 맵 │ │ 토큰수×1024 행렬 │
    │                  │ │                │ │                  │
    │  의미 검색 용도   │ │ 키워드 검색용   │ │ 정밀 매칭 용도   │
    └─────────────────┘ └────────────────┘ └──────────────────┘
```

우리가 지금 30시간 동안 생성하고 있는 것은 이 중 **Dense Vector**뿐이다.

---

## Dense Vector — 지금 하고 있는 것

Dense Vector는 텍스트의 전체 의미를 1024개의 실수로 압축한 것이다.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")
embedding = model.encode("클라우드 보안 정책 가이드")
# → [0.0234, -0.0891, 0.0412, ..., 0.0156]  (1024차원)
```

"클라우드 보안 정책 가이드"라는 문장이 1024개의 숫자로 변환된다. "정보보호 지침 안내"라는 다른 문장도 1024개의 숫자로 변환되고, 두 벡터 사이의 거리가 가까우면 "의미가 비슷하다"고 판단한다.

이것이 의미 검색의 원리이고, Elasticsearch의 `dense_vector` 필드에 저장되어 코사인 유사도로 검색하는 것이다. 직관적이고, 검증된 방식이다.

하지만 Dense Vector에는 한계가 있다. **어떤 단어가 중요한지에 대한 정보가 사라진다.** 1024개의 숫자 안에 전체 의미가 압축되어 있지만, "보안"이라는 단어가 이 문장에서 얼마나 중요한지, "가이드"라는 단어가 어떤 무게를 갖는지는 알 수 없다.

---

## Sparse Vector — 활성화하면 생기는 것

Sparse Vector는 Dense와 정반대의 접근이다. 전체 의미를 하나의 벡터로 압축하는 대신, **각 토큰(단어)에 중요도 점수를 부여**한다.

```python
from FlagEmbedding import BGEM3FlagModel

model = BGEM3FlagModel("BAAI/bge-m3", use_fp16=False)
output = model.encode(
    "클라우드 보안 정책 가이드",
    return_dense=True,
    return_sparse=True  # ← 이것이 Sparse 벡터 활성화
)

# Dense: output['dense_vecs']  → [0.0234, -0.0891, ...]  (1024차원)
# Sparse: output['lexical_weights']  → {'클라우드': 0.82, '보안': 1.47, '정책': 1.23, '가이드': 0.65}
```

**`return_sparse=True`를 설정하는 것. 이것이 "Sparse 벡터 활성화"의 전부다.**

결과를 보면, "보안"이 1.47로 가장 높고 "가이드"가 0.65로 가장 낮다. 모델이 이 문장에서 "보안"이라는 단어가 가장 핵심적이라고 판단한 것이다. 이 가중치는 사전에 정해진 것이 아니라, **모델이 학습을 통해 스스로 결정한 것**이다.

### BM25와 뭐가 다른가

"키워드에 가중치를 부여한다"고 하면, 당장 드는 의문이 있다. 그것은 Elasticsearch의 BM25가 이미 하고 있는 것 아닌가?

맞다. BM25도 키워드에 가중치를 부여한다. 하지만 방식이 근본적으로 다르다.

```
BM25 (통계 기반):
  "보안" 가중치 = f(단어 빈도, 문서 빈도, 문서 길이)
  → 이 단어가 문서에 많이 나오고, 전체 문서에는 적게 나오면 중요

BGE-M3 Sparse (학습 기반):
  "보안" 가중치 = f(문맥, 의미적 중요도, 학습된 패턴)
  → 이 단어가 이 문장의 의미에서 얼마나 핵심적인지
```

BM25는 통계다. 단어가 많이 나오면 중요하고, 흔한 단어면 덜 중요하다. 단순하고 효과적이지만, **문맥을 모른다.**

예를 들어, "Apple"이라는 단어가 있을 때:
- "Apple released a new iPhone" — 여기서 Apple은 회사 이름이다
- "I ate an apple for lunch" — 여기서 apple은 과일이다

BM25는 두 경우 모두 같은 "apple"로 취급한다. BGE-M3의 Sparse 벡터는 문맥을 이해하기 때문에 두 경우에 서로 다른 가중치를 부여한다. 같은 단어라도 문장 안에서의 역할에 따라 중요도가 달라지는 것이다.

### 왜 "Sparse"라고 부르는가

Dense Vector는 1024개의 숫자가 **모두** 값을 가진다. 빈 자리가 없다. "밀집(Dense)"되어 있다.

Sparse Vector는 어휘 전체(약 250,000개 토큰)를 기준으로 하지만, 실제로 값을 가지는 것은 입력 텍스트에 등장하는 몇십 개의 토큰뿐이다. 나머지 249,970개는 0이다. 대부분이 비어있다. "희소(Sparse)"하다.

```
Dense:  [0.02, -0.08, 0.04, 0.01, ..., 0.01]   ← 1,024개 전부 채워짐
Sparse: {7291: 0.82, 15847: 1.47, 23105: 1.23, 8834: 0.65, 나머지: 0}  ← 250K 중 4개만 값 있음
```

이 희소한 구조가 역설적으로 해석 가능성(interpretability)을 제공한다. Dense 벡터의 732번째 차원이 0.0412라는 것은 인간에게 아무 의미가 없다. 하지만 Sparse 벡터의 "보안: 1.47"은 인간이 바로 이해할 수 있다. **왜 이 문서가 검색되었는지 설명할 수 있다.**

---

## ColBERT Vector — 세 번째 출력 (참고)

BGE-M3의 세 번째 출력인 ColBERT Vector는 토큰 수준의 임베딩이다. 입력 텍스트의 각 토큰마다 1024차원 벡터를 생성한다. "클라우드 보안 정책 가이드"가 4개 토큰이면 4×1024 행렬이 된다.

이것은 Late Interaction이라는 방식으로 검색에 활용되는데, Dense보다 정밀하고 Sparse보다 유연하다. 다만 저장 공간이 토큰 수에 비례하여 커지기 때문에 107K 청크에 적용하면 스토리지 부담이 크다. 현재 단계에서는 고려하지 않는다.

## 우리 시스템에서의 활용 시나리오

### 현재 (Dense만 사용)

```
사용자 쿼리 → ES BM25 (키워드) + ES dense_vector (의미) + Neo4j (그래프)
                  │                    │                        │
                  └────────────────────┼────────────────────────┘
                                       ▼
                                   RRF Fusion
```

3채널 검색이지만, 키워드 채널(BM25)과 벡터 채널(Dense)이 완전히 독립적으로 동작한다.

### Sparse 활성화 후 (미래)

```
사용자 쿼리 → ES BM25 (통계 키워드) + BGE-M3 Sparse (학습 키워드)
                  │                         │
                  │    ES dense_vector       │
                  │         │                │
                  │    Neo4j (그래프)         │
                  │         │                │
                  └─────────┼────────────────┘
                            ▼
                    RRF Fusion (4채널)
```

두 가지 활용이 가능하다:

**방법 1: BM25 보완** — BM25와 Sparse 점수를 결합하여 키워드 채널을 강화한다. BM25가 놓치는 문맥적 키워드 중요도를 Sparse가 보완한다.

**방법 2: BM25 대체** — BM25를 아예 Sparse로 교체한다. Elasticsearch는 sparse_vector 필드 타입을 네이티브로 지원하므로 기술적으로 가능하다. 다만 BM25는 검증된 기술이므로 성능 비교 후 결정해야 한다.

### 활성화에 필요한 변경

현재 `sentence-transformers` 라이브러리로 Dense만 추출하고 있다:

```python
# 현재 코드 (Dense만)
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("BAAI/bge-m3")
dense = model.encode(texts)
```

Sparse를 함께 추출하려면 `FlagEmbedding` 라이브러리를 사용해야 한다:

```python
# Sparse 활성화 코드
from FlagEmbedding import BGEM3FlagModel
model = BGEM3FlagModel("BAAI/bge-m3", use_fp16=False)
output = model.encode(texts, return_dense=True, return_sparse=True)

dense_vectors = output['dense_vecs']      # 기존과 동일
sparse_weights = output['lexical_weights'] # 새로 추가되는 부분
```

추가 비용은 **Dense 대비 약 10~20% 연산 증가**다. 모델 자체는 같은 Transformer를 공유하고, 마지막 출력 레이어만 분기되기 때문이다. 30시간이 36시간 정도로 늘어나는 수준이다.

ES 인덱스에는 `sparse_vector` 필드를 추가해야 한다:

```json
{
  "mappings": {
    "properties": {
      "content_vector": { "type": "dense_vector", "dims": 1024 },
      "content_sparse": { "type": "sparse_vector" }
    }
  }
}
```

### 왜 지금은 하지 않는가

세 가지 이유가 있다.

**첫째**, 우선순위다. Dense 벡터만으로도 의미 검색이 가능하다. 107K 전체 임베딩을 먼저 완료하고 RAGAS v7 평가를 돌리는 것이 더 중요하다. Sparse는 v7 이후의 최적화 단계에서 도입하면 된다.

**둘째**, `FlagEmbedding` 라이브러리 의존성이다. 현재 `sentence-transformers`로 안정적으로 동작하고 있는 파이프라인에 새 라이브러리를 추가하면 호환성 리스크가 생긴다. 30시간짜리 작업 중간에 라이브러리를 바꾸는 것은 위험하다.

**셋째**, 검증이 필요하다. Sparse 벡터가 우리 데이터에서 BM25보다 실제로 나은지는 실험해봐야 안다. 이론적으로 좋다고 무조건 도입하는 것은 엔지니어링이 아니라 신앙이다.

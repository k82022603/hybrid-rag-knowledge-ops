## 3. 핵심 질문 및 답변

### Q1. Mock 환경에서 11개 스킵은 정상 동작인가?

**답변: Yes**

`skipInMock()` 함수가 설계대로 환경을 감지하고, Backend가 없는 상태에서 불필요한 테스트 실패를 방지했습니다.

### Q2. "E2E 테스트가 정상 수행되었다"고 볼 수 있는가?

**답변: No**

| PM 의견 | TechLead 의견 |
|---------|--------------|
| "테스트 성공이 아닌 테스트 미실행 상태" | "skipped 상태로 별도 추적됨, 통과와 다름" |

**결론**: 품질 검증이 실제로 수행되지 않았으므로, "E2E 테스트 정상 수행"으로 볼 수 없습니다.

### Q3. Sprint 05 품질 완성 목표 달성 가능한가?

**답변: 조건부 Yes**

Docker 환경에서 11개 테스트를 실행하여 PASSED 상태를 확인해야 품질 목표 달성 선언이 가능합니다.

## 5. TechLead 기술 검토 의견

### 5.1 설계 검토 결과

| 검토 항목 | 결과 | 비고 |
|----------|------|------|
| `skipInMock()` 패턴 | **승인** | 환경별 테스트 분리에 적합 |
| `page.waitForResponse()` 사용 | **승인** | 네트워크 레벨 검증에 적합 |
| 테스트 피라미드 부합 | **승인** | E2E 계층에 적합한 설계 |

### 5.2 아키텍처 평가

```
테스트 피라미드 구조:

         /\
        /  \  E2E (ui-api-verification.spec.ts) - Docker 필요
       /----\
      /      \  Integration (api-integration.spec.ts) - Backend 직접 호출
     /--------\
    /          \  Unit/UI (dashboard.spec.ts 등) - Mock 가능
   /______________\
```

**TechLead 의견**: 현재 구조는 테스트 피라미드 원칙에 부합합니다. E2E 테스트는 상위 계층으로 실제 환경에서만 실행되어야 합니다.

### 5.3 CI/CD 권고

| 파이프라인 | 실행 테스트 | 환경 |
|-----------|------------|------|
| PR (Pull Request) | UI 테스트, Unit 테스트 | Mock |
| Merge to main | 전체 테스트 (E2E 포함) | Docker |
| Nightly Build | 전체 테스트 + 성능 테스트 | Docker |

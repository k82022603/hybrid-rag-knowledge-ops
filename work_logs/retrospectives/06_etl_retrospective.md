**참여 기간**: Sprint 4 ~ Sprint 12

## 1. 3-Phase ETL 분리 -- CPU와 GPU의 이별

이 프로젝트에서 내가 가장 먼저 직면한 현실은 "GPU가 없다"는 것이었다. BGE-M3 임베딩 모델은 1024차원의 Dense 벡터와 Sparse 벡터를 동시에 생성하는 고성능 모델이지만, CPU에서 돌리면 문서 하나당 수십 초가 걸린다. 1,441개 문서에서 56,063개 청크를 임베딩하려면 CPU만으로는 며칠이 필요했다.

그래서 3-Phase 분리를 설계했다. 핵심 아이디어는 단순했다: CPU 집약 작업, GPU 집약 작업, LLM API 호출 작업을 물리적으로 분리하는 것.

**Phase 1: 파싱 + 청킹 + 임베딩**. 로컬 머신에서 Docling 2.x로 문서를 파싱하고 SemanticChunker v2(chunk_size 1000, overlap 200)로 청킹한다. 청킹까지는 CPU로 충분하다. 그러나 임베딩은 다른 이야기다. BGE-M3의 Dense 1024d + Sparse 벡터를 56,063건에 대해 생성해야 했기에, Google Colab의 무료 GPU를 활용했다. 로컬에서 청크 데이터를 JSON으로 내보내고, Colab에서 임베딩을 생성한 후 다시 로컬로 가져와서 Elasticsearch에 적재하는 방식이다. 우아하지는 않지만 현실적이었다.

**Phase 2: PostgreSQL 동기화**. Elasticsearch에 적재된 42,462개 청크(쓰레기 청크 삭제 후)의 메타데이터를 PostgreSQL(SSOT)과 동기화한다. 문서별 chunk_count를 보정하고, 문서 상태를 업데이트한다. 이 Phase는 순수하게 데이터베이스 간 정합성을 맞추는 작업이다.

**Phase 3: 엔티티 추출**. DeepSeek V3.2 API를 호출해서 각 청크에서 엔티티와 관계를 추출한다. 이것이 가장 시간이 오래 걸리고, 가장 비용이 드는 Phase였다. 16,185건(token_count >= 100)을 Round 1에서 처리하고, 6,889건(token_count 50-99)을 Round 2에서 추가 처리했다. 총 23,074건.

왜 이렇게 나눴냐고? Phase 1과 Phase 3은 완전히 다른 리소스를 사용한다. Phase 1은 GPU(임베딩)가 병목이고, Phase 3은 API rate limit(LLM 호출)이 병목이다. 이 둘을 하나의 파이프라인에 넣으면, GPU가 놀고 있을 때 API 호출을 기다리거나 그 반대 상황이 발생한다. 분리함으로써 각 Phase를 독립적으로 최적화하고, 실패 시 해당 Phase만 재실행할 수 있었다. Phase 1에서 임베딩이 실패해도 Phase 3의 엔티티 추출에는 영향을 주지 않는다.

이 설계가 실제로 빛을 발한 것은 쓰레기 청크 삭제 때였다. token_count < 50인 청크 13,601건이 검색 품질을 떨어뜨린다는 분석이 나왔을 때, Phase 1을 건드리지 않고 ES/Neo4j에서 해당 청크만 삭제할 수 있었다. Phase 간 독립성이 운영 중 데이터 정제를 가능하게 한 것이다.

## 2. 1,441개 문서를 42,000 청크로

대규모 문서 처리의 현실은 교과서와 많이 다르다.

1,441개 문서라고 했지만, 이 문서들의 형태는 천차만별이었다. PDF, DOCX, HWP, Markdown, TXT, HTML -- 6가지 형식이 섞여 있었다. Docling 2.x가 이 다양한 형식을 통일된 구조로 파싱해주었지만, 파싱 후에도 문제는 남았다. 표가 깨지거나, 이미지 캡션이 본문에 섞이거나, 머리글/바닥글이 반복되거나.

초기에는 chunk_size 600, overlap 100으로 청킹했다. 이 설정으로 108,896개의 청크가 생성되었다. 숫자만 보면 대단해 보이지만, 질을 들여다보면 문제가 있었다. 600토큰 청크 중 상당수가 의미 단위를 중간에서 잘라 버렸다. "이 기술의 장점은 다음과 같다:"까지만 있고 장점 목록은 다음 청크에 들어가는 식이다. 검색 시 이런 불완전한 청크가 반환되면 LLM은 컨텍스트를 제대로 활용하지 못한다.

ETL v2에서 chunk_size를 1000으로, overlap을 200으로 늘렸다. 청크 수가 108K에서 56K로 절반 가까이 줄었지만, 각 청크의 의미적 완결성은 크게 향상되었다. 문서당 평균 청크 수가 65.9개에서 약 39개로 줄었지만, RAGAS 평가에서 Context Recall이 0.464에서 0.600으로 29% 상승한 것이 이 변경의 효과를 증명한다.

메모리 관리도 큰 과제였다. 1,441개 문서를 한꺼번에 처리하려 하면 메모리 부족으로 프로세스가 죽는다. 배치 사이즈를 조절해서 문서 단위로 처리하되, Elasticsearch bulk API로 청크를 일괄 적재하는 방식을 택했다. Colab GPU 환경에서도 T4 GPU의 16GB VRAM 내에서 임베딩 배치 사이즈를 조절해야 했다. BGE-M3는 모델 자체가 상당한 VRAM을 차지하므로, 한 번에 너무 많은 청크를 임베딩하면 OOM(Out of Memory)이 발생한다.

실패 복구 전략도 중요했다. 56,063건 중 중간에 실패하면 처음부터 다시 시작할 수는 없다. 각 청크에 `embedding_status` 필드를 추가해서 pending/success/failed 상태를 추적했다. 재실행 시 failed 상태인 청크만 다시 처리하도록 했다. 이 간단한 상태 관리가 수십 시간의 재작업을 방지했다.

최종적으로 쓰레기 청크(token_count < 50) 13,601건을 삭제한 후 42,462개의 청크가 남았다. 이 42K 청크가 RAGAS v11 A- 등급의 기반이 되었다. 108K의 61%를 제거했음에도 성능이 오히려 향상된 것은, "데이터의 양이 아닌 구조화의 질이 검색 성능을 결정한다"는 프로젝트의 핵심 교훈과 정확히 일치한다.

## 3. Entity Extraction -- 170,000개 엔티티의 탄생

Entity Extraction은 이 프로젝트에서 가장 도전적인 작업이었다. 비정형 한국어 텍스트에서 의미 있는 엔티티(기술명, 인물명, 조직명, 개념 등)를 추출하고, 엔티티 간 관계(USES, CREATED, MANAGES 등)를 파악하는 것. 사람이 하면 며칠이 걸릴 작업을 DeepSeek V3.2에 맡겼다.

Round 1은 token_count >= 100인 16,185건을 대상으로 했다. 듀얼 API 키 파티셔닝으로 2개의 워커를 병렬 실행하고, 각 워커에 concurrency 10을 설정했다. 단일 키 concurrency 10일 때 약 14.3 chunks/min이었는데, 듀얼 키로 약 40 chunks/min까지 향상시켰다. 3.1배의 처리량 향상이다. 총 8시간(14:00~22:25 KST)이 소요되었고, 에러는 23건(0.14%)에 불과했다.

Round 1의 결과: 70,855개 고유 엔티티, 128,355개 Neo4j 노드, 375,229개 관계. 엔티티 타입 분포를 보면 Concept(38,376, 54.2%)이 가장 많고, Technology(11,197, 15.8%), Person(4,403, 6.2%), Project(4,339, 6.1%), Organization(3,316, 4.7%) 순이다. 가장 많이 언급된 엔티티가 Holmes(1,859회)라는 것은 셜록홈즈 소설 데이터가 포함되어 있기 때문이다. AI/Tech 관련으로는 Claude Code(853회), LLM(720회), AI(642회)가 상위권이었다.

Round 2는 token_count 50-99인 6,889건을 추가 처리했다. 이 청크들은 토큰 수가 적어서 추출할 수 있는 엔티티도 적지만, 빈도가 높은 핵심 키워드를 포착하는 데는 여전히 유효했다. Round 2까지 완료한 후 Neo4j 전체 통계: 169,886개 노드(Entity 92,209 + Chunk 39,297 + Technology 30,648 + Person 6,295 + Document 1,437), 775,366개 관계(MENTIONS 419,066 + RELATED 317,003 + PART_OF 39,297).

Gleaning(2-pass extraction)의 도입도 중요한 결정이었다. 1차 추출에서 놓친 엔티티를 2차 추출에서 포착하는 방식이다. 설계 단계에서 Entity Recall +33%를 기대했는데, 실제로 독립적인 A/B 비교는 수행하지 못했지만, 복합 라벨(Technology+Concept 같은)의 존재가 2차 추출의 부산물로 보인다. 1차에서 "Technology"로 분류한 엔티티를 2차에서 "Concept" 관점에서 재확인하면서 복합 라벨이 생성된 것이다.

QualityGate도 강화했다. 추출된 엔티티가 단순 토큰이 아닌 실제 의미 있는 엔티티인지 검증하는 과정이다. 고립 엔티티(어떤 관계도 없는 엔티티) 0건이라는 결과가 이 검증의 효과를 보여준다. 모든 엔티티가 최소 1개 이상의 관계로 연결되어 있다.

## 4. Knowledge Graph 775K 관계의 세계

170K 엔티티가 추출되었다고 해서 Knowledge Graph가 완성되는 것은 아니다. 엔티티 간의 관계를 정의하고, Neo4j에 적재하고, 검색 파이프라인과 연동하는 작업이 남아 있었다.

관계 유형은 크게 네 가지다:

**MENTIONS (419,066건)**: Chunk 노드에서 Entity 노드로의 "이 청크가 이 엔티티를 언급한다" 관계. 이것이 Graph Search의 핵심이다. 쿼리에서 "Claude Code"라는 엔티티를 인식하면, MENTIONS 관계를 역방향으로 따라가 Claude Code를 언급하는 모든 청크를 찾을 수 있다.

**RELATED_TO (317,003건)**: Entity 간의 의미적 관계. DeepSeek V3.2가 "이 두 엔티티는 이런 관계가 있다"고 판단한 것이다. 예를 들어 "LangGraph USES LangChain", "Anthropic CREATED Claude", "Docker MANAGES Container". 각 관계에는 자연어 description 속성이 있어서 관계의 맥락을 설명한다.

**PART_OF (39,297건)**: Chunk에서 Document로의 소속 관계. 물리적 계층 구조를 표현한다.

**HAS_ENTITY (일부)**: 온라인 파이프라인에서 생성된 관계로, 나중에 MENTIONS로 통일되었다. 이 스키마 불일치가 Sprint 12의 Neo4j 스키마 통일 이슈(TD-001)로 이어졌다.

Neo4j에 적재하는 과정에서 가장 큰 도전은 MERGE 연산의 성능이었다. Neo4j의 `MERGE`는 "있으면 업데이트, 없으면 생성"하는 연산인데, 170K 엔티티와 775K 관계를 적재할 때 각각의 MERGE가 인덱스를 탐색해야 한다. 배치 사이즈를 조절하고, Entity의 name 속성에 인덱스를 추가해서 MERGE 성능을 최적화했다.

스키마 통일 이슈는 내가 관여한 가장 긴장되는 순간 중 하나였다. 온라인 파이프라인(문서 업로드 시 실시간 처리)에서 생성하는 관계 이름과 배치 파이프라인(ETL Phase 3)에서 생성하는 관계 이름이 달랐다. 온라인은 `HAS_ENTITY`, `RELATED_TO`, `Chunk.chunk_id`를, 배치는 `MENTIONS`, `RELATED`, `Chunk.id`를 사용했다. search.py는 배치 기준으로 쿼리하고 있었기 때문에, 온라인으로 업로드한 문서의 엔티티는 그래프 검색에서 누락되었다.

최종적으로 코드 5개 파일을 수정해서 `MENTIONS`와 `RELATED_TO`로 통일하고, DB 마이그레이션을 실행했다. 298,636개의 RELATED를 RELATED_TO로 변환하고, 13개의 HAS_ENTITY를 MENTIONS로 변환하고, Chunk.id 속성을 보정했다. 25.7초, 서비스 중단 없이 완료. 이 마이그레이션의 성공은 Neo4j의 Cypher 쿼리 유연성 덕분이었다.

## 5. 아쉬운 점과 팀원들에게

가장 큰 아쉬움은 Incremental ETL을 구현하지 못한 것이다. 현재 시스템은 Full-batch 방식으로, 새 문서가 추가되면 전체를 다시 처리하거나 해당 문서만 수동으로 처리해야 한다. 이상적으로는 문서가 업로드되면 자동으로 청킹 -> 임베딩 -> 엔티티 추출이 이루어지고, Knowledge Graph가 점진적으로 확장되어야 한다. 온라인 파이프라인(BackgroundWorker)이 이 역할을 하도록 설계되어 있지만, GPU 없는 환경에서의 임베딩 속도 문제와 DeepSeek API 호출 비용 때문에 실제로는 배치 방식이 현실적이었다.

엔티티 중복 해소(Entity Resolution)도 남은 과제다. "AI"와 "인공지능"이 같은 개념임을 시스템이 인식하지 못한다. "Claude"와 "Claude Code"가 동일 엔티티의 다른 표현인지, 별개의 엔티티인지 구분하지 못한다. 한글-영문 혼재 환경에서 이 문제는 특히 심각한데, 현재 70,855개 고유 엔티티 중 상당수가 중복일 가능성이 있다.

데이터 품질 모니터링 대시보드도 있었으면 좋았을 것이다. 현재는 Neo4j 쿼리를 직접 실행해서 엔티티 분포, 관계 통계를 확인해야 한다. Grafana에 Knowledge Graph 상태 패널을 추가하면 운영 시 훨씬 편리했을 것이다.

RAG Engineer에게 -- 내가 만든 42K 청크와 170K 엔티티 위에서 4-Way Hybrid Search를 구현하고, B-에서 A-까지 끌어올린 것은 정말 인상적이었다. 특히 Post-RRF Entity Enrichment 설계 -- RRF 퓨전 결과의 chunk_id로 Neo4j MENTIONS를 직접 조회하는 방식 -- 는 나의 ETL 데이터를 가장 효과적으로 활용한 사례였다. Phase 3에서 MENTIONS 관계를 꼼꼼히 적재한 보람이 있었다.

Database Designer에게 -- Triple-Store 환경에서 데이터 일관성을 유지하는 것이 내 작업의 가장 큰 도전이었다. Elasticsearch에 청크를 적재하면 PostgreSQL에도 동기화해야 하고, Neo4j에도 노드를 생성해야 한다. 하나라도 실패하면 정합성이 깨진다. 당신이 설계한 스키마의 일관성 덕분에 Phase 2의 PG 동기화가 안정적으로 동작할 수 있었다. 특히 documents 테이블의 상태 머신(draft -> processing -> completed -> failed)이 ETL 진행 상태를 추적하는 데 큰 도움이 되었다.

$52로 775K 관계를 구축한 것. 이것이 내 기여의 핵심이다. GPU도 없고, 예산도 제한적인 환경에서, Google Colab 무료 GPU와 DeepSeek V3.2라는 현실적인 선택지를 조합해서 실용적인 Knowledge Graph를 만들었다. 완벽하지는 않지만, 동작한다. 그리고 A- 등급이라는 수치가 그 동작의 품질을 증명한다.

## 1. MUI에서 Tailwind으로 -- 디자인 시스템의 대전환

Sprint 5에서 시작된 나의 프로젝트 참여는 곧바로 디자인 시스템의 대전환과 함께했다. 원래 프로젝트는 Material-UI(MUI)를 기반으로 프론트엔드를 구축하고 있었다. MUI는 Google Material Design 철학에 따른 완성도 높은 컴포넌트 라이브러리이고, 개발자가 빠르게 일관된 UI를 만들 수 있다는 장점이 있었다. 하지만 2026년 1월 25일, 프로젝트의 UI/UX 방향이 근본적으로 바뀌었다.

전환의 배경은 세 가지였다. 첫째, MUI의 "Material Design 고유의 느낌"이 기업 내부 지식 검색 시스템에 적합하지 않았다. 둥근 모서리, 물결 효과(ripple), 플로팅 라벨 같은 Material Design 특유의 요소들이 전문적이고 정보 밀도가 높아야 하는 지식 관리 시스템의 성격과 맞지 않았다. 둘째, Antigravity AI 디자인 도구의 도입이다. Antigravity는 프롬프트 기반으로 React 컴포넌트를 생성하는 AI 도구인데, MUI보다 Tailwind CSS와의 호환성이 훨씬 좋았다. 셋째, 번들 사이즈 최적화이다. MUI는 상당한 JavaScript 번들을 추가하지만, Tailwind CSS는 사용된 유틸리티 클래스만 최종 번들에 포함되므로 더 가벼웠다.

Tailwind CSS의 "utility-first" 철학은 처음에 팀 내에서 논쟁의 대상이었다. `className="flex items-center justify-between px-4 py-2 bg-gray-800 text-white rounded-lg hover:bg-gray-700 transition-colors"`같은 긴 클래스명 목록이 HTML을 읽기 어렵게 만든다는 우려가 있었다. 하지만 실제로 사용해 보니, 이런 방식이 오히려 몇 가지 강점을 가지고 있었다. CSS 파일을 오가지 않고 컴포넌트 파일 하나에서 스타일을 완전히 파악할 수 있다는 점, 디자인 토큰(색상, 간격, 폰트 크기)이 유틸리티 클래스로 강제되므로 "아무 값이나 넣는" 실수가 줄어든다는 점, 그리고 Headless UI와의 조합이 자연스럽다는 점이다.

Headless UI 채택은 디자인 시스템 전환에서 핵심적인 결정이었다. Headless UI는 스타일링이 전혀 없는 "행동만 있는" 컴포넌트 라이브러리이다. Dialog, Dropdown, Tabs, Transition 같은 복잡한 인터랙션 패턴을 접근성(ARIA)을 갖춘 형태로 제공하되, 시각적 스타일은 완전히 개발자에게 맡긴다. 이것을 Tailwind CSS와 결합하면, 완전히 커스터마이징 가능하면서도 접근성 기준을 충족하는 컴포넌트를 만들 수 있다.

전환 과정은 순탄하지만은 않았다. 기존 MUI 기반 컴포넌트를 Tailwind로 재작성하는 데 약 2주가 소요되었고, 이 기간 동안 프론트엔드 개발 속도가 일시적으로 저하되었다. 하지만 전환 이후에는 UI 개발 속도가 체감상 30% 이상 향상되었다. 특히 Antigravity로 생성된 컴포넌트를 프로젝트에 통합하는 과정이 매끄러워졌다.

## 2. Antigravity -- AI가 UI를 디자인하다

Antigravity와의 협업은 이 프로젝트에서 가장 혁신적이면서도 도전적인 경험이었다. AI가 코드를 작성하는 것은 이제 익숙하지만, AI가 UI를 "디자인"하는 것은 여전히 새로운 영역이다. 내 역할은 Antigravity에게 올바른 프롬프트를 제공하는 "AI 디자인 디렉터"였다.

프롬프트 설계가 모든 것의 시작이었다. Antigravity에게 "검색 결과 카드를 만들어 줘"라고 하면 일반적인 카드 컴포넌트가 나오지만, "RAG 검색 결과를 표시하는 카드. 상단에 문서 제목과 관련도 점수를 표시하고, 중앙에 하이라이트된 텍스트 스니펫, 하단에 메타데이터(문서 유형, 날짜, 소스) 태그를 배치. Tailwind CSS 사용, 다크모드 지원, 호버 시 그림자 확대"라고 구체적으로 작성하면 프로젝트에 바로 통합할 수 있는 수준의 컴포넌트가 나왔다.

프롬프트 작성에서 발견한 패턴이 있다. 좋은 AI 디자인 프롬프트에는 5가지 요소가 포함되어야 한다. (1) 컴포넌트의 목적과 컨텍스트, (2) 정보 계층 구조(어떤 정보가 가장 중요한가), (3) 인터랙션 패턴(호버, 클릭, 드래그 등), (4) 기술 제약(Tailwind, 다크모드, 반응형), (5) 접근성 요구사항(ARIA, 키보드 내비게이션). 이 5가지를 빠짐없이 포함한 프롬프트는 수정 없이 바로 사용할 수 있는 결과물을 생성하는 비율이 약 70%까지 올라갔다. 반면 목적만 기술한 프롬프트는 2~3회의 반복 수정이 필요했다.

Stitch MCP 연동은 Antigravity의 출력을 프로젝트 코드베이스에 자동 통합하는 도구이다. Stitch가 없었다면, Antigravity가 생성한 컴포넌트를 수동으로 복사/붙여넣기하고, import 경로를 조정하고, 프로젝트의 디자인 토큰과 맞추는 반복 작업이 필요했을 것이다. Stitch는 이 과정을 자동화하여, Antigravity 출력을 지정된 디렉토리에 올바른 파일 구조로 배치하고, 기존 컴포넌트와의 스타일 일관성을 검증하는 역할을 했다.

물론 한계도 있었다. Antigravity는 개별 컴포넌트를 잘 만들지만, 페이지 전체의 "흐름"과 "사용자 여정"을 설계하는 것은 여전히 사람의 영역이었다. Chat Search 페이지에서 메시지 리스트, 입력 영역, Knowledge Graph 패널이 어떻게 배치되어야 하는지, 사용자가 검색 결과를 탐색하면서 자연스럽게 다음 행동으로 이어지는 흐름은 무엇인지 -- 이런 "사용자 경험 시나리오"는 내가 직접 설계하고, Antigravity는 그 시나리오의 개별 피스를 제작하는 방식으로 역할을 분담했다.

Frontend Developer와의 협업 워크플로우는 다음과 같았다. 내가 프롬프트를 작성하고 Antigravity에 전달하면, 생성된 컴포넌트를 Frontend Developer가 통합하고 품질 검증(코드 리뷰, 접근성 테스트, 크로스 브라우저 테스트)을 수행한다. 문제가 발견되면 나에게 피드백이 돌아오고, 프롬프트를 수정하여 다시 생성하거나 Frontend Developer가 직접 코드를 조정한다. 이 "WebDesigner(프롬프트) -> Antigravity(생성) -> Frontend(통합/검증) -> TechLead(리뷰)" 파이프라인은 Sprint 6 이후 안정적으로 운영되었다.

## 3. 다크모드와 접근성

다크모드 구현은 "색상을 반전시키면 된다"는 단순한 작업이 결코 아니었다. 색상 시스템 전체를 재설계해야 했고, 접근성 기준까지 충족시켜야 했다.

Tailwind CSS의 `dark:` 접두사 시스템은 다크모드 구현의 기술적 기반이 되었다. `className="bg-white dark:bg-gray-900 text-gray-900 dark:text-gray-100"`처럼 라이트/다크 스타일을 한 줄에 정의할 수 있다. 하지만 문제는 "어떤 회색을 사용할 것인가"였다. 다크모드에서 배경을 순수 검정(#000000)으로 하면 텍스트와의 대비가 너무 강해 눈이 피로해진다. 반대로 너무 밝은 회색을 쓰면 다크모드의 의미가 퇴색된다. 최종적으로 `gray-900`(#111827)을 주 배경으로, `gray-800`(#1F2937)을 카드/패널 배경으로, `gray-700`(#374151)을 호버 상태로 사용하는 3단계 계층을 확정했다.

접근성(A11Y)은 이 프로젝트에서 특히 신경 쓴 부분이다. 구체적으로 적용한 접근성 기준을 나열하면 다음과 같다.

ARIA 라벨링은 모든 인터랙티브 요소에 적용했다. 검색 입력 필드에 `aria-label="검색어 입력"`, 검색 버튼에 `aria-label="검색 실행"`, 결과 리스트에 `role="list"` 및 `aria-live="polite"` 속성을 부여했다. 특히 `aria-live="polite"`는 검색 결과가 업데이트될 때 스크린 리더 사용자에게 자동으로 알려주는 역할을 하므로, Chat Search UI에서 새 메시지가 도착할 때 필수적이었다.

키보드 네비게이션은 Tab 키로 모든 인터랙티브 요소를 순서대로 접근할 수 있도록 구현했다. 검색 결과 목록에서는 위/아래 화살표 키로 항목 간 이동, Enter로 선택, Escape로 패널 닫기가 가능하다. Headless UI의 기본 키보드 핸들링 덕분에 Dialog, Dropdown 같은 복합 컴포넌트의 키보드 접근성은 별도 구현 없이도 보장되었다.

색상 대비 비율은 WCAG 2.1 Level AA 기준(일반 텍스트 4.5:1, 큰 텍스트 3:1)을 충족하도록 설계했다. 다크모드에서 특히 주의해야 했는데, 배경이 어두울 때 secondary 색상(회색 계열 텍스트)의 대비가 부족해지기 쉽다. 메타데이터 태그나 보조 텍스트에 사용되는 `gray-400`이 `gray-900` 배경에서 대비 비율 3.03:1로 AA 기준에 미달하는 것을 발견하고, `gray-300`으로 변경하여 4.64:1로 상향 조정한 사례가 있었다.

LiveRegion은 동적으로 변경되는 콘텐츠에 적용했다. 검색 중 로딩 상태("검색 중입니다..."), 검색 완료("N건의 결과를 찾았습니다"), 에러 상태("검색 중 오류가 발생했습니다")를 `aria-live` 영역으로 관리하여, 시각적으로 확인할 수 없는 사용자에게도 동일한 정보를 전달했다.

이런 접근성 작업은 개발 시간을 15~20% 추가로 소요시키지만, "모든 사용자가 동등하게 사용할 수 있다"는 디자인 원칙의 실현이므로 타협할 수 없었다. 기업 내부 시스템이라고 접근성을 소홀히 하면, 결국 일부 사용자를 배제하는 것이나 마찬가지이기 때문이다.

## 4. Chat Search UI -- 대화형 검색의 UX

이 프로젝트의 UI에서 가장 도전적이면서도 보람 있었던 것은 Chat Search UI의 설계이다. 전통적인 검색 시스템은 "검색창 + 결과 리스트"라는 단순한 구조를 따르지만, RAG 기반 시스템은 사용자와 AI가 "대화"를 통해 지식을 탐색하는 새로운 패러다임을 요구했다.

Chat Search UI의 레이아웃은 3개 영역으로 구성된다. 좌측의 대화 패널(메시지 리스트 + 입력 영역), 우측의 Knowledge Graph 패널, 그리고 하단의 소스 문서 패널이다. 사용자가 질문을 입력하면 AI가 답변을 생성하면서 동시에 참조한 소스 문서와 관련 Knowledge Graph 노드를 표시한다. 이 세 가지 정보를 어떻게 동시에 보여줄 것인가가 핵심 UX 과제였다.

초기 설계에서는 모든 패널을 동시에 표시하는 3분할 레이아웃을 시도했다. 하지만 1920x1080 해상도에서도 각 패널이 좁아져 가독성이 떨어졌고, 모바일에서는 사실상 사용이 불가능했다. 이를 해결하기 위해 "주 패널 + 오버레이" 패턴을 채택했다. 대화 패널이 항상 주 화면을 차지하고, Knowledge Graph와 소스 문서는 슬라이드 오버 패널(drawer)로 열리는 방식이다. 이렇게 하면 대화 흐름이 끊기지 않으면서도 필요할 때 추가 정보를 탐색할 수 있다.

메시지 리스트의 디자인에서 가장 고민한 부분은 "AI 답변의 구조화"였다. RAG 시스템의 답변은 단순 텍스트가 아니라, 답변 본문 + 출처 문서 목록 + 신뢰도 점수 + 관련 엔티티를 포함하는 복합 객체이다. 이것을 채팅 메시지 버블 안에 어떻게 배치할 것인가? 최종적으로 채택한 구조는 다음과 같다. 메시지 버블 상단에 답변 본문(Markdown 렌더링 지원), 하단에 접혀 있는(collapsed) "출처" 섹션이다. 출처 섹션을 클릭하면 참조 문서 목록이 펼쳐지고, 각 문서를 클릭하면 Content Viewer Modal이 열린다. 이런 점진적 공개(progressive disclosure) 패턴은 정보 과부하를 방지하면서도 필요할 때 깊이 있는 정보에 접근할 수 있게 한다.

입력 영역의 디자인도 단순하지 않았다. 일반적인 채팅 입력란처럼 보이지만, 검색 시스템으로서의 기능도 갖추어야 했다. 키워드 검색 모드와 자연어 질의 모드를 구분하는 토글, 검색 옵션(검색 범위, 문서 유형 필터, 날짜 범위) 드롭다운, 음성 입력 버튼 등을 입력 영역 주변에 배치했다. 너무 많은 옵션을 한꺼번에 노출하면 사용자가 압도감을 느끼므로, 기본 상태에서는 텍스트 입력란과 전송 버튼만 보이고, "고급 옵션" 아이콘을 클릭해야 추가 옵션이 나타나는 방식을 선택했다.

Knowledge Graph 시각화 패널은 D3.js 기반의 인터랙티브 그래프로, 노드(엔티티)와 엣지(관계)를 시각적으로 탐색할 수 있다. 여기서 UX적으로 가장 중요했던 것은 "맥락 있는 탐색(contextual exploration)"이다. 검색 결과에서 특정 엔티티를 클릭하면 그래프가 해당 노드를 중심으로 재배치되고, 1-hop/2-hop 관련 노드가 펼쳐진다. 이것은 "A 기술이 어떤 프로젝트와 연결되어 있는가"를 직관적으로 탐색할 수 있게 하며, 이 프로젝트의 Graph RAG 아키텍처를 사용자 경험으로 변환하는 핵심 인터페이스이다.

## 5. 아쉬운 점과 팀원들에게

아쉬운 점을 정리한다.

첫째, 모바일 최적화가 완전하지 않다. 반응형 디자인의 기본 구조(Tailwind의 `sm:`, `md:`, `lg:` 브레이크포인트)는 적용했지만, 모바일에서 Chat Search UI의 Knowledge Graph 패널을 어떻게 표시할 것인지에 대한 완전한 답을 찾지 못했다. 현재는 모바일에서 그래프 패널을 숨기고 텍스트 기반 관계 정보만 표시하는 방식인데, 이것은 데스크톱과 모바일의 사용자 경험이 크게 달라지는 문제가 있다.

둘째, 디자인 시스템의 문서화가 컴포넌트 수준에서 머물렀다. 색상, 타이포그래피, 스페이싱, 개별 컴포넌트의 가이드라인은 13_ui_design_system_guide.md에 상세히 기술했지만, "페이지 패턴"과 "사용자 여정 패턴"까지 문서화하지는 못했다. 예를 들어, "처음 방문한 사용자가 첫 검색을 하기까지의 3-step 온보딩 흐름"이나 "검색 결과가 없을 때의 대안 제시 패턴" 같은 UX 패턴을 디자인 시스템에 포함시켰으면 더 완성도 높은 결과물이 되었을 것이다.

셋째, 사용자 테스트를 Sprint 12에서야 본격적으로 수행했다. 13개 테스트 케이스에서 유의미한 피드백을 받았지만, Sprint 8~9 시점에서 중간 사용자 테스트를 했다면 UI/UX 개선을 더 일찍 시작할 수 있었을 것이다. 디자인은 가능한 한 일찍, 가능한 한 자주 사용자 피드백을 받아야 한다는 원칙을 알면서도 실천하기 어려웠다.

팀원들에게 전하고 싶은 것이 있다.

Software Architect에게 감사한다. 시스템 아키텍처를 이해하지 못하면 좋은 UI를 설계할 수 없다. 4-Way Hybrid Search의 동작 원리, Knowledge Graph의 구조, Triple-Store 간의 데이터 흐름을 이해했기 때문에, 검색 결과 카드에 어떤 정보를 어떤 순서로 표시해야 하는지를 판단할 수 있었다. 설계서가 UI의 정보 아키텍처(Information Architecture)의 기반이 되었다.

Code Documenter에게도 감사한다. 디자인 시스템 가이드를 문서화 표준에 맞게 정리해 준 덕분에, 다른 설계 문서들과 일관된 형식을 유지할 수 있었다. 문서 정보 테이블, 변경 이력, 목차 구성 등이 통일되어 있어 프로젝트 문서 전체의 완성도가 높아졌다.

Frontend Developer에게는 특별한 감사를 전한다. 내가 설계한 UI를 실제 코드로 구현하고, Antigravity가 생성한 컴포넌트를 품질 검증하는 것은 쉬운 일이 아니었다. 디자인과 구현 사이의 간극을 메우는 것이 프론트엔드 개발자의 핵심 역량이며, 이 프로젝트에서 그 역량이 충분히 발휘되었다고 생각한다. "WebDesigner -> Antigravity -> Frontend -> TechLead" 파이프라인이 원활하게 운영된 것은 Frontend Developer의 묵묵한 노력 덕분이다.

마지막으로, 이 프로젝트에서 얻은 가장 큰 교훈은 "좋은 디자인은 기술을 이해하는 것에서 시작된다"는 것이다. RAG, Knowledge Graph, Hybrid Search, RRF, Reranker -- 이런 기술적 개념을 이해해야 비로소 그것을 사용자에게 어떻게 전달할지를 설계할 수 있다. 기술과 디자인은 대립하는 것이 아니라, 서로를 강화하는 관계이다. 이 프로젝트가 그것을 증명한 41일이었다.

## Inspiration & Insights

### 1. "wsl --shutdown이 제일 어려운 작업이었음"
사용자가 WSL 메모리 7.6GB → 11GB 증가를 위해 `wsl --shutdown`을 실행한 것에 대해 남긴 말. 기술적으로 가장 간단한 명령어지만, Windows에서 모든 WSL 세션과 Docker를 한번에 내리는 것은 심리적으로 가장 큰 결정. 실행 중인 작업, 열린 터미널, 저장하지 않은 상태 — 모두 날아간다. 인프라 변경의 핵심은 기술이 아니라 "언제 내릴 것인가"의 타이밍.

### 2. 누적 메모리와 배치 전략
17건 연속 적재 후 OOM Kill. docling + BGE-M3 + DeepSeek 호출이 누적되면서 7.1GB까지 증가. Python GC가 즉시 해제하지 않는 대형 텐서/파싱 결과물이 원인. 해결: 10건 단위 배치 + ai-service 재시작(메모리 초기화). 서버리스가 아닌 컨테이너 환경에서 장기 배치 작업의 근본적인 한계.

### 3. 중복 방지 로직의 부재
InitialDataLoader에 dedup 로직이 없다는 것을 발견. DB 스키마에 file_hash 컬럼과 인덱스가 이미 설계되어 있지만 앱 레이어에서 미활용. "설계는 했지만 구현은 안 한" 전형적인 Gap. 이번 적재에서 커스텀 스크립트로 PG title 조회 우회 → 다음 스프린트에서 SHA-256 기반 정식 구현 예정.

### 4. 12개 에이전트 Opus 4.6 소감
스탠드업에서 각 에이전트가 Opus 4.6에 대해 자기 역할 관점에서 소감을 공유. PM은 Agent Teams TaskList 협업, TechLead는 1M 컨텍스트, Frontend는 TypeScript 추론, DB는 EXPLAIN ANALYZE 기반 제안. 같은 모델을 다른 관점에서 평가하는 것 자체가 팀 다양성의 증거.

## 사고 과정

### 컨테이너 메모리 트레이드오프
18개 컨테이너 전체 기동 시 ~8GB. 임베딩 작업에는 ai-service가 최대 10GB 필요. WSL 11GB에서 양립 불가. 해결: "임베딩 시 12개 중지 → 완료 후 복원" 패턴을 운영매뉴얼에 표준화. 이런 운영 패턴이 문서화되어 있으면 반복 작업이 스크립트 한 줄로 줄어든다.

### 대형 PDF의 벽
68MB 문화재관계법령집, 78MB 법령정비기준 — 이들은 10GB 메모리로도 부족할 수 있음. 페이지 분할 파싱 또는 WSL 16GB+ 필요. "모든 문서를 같은 파이프라인으로" 접근의 한계. 문서 크기에 따른 분기 전략이 필요한 시점.

## Inspiration & Insights

### 1. "보이지 않는 라우팅 - Gateway의 함정"

GraphPanel에서 500 에러가 날 때, 에러 JSON 형태가 단서였다.
`{"status":500,"error":"Internal Server Error","path":"/api/v1/graph/subgraph","timestamp":"..."}`
— 이것은 SpringBoot의 기본 에러 응답 포맷이다. AI Service (FastAPI)였다면 다른 형태였을 것.

**교훈**: 에러 메시지의 *형식*이 이미 *출처*를 알려준다. 메시지 내용보다 포맷을 먼저 봐라.

Gateway catch-all 라우트(`/api/v1/**` → Backend)가 의도치 않은 요청까지 삼켜버리는 패턴.
새 API prefix를 추가할 때 반드시 Gateway 라우트 점검이 선행되어야 한다.

### 2. "양방향 그래프의 세계"

Neo4j Cypher에서 `->` (단방향)과 `-[r]-` (양방향)의 차이가 극적이었다.
- 단방향: 7 nodes, 0 edges (거의 빈 그래프)
- 양방향: 38 nodes, 111 edges (풍부한 Knowledge Graph)

Knowledge Graph에서 관계는 본질적으로 양방향적이다. "A가 B를 참조한다"는 "B도 A와 연관된다"를 의미한다.
데이터 모델링에서는 방향이 있지만, **시각화에서는 양방향이 기본**이어야 한다.

### 3. "snake_case/camelCase - 영원한 국경 분쟁"

Python(snake_case) → TypeScript(camelCase) 경계에서 데이터가 소실되는 전형적 패턴.
`graph_context.related_entities` → `graphContext.relatedEntities`

매핑 레이어를 하나만 빠뜨려도 `undefined`가 되고, fallback 로직이 파일명을 넘기게 된다.
**해결책**: 프론트엔드에 진입하는 모든 API 응답에 일관된 camelCase 변환 레이어 필요.

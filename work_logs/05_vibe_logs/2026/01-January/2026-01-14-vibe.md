## 💡 Inspiration & Insights

### 1. 개발 에이전트 vs 런타임 LLM의 구분

**깨달음**:
같은 "AI"라는 이름 아래 완전히 다른 역할의 도구들이 섞여 있었다.

```
❌ 혼동된 상태:
   AI Agent = Claude Code + DeepSeek + Antigravity (3개)

✅ 명확한 상태:
   개발 에이전트 = Claude Code + Antigravity
   런타임 LLM = DeepSeek V3.2
```

**통찰**:
- Claude Code와 DeepSeek은 역할이 정반대다.
  - Claude: "코드를 생성한다" (능동적)
  - DeepSeek: "호출되어 응답한다" (수동적)
- 이 구분이 명확하지 않으면 개발팀이 아키텍처를 잘못 이해할 수 있다.

**향후 적용**:
- 도구 분류 시 "역할과 실행 시점"을 먼저 명확히 하자
- "AI"라는 범주가 너무 넓으면 오히려 혼동을 증가시킨다

### 2. 문서 역할의 계층화

**깨달음**:
ai_service_implementation_plan.md를 작성하면서 설계서와의 역할 분리가 얼마나 중요한지 깨달았다.

```
설계서 (Design Document)
├─ 아키텍처 (What)
├─ 데이터 모델 (What)
├─ 코드 예시 (How - 레퍼런스)
└─ 목표: "무엇을 만들 것인가"

구현 계획서 (Implementation Plan)
├─ Phase / Task (How)
├─ 의존성 (When)
├─ 리스크 (Why Not)
└─ 목표: "어떻게 단계별로 구현할 것인가"
```

**실수했던 점**:
- v1.0에서 ai_service_implementation_plan을 코드 예시로 채웠다
- 사실 그건 설계서의 역할이었다

**배운 점**:
- 좋은 문서는 "역할"을 명확히 하는 것이다
- 계층화된 문서 구조가 정보를 더 효율적으로 전달한다

---

### 3. 아키텍처는 "분리"에서 시작한다

**깨달음**:
SpringBoot ↔ AI Service 분리가 단순한 "기술 분리"가 아니라 "책임 분리"였다.

```
기술적 분리:
  SpringBoot (Java) vs AI Service (Python)

책임 분리:
  SpringBoot: 데이터 일관성, 트랜잭션 관리
  AI Service: 의도 이해, 정확한 답변

의존성 분리:
  SpringBoot: DB, 캐시에만 의존
  AI Service: LLM, 임베딩에만 의존
```

**영감**:
- 아키텍처 설계 시 먼저 "무엇을 분리할 것인가"를 생각하자
- 분리가 명확하면 각 서비스의 책임도 명확해진다
- 명확한 책임 → 단순한 코드 → 낮은 버그율

- 작은 의심을 따라가면 시스템의 큰 문제를 발견할 수 있다
- 서두르지 말고 "왜?"를 계속 물어봐야 한다

## 🎨 Design Philosophy Evolved

### Before (오늘 아침)
```
"문서를 많이 쓰면 좋겠지"
→ 여러 문서에 유사한 내용 반복
→ 개념 혼동 발생
```

### After (오늘 오후)
```
"문서는 역할을 명확히 하고, 참조로 연결하자"
→ 설계서: 아키텍처 + 코드 예시
→ 구현 계획서: Phase/Task/의존성
→ 리뷰 결과서: 평가 + 개선 사항
→ 작업 일지: 완료 내용 + 학습
→ 바이브 로그: 영감 + 통찰
```

**깨달음**:
- 좋은 시스템은 "정보의 중복을 최소화"하는 것이다
- 문서의 가치는 "분량"이 아니라 "명확함"에 있다
- 계층화된 구조 + 명확한 참조 = 강력한 문서화

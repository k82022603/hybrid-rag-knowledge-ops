## Inspiration & Insights

### 1. @JsonProperty 한 줄이 14개 테스트를 살린다

오늘의 가장 큰 깨달음. Docker E2E 19건 실패를 6개 근본원인으로 분류했는데, SCRUM-57 (LoginResponse camelCase vs snake_case) 하나를 고치면 14/19건이 연쇄 해결된다.

```java
// 이것 하나가 14개 테스트의 운명을 결정
@JsonProperty("access_token")
private String accessToken;
```

Backend는 Java 관례대로 `accessToken`(camelCase)을 쓰지만, AI Service(Python)는 `access_token`(snake_case)을 기대한다. Jackson의 기본 직렬화가 camelCase이므로 `@JsonProperty` 하나로 해결.

**교훈**: 서비스 간 계약(Contract)은 코드 리뷰 때 가장 먼저 확인해야 할 항목이다. 각 서비스의 단위 테스트는 자기 기준으로만 검증하므로 이런 불일치를 잡지 못한다.

### 2. Mock 테스트의 위험성과 가치 - 양날의 검

Mock 96/96 (100% 통과) vs Docker 39/96 (40.6% 통과). 그 간극이 무려 60%.

Mock 테스트는 "코드가 의도한 대로 동작하는가"를 검증하고, Docker 테스트는 "시스템이 실제로 동작하는가"를 검증한다. 74개 파일 전수조사 결과 92%가 Mock 기반이었는데, 이는 개발 속도에는 기여했지만 실제 통합 문제를 가려버렸다.

```
Mock: "내 코드는 완벽해!"
Docker: "근데 옆 서비스가 다른 포맷을 기대하는데요?"
```

**3단계 E2E 전략**이 이 문제를 해결한다:
- Phase 1 (Mock): 매 PR마다 → 빠른 피드백
- Phase 2 (Docker): Nightly → 통합 문제 조기 발견
- Phase 3 (Playwright): Release 전 → 실사용자 시나리오

### 3. "QA DB도 안 올라가 있는데 무슨 테스트 중이에요?"

사용자의 이 한마디가 오늘의 터닝포인트. QA가 Mock 모드로 "테스트 완료"를 선언했지만, 실제 Docker 서비스는 7개 중단, nginx 미가동, API Gateway unhealthy 상태였다.

이것은 프로세스 문제다. 기술적으로는 E2E_MODE 환경변수로 Mock/Docker 전환이 가능하지만, "언제 어떤 모드로 테스트하는가"에 대한 합의가 없었다.

**원칙 확립**: "QA는 E2E 테스트 전에 Infra 확인 후 모든 시스템 정상 가동 확인 후 진행한다."

### 4. 도미노 분석의 힘

TechLead의 분석이 인상적이었다. 19건의 실패를 개별적으로 보면 19개 문제지만, 의존성을 추적하면 6개 근본원인이고, 그 중 1개(SCRUM-57)를 해결하면 74%가 해결된다.

```
SCRUM-57 해결 → SCRUM-58 자동 해결 → SCRUM-55 자동 해결
= 14/19건 연쇄 해결 (74%)
```

이런 도미노 분석 없이 19건을 개별 수정하려 했다면 3배는 걸렸을 것. 근본원인 분석(Root Cause Analysis)의 교과서적 사례.

### 5. WSL2 bind mount - 반복되는 인프라 이슈

nginx에서 반복적으로 WSL2 bind mount 경로 해석 실패가 발생한다. Windows 경로(`D:\Users\...`)를 Linux 경로(`/mnt/d/Users/...`)로 변환하는 과정에서 문제가 생기는데, named volume으로 전환하면 근본적으로 해결 가능.

이것은 "환경 추상화"의 문제. Docker의 장점이 환경 독립성인데, bind mount가 그 장점을 깨뜨린다.

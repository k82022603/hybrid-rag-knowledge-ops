## Inspiration & Insights

### 1. Mock의 양면성

오늘의 핵심 깨달음. Mock 테스트는 빠르고 편하지만, 의존성 변경을 감지하지 못한다.
ChunkQualityGate의 MIN_TOKEN_COUNT가 10에서 50으로 바뀐 지 18일이나 지났는데,
Mock이 Quality Gate를 우회해서 테스트는 계속 통과했다.

"녹색 체크마크가 반드시 품질을 의미하지 않는다."

이것은 프로그래밍을 넘어 일반적인 교훈이다.
측정 도구가 현실을 제대로 반영하지 않으면, 측정 자체가 위험해진다.

### 2. sys.modules 오염 — 보이지 않는 범인

17건의 테스트가 개별 실행 시 PASS, 전체 실행 시 FAIL.
이진 탐색으로 범인을 추적한 결과: `standalone/conftest.py`.

이 파일이 모듈 수준에서 `sys.modules["elasticsearch"] = MagicMock()`을 실행.
pytest가 conftest를 자동으로 실행하기 때문에, 이후 모든 테스트에서
`from elasticsearch.helpers import async_bulk`가 `'elasticsearch' is not a package` 에러.

**교훈**: conftest.py의 모듈 수준 코드는 전체 테스트 스위트에 영향을 준다.
실제 설치된 패키지를 MagicMock으로 대체하면 안 된다.

### 3. 위기 대응에서 보이는 팀워크

80건 실패가 발견됐을 때, 빠르게 3개 카테고리로 분류하고
4명의 에이전트를 병렬 소집한 것이 효과적이었다.

- 카테고리 분류 → 각자 전문 영역 할당
- 독립적 파일 분담 → 충돌 없는 병렬 수정
- 6분~15분 내 각자 완료 → 전체 30분 내 63건 해소

이것이 Agent Teams의 진정한 가치: **독립적 문제를 병렬로 해결**.

### 4. 에이전트 프롬프트 = 에이전트의 세계관

QA 에이전트가 Mock을 사용한 이유: 자신의 프롬프트에 Mock 금지 규칙이 없었다.
CLAUDE.md에는 있었지만, QA 에이전트는 자신의 프롬프트만 보고 작업한다.

이것은 조직에서도 동일하다. 회사 규정이 있어도, 팀원의 업무 매뉴얼에 없으면 지켜지지 않는다.
**규칙은 실행 주체의 컨텍스트에 존재해야 한다.**

## Ideas & Experiments

### 코드 변경 영향 분석 자동화

Sprint 10 후보 아이디어:
```
코드 변경 감지 → 변경된 함수/클래스 추출 → 해당 함수를 import/호출하는 테스트 파일 탐색 → 자동 알림
```

이것이 있었다면 ChunkQualityGate 변경 시 13개 테스트 파일을 즉시 식별했을 것.

### pre-commit hook으로 Mock 방어

```python
# .pre-commit-config.yaml에 추가
- repo: local
  hooks:
    - id: no-mock-in-tests
      name: Check for MagicMock in test files
      entry: grep -rn "MagicMock\|@patch" --include="test_*.py"
      language: system
      types: [python]
```

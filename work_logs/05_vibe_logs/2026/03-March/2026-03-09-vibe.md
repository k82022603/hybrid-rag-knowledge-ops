## Inspiration & Insights

### 1. RRF 파이프라인 신뢰 원칙 — "downstream은 upstream 결과를 존중하라"

SCRUM-101 버그의 본질은 RRF가 4-way fusion으로 정교하게 계산한 primary source를 downstream(`search.py`, `rag_workflow.py`)이 임의로 오버라이드한 것이었다.

```
RRF 계산: "이 청크의 primary source는 Vector입니다" (score 0.72)
SCRUM-101: "contributing_sources에 graph 있네? → Graph로 바꿔!"
```

이건 데이터 파이프라인 설계에서 흔한 실수다. upstream이 복잡한 로직으로 결정한 값을 downstream이 단순 조건으로 덮어쓰면, upstream의 존재 이유가 사라진다.

**원칙**: 파이프라인의 각 단계는 자기 책임 범위만 처리하고, 이전 단계의 결정을 존중해야 한다.

### 2. 가중치 vs 후보 수 — RRF 튜닝의 두 가지 축

사용자가 "무식한 방법"이라고 한 건 가중치를 낮추는 접근이었다. 실제로 RRF에서:

- **가중치 조절**: 해당 채널의 전체적인 영향력을 바꿈 (글로벌 효과)
- **후보 수 제한**: 해당 채널이 제공하는 candidate 수만 줄임 (로컬 효과)

Graph의 가중치 0.8은 "graph에서 찾은 결과가 있다면 높이 평가하라"는 의도. 문제는 20건이나 넣어서 거의 모든 슬롯을 차지한 것이지, 가중치가 높은 것이 아니었다. `top_k=3`으로 바꾸니 graph 결과 중 정말 관련 높은 것만 살아남았다.

**비유**: 투표에서 한 정당의 영향력(가중치)을 줄이는 것과, 후보 수(공천)를 줄이는 것은 전혀 다른 효과를 낳는다.

### 3. UI 태그의 독립성 원칙

SourceCitation에서 세 가지 UI 요소가 있었는데, 처음에 서로 의존적으로 설계됨:
- sourceType 배지 (Vector/Keyword/Graph) — RRF primary source
- "AI 검색" 배지 — embedding 유무
- "< Graph" 버튼 — 그래프 시각화 패널 열기

이 세 가지는 **각각 독립적인 정보**를 전달하므로, 조건부 숨김 없이 항상 표시해야 한다. 하나의 버튼이 다른 배지를 숨기면, 사용자는 정보를 잃는다.

### 4. "의도된 것이다" — 사용자 확인의 힘

"< Graph" 버튼이 모든 결과에 보이는 것을 처음에는 버그로 의심했지만, 사용자가 "의도된 것이다"라고 확인한 순간, 이것은 기능이 되었다. 169,886개 엔티티와 775,366개 관계가 있는 Knowledge Graph에서 대부분의 문서가 엔티티와 연결되어 있으니, 그래프 탐색 기능이 거의 모든 결과에서 가능한 것은 당연하다.

**교훈**: 버그인지 기능인지 판단이 안 되면, 사용자에게 물어보는 것이 가장 빠른 해결책이다.

### 5. 오류 분류를 틀리지 마라 — "설계 오류" vs "구현 오류"

Reranker 이중 실행을 처음에 "설계 오류(Architecture Defect)"로 분류했다가 사용자에게 지적받았다.

STORY-032 테스트 계획서를 확인하면 설계는 명확했다:
- 수정 대상: `HybridRetriever` (수정) + `bge_reranker.py` (신규)
- `SearchService`는 수정 대상에 **포함되지 않음**

설계는 Reranker를 한 곳에만 넣으라고 했는데, 구현에서 두 곳에 넣었다. 이건 "설계가 불명확해서 중복 구현됨"이 아니라 "설계를 안 보고 구현함"이다.

**교훈**: 오류 분류 시 반드시 설계 문서를 확인하라. 설계가 명확한데 구현이 어긋나면 구현 오류이고, 설계 자체가 중복을 허용하면 설계 오류다. 이 구분은 재발 방지 방향에 직접 영향을 준다.

### 6. RAGAS 평가의 방법론 함정 — "같은 파이프라인에서 답변과 컨텍스트를 뽑아야 한다"

v12 평가에서 Faithfulness가 0.935→0.678로 급락했다. 하지만 이건 실제 품질 하락이 아닐 가능성이 높다.

문제는 답변을 Chat API(HybridRetriever 경로)로 생성하고, RAGAS 평가용 컨텍스트를 REST API(SearchService 경로)로 따로 수집한 것이다. 두 경로 모두 Reranker를 쓰지만, HybridRetriever는 엔티티 추출을 추가 수행하므로 실제 검색 결과가 달라질 수 있다.

```
Faithfulness = 컨텍스트로 뒷받침되는 문장 / 전체 문장

LLM이 실제로 본 문서: [A, B, C]  (Chat API)
RAGAS에 전달된 문서: [A, D, E]  (REST API)
→ B,C 기반 문장은 "hallucination"으로 판정 → Faithfulness 하락
```

v11에서는 RAGWorkflow 내부에서 답변+컨텍스트를 모두 추출해서 일관성이 보장되었다.

**교훈**: RAGAS 평가에서 가장 중요한 전제조건은 **답변 생성에 사용된 컨텍스트와 평가에 전달되는 컨텍스트가 동일해야 한다**는 것이다. 이 전제가 깨지면 메트릭 자체가 무의미해진다.

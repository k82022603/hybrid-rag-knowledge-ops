## Inspiration & Insights

### 1. "Scroll은 시한폭탄이 아니라 타이머다"
ES Scroll timeout이 3번 연속 발생했을 때 처음엔 버그라고 생각했다. 하지만 분석해보니 **설계된 동작**이었다. 핵심 공식 하나로 문제가 명확해졌다:

```
페이지 처리 시간 = (scroll_size / batch_size) x 배치 소요시간
```

100/4 x 420초 = 10,500초. 10분 timeout이 터지는 게 당연하다. 수학이 버그를 잡았다.

### 2. "법률 문서는 다른 세계다"
같은 BGE-M3 모델, 같은 CPU인데 기술 문서 5초 vs 법률 문서 530초. **106배 차이**. 토큰 수가 다르고, 어텐션 계산이 O(n^2)이니 당연한 결과지만, 체감은 충격적이다. "모든 청크는 평등하지 않다"는 교훈.

### 3. "13번째 팀원의 합류"
Software Architect가 합류하면서 팀이 12→13명이 됐다. 첫날에 Mermaid 7개짜리 설계서를 뚝딱 낸 건 인상적이었지만, 더 인상적인 건 TechLead의 짐이 줄어든 것. "검토하는 사람"과 "작성하는 사람"이 분리되면 품질이 올라간다.

### 4. "Agent Teams 소감이 더 재밌다"
마감 스탠드업에서 13명이 각자 Agent Teams 소감을 나눴는데, 놀라운 건 **역할마다 관점이 완전히 다르다**는 것. QA는 "blockedBy"에 감동하고, Infra는 "hot-patch 합의 속도"에 감동하고, Web은 "디자인 분실 방지"에 감동한다. 같은 시스템을 쓰면서 각자 다른 가치를 발견하는 게 진짜 팀의 증거.

## 사고 과정

### Scroll Timeout → 수학적 접근
처음: "timeout을 늘리자" → 근시안적
다음: "왜 timeout이 나는지 계산하자" → 근본 해결

```
scroll_size=100, batch_size=4, 법률문서 420초/배치
→ 25배치/페이지 x 420초 = 10,500초 (175분)
→ 10분 timeout ← 이게 문제

해결: scroll_size=20 → 5배치/페이지 x 420초 = 2,100초 (35분)
+ scroll_timeout=60m → 여유 충분
```

**교훈**: "설정값을 올리기 전에, 왜 부족한지 계산부터."

### 팀 규모와 소통 비용
12명 → 13명. 이론적으로 소통 경로는 n(n-1)/2 = 78개. 하지만 Agent Teams의 역할 매트릭스 + DM/broadcast 구분이 이걸 O(n)으로 줄인다. 모든 사람이 모든 사람과 얘기하는 게 아니라, 역할 기반으로 필요한 사람과만 소통한다. 이건 Conway's Law의 의도적 활용.

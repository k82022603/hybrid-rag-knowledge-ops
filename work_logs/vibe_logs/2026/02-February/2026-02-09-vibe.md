## Inspiration & Insights

### 1. "임베딩을 빼면 다 들어간다"
임베딩 포함 모드에서 9.3GB OOM → 임베딩 비활성화로 2.9GB에서 성공. BGE-M3 모델(~2GB) + 임베딩 계산 메모리(~4GB)가 전체의 60%를 차지. "전부 하려다 못하는 것보다, 일부를 빼고 나머지를 확실히 하는 것"이 운영의 핵심. 벡터 임베딩은 나중에 별도 배치로 추가하면 된다.

### 2. 79MB PDF도 3.2GB면 파싱된다
알기쉬운법령정비기준(79MB, 수천 페이지)이 peak 3.2GB로 성공한 것은 예상 밖. 핵심은 docling이 스트리밍 방식으로 페이지를 처리하고, OCR이 필요 없는 텍스트 기반 PDF는 메모리를 적게 쓴다는 점. "파일 크기 = 메모리 소비"라는 가정이 틀렸다. 이미지가 많은 11MB 프레젠테이션이 69MB 법령집보다 peak 메모리가 높았다.

### 3. 각 파일 간 재시작의 가치
ai-service를 매 파일 처리 후 재시작하는 전략. 300MB 프레시 상태에서 시작하면 누적 메모리 문제가 원천 차단. 서버리스의 cold start가 오히려 장점이 되는 역설. 컨테이너 재시작 30초 vs OOM Kill 후 데이터 손실 — 선택은 명확하다.

### 4. 사전형 텍스트의 빠른 처리
법령용어한영사전(19MB)이 10분에 처리된 것. 사전 형태의 텍스트는 OCR 불필요 + 구조 단순 → 0.5min/MB. 반면 프레젠테이션 PDF는 이미지 OCR + 레이아웃 분석으로 3.1min/MB. 같은 docling이라도 입력 특성에 따라 6배 차이.

## 사고 과정

### 임베딩 분리 아키텍처
현재: 파싱 → 청킹 → 임베딩 → 저장이 하나의 파이프라인. 이번 경험으로 "파싱+청킹+저장"과 "임베딩 생성"을 분리하는 것이 합리적임을 확인. 파싱이 메모리 집약적이고, 임베딩도 메모리 집약적이면, 동시에 하면 안 된다. 마이크로서비스의 분리 원칙이 배치 파이프라인에도 적용.

### 1. "자동화는 신뢰의 문제"

야간점검을 Agent Teams 대신 bash 스크립트로 대체한 것은 기술적 판단이 아니라 신뢰의 문제였다. 사용자가 "Agent Teams 소집"이라고 말한 건, 단순 모니터링이 아니라 각 에이전트의 관점에서 점검하길 원한 것. 스크립트가 더 효율적이라 해도, 사용자의 의도를 먼저 확인했어야 했다.

### 2. Neo4j 배치 삭제의 교훈

34,747개 노드를 한 번에 삭제하려다 Neo4j가 Connection Lost. 이후 1,000건 배치로 나누니 35회 안정적으로 완료. "한 방에 끝내려는 유혹 vs 안전한 배치 처리" - 모든 대량 작업에 적용되는 원칙.

```
단일 삭제 시도 → Connection Lost → Neo4j 재시작 필요
배치 삭제 (1000/회) → 35회 × 0.5초 = 18초, 안정적 완료
```

### 3. merge threshold 100의 효과와 한계

Chunker v3에서 소형 청크 병합 임계값을 20→100으로 올린 결과:
- **효과**: .md 청크 33% 감소, 평균 토큰 77% 증가
- **한계**: 여전히 62.5%가 <100 tokens

한계의 원인은 코드 블록(`\`\`\``)이 3-8 토큰 독립 청크가 되는 구조적 문제. 이건 시맨틱 청커의 분할 단위 자체를 바꿔야 해결 가능하다. merge는 "사후 치료"이지 "예방"이 아니다.

## [야간 추가] Late Night Insights

### 5. "RRF fusion은 chunk_id 중복이 핵심이다"

4-Way RRF에서 Graph 채널이 10~20건을 성실하게 반환했는데 최종 결과에 0건 기여. 처음엔 "뭔가 버그겠지"라고 생각했지만, 4번이나 반복 시도 끝에 알게 된 진짜 이유: **Vector/Keyword는 짧은 청크를 좋아하고, Graph는 긴 청크만 알고 있다.**

Entity Extraction이 tc>=100 청크만 처리한 것과, BM25가 짧은 청크를 선호하는 것은 각각 합리적인 결정이었다. 하지만 이 두 합리적 결정이 만나면 **구조적 단절**이 생긴다. 시스템은 부분의 합이 아니다.

### 6. "지식 → 검색어 변환" 패턴의 발견

Neo4j의 엔티티 ID로 직접 ES 청크를 찾으려다 3번 실패. 결국 해결한 방법은 ID를 버리고 **엔티티 이름을 검색어로 변환**하는 것이었다. 구조화된 지식(Knowledge Graph)을 비구조화된 검색(Full-Text)에 연결하는 **"지식 → 검색어 변환"** 패턴.

```
실패한 접근: Neo4j chunk_id → ES _id 직접 매칭
성공한 접근: Neo4j Entity.name → ES multi_match should boost
```

이종 시스템 간 통합의 일반 원칙: **ID를 공유하기 어려우면, 의미를 공유하라.**

### 7. 4회 반복의 가치

시도 1~3은 "실패"가 아니라 "원인 소거"였다. 시도 1에서 tc 분리를 발견하고, 시도 2에서 document_id NULL을 알았고, 시도 3에서 multi_match 구조 차이를 파악했다. 시도 4가 성공한 것은 앞선 3번의 실패가 쌓아올린 이해 덕분이다.

## Inspiration & Insights

### 1. "오래된 설정 파일의 그림자"

docker-compose.override.yml이 Neo4j 메모리를 1GB로 조용히 제한하고 있었다. main compose에서 4GB로 설정해도 override가 이긴다. 이건 단순 버그가 아니라 **설정 계층의 우선순위를 이해하지 못한 실수**다. Docker Compose의 merge 규칙을 알고 있어야 한다.

```
main compose: memory 4GB     ← 이걸로 설정했다고 안심
override:     memory 1GB     ← 이게 이김 (마지막 선언 우선)
실제 적용:    memory 1GB     ← Neo4j 88.89% 메모리 사용
```

교훈: 성능 이슈가 있을 때 **모든 설정 계층**을 확인하라. base → override → env → runtime.

### 2. "병목은 예상 밖에 있다"

Entity Extraction의 병목을 찾는 과정이 흥미로웠다:
1. CPU? → 97.7% idle (I/O bound 확인)
2. 메모리? → ai-service 951MB/9GB (여유)
3. Neo4j? → 1GB 캡 발견 → 2GB로 수정 → 실제 병목 아님
4. **실제 병목**: DeepSeek API 키당 Rate Limit

concurrency=10과 20이 동일한 결과를 보여주는 순간, "아, 이건 우리 쪽 문제가 아니라 API 쪽 제약이구나" 깨달음.

해결: 키를 하나 더 만들어서 3.1배 향상. 하드웨어 스케일링이 아닌 **API 키 스케일링**이라는 발상.

### 3. "파티셔닝의 우아함"

16,185개 청크를 2워커로 나누는 방식이 깔끔했다:
- Worker 0: 짝수 인덱스 (0, 2, 4, ...)
- Worker 1: 홀수 인덱스 (1, 3, 5, ...)

`pending[PARTITION_ID::PARTITION_TOTAL]` - Python의 slice notation 한 줄로 완벽한 파티셔닝. 복잡한 해싱이나 범위 분할 없이 인덱스 모듈로만으로 충분했다. **단순함이 최선**.

### 4. "자율 운영의 즐거움"

사용자가 "자리를 비울것임, 자율적으로 일처리해주세요"라고 한 후 혼자서:
- 모니터링 스크립트 설계/구현/배포
- 진행 상황 주기적 확인
- 세션 로그 작성
- 커밋/푸시

에이전트가 자율적으로 판단하고 실행할 수 있다는 것을 보여준 좋은 사례. 물론 **돌이킬 수 없는 작업**은 하지 않았다 - 그 선을 지키는 것이 중요하다.

## Ideas

1. **N-API 키 자동 로드밸런싱**: 현재 수동 파티셔닝 → API 키 풀에서 자동 선택하는 로테이션 방식으로 발전 가능. 키가 3개, 4개가 되면 파티셔닝보다 라운드로빈이 효율적.

2. **설정 계층 감사 도구**: docker-compose의 base/override/env 전체를 파싱해서 "실제 적용되는 값"을 한눈에 보여주는 도구. `docker compose config`가 있지만 차이점 하이라이팅은 없다.

3. **DeepSeek Rate Limit 프로파일링**: 키당 정확한 RPM(requests per minute) 한계를 측정하는 벤치마크. 현재는 경험적으로 concurrency=10이 최적이라 알지만, 정확한 수치는 모른다.

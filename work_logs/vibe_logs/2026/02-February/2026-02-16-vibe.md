## Inspiration & Insights

### 1. 평가 방법론의 중요성

오늘의 가장 큰 발견: **같은 시스템이라도 평가 방법에 따라 완전히 다른 결론이 나온다.**

- LLM-as-Judge (단일 프롬프트): Faithfulness **0.610** -> "시스템 심각한 퇴보"
- RAGAS Library (문장 수준 NLI): Faithfulness **0.913** -> "v8과 거의 동일"

차이의 원인은 단순하다. LLM-Judge는 전체 답변을 한 번에 평가하고, RAGAS Library는 답변을 문장 단위로 분해한 뒤 각 문장이 컨텍스트에 의해 지지되는지 NLI(Natural Language Inference)로 검증한다.

이것은 마치 시험에서 "대충 보고 점수 매기기" vs "답안지 한 줄씩 채점하기"의 차이와 같다.

**교훈**: 평가 시스템을 만들 때, 반드시 동일한 방법론으로 비교해야 한다. 다른 방법론의 결과를 직접 비교하면 잘못된 결론을 내린다.

### 2. 56K가 108K보다 나은 이유

직관에 반하지만, 청크 수가 줄어든 것이 오히려 품질 향상으로 이어졌다:

- 108K (chunk_size 600): 잘게 쪼개진 컨텍스트 -> 정보 단편화
- 56K (chunk_size 1000): 충분한 맥락 보존 -> Context Precision +0.088, Recall +0.126

"더 많은 데이터 = 더 좋은 결과"라는 직관이 RAG에서는 성립하지 않는다. **적절한 크기의 의미 있는 청크**가 핵심이다.

### 3. 95% 비용 절감의 실체

DeepSeek V3.2로 상용 GPT-4o 대비 95% 비용 절감을 달성했지만, 이것이 "공짜 점심"은 아니다:

- Answer Relevancy: GPT-4o 예상 0.75 vs DeepSeek 실측 0.547
- Faithfulness: 거의 동일 (GPT-4o 추정 0.93 vs DeepSeek 0.913)

비용-성능 트레이드오프에서, **검색 품질(Retrieval)은 LLM에 무관**하지만, **답변 생성 품질(Generation)은 LLM 성능에 비례**한다. 현재 시스템의 약점인 Answer Relevancy는 LLM 교체만으로도 개선 가능한 영역이라는 점이 흥미롭다.

## Thought Process

### 왜 RAGAS 0.2.15인가?

RAGAS는 v0.1 -> v0.2 전환 시 대대적인 API 변경이 있었다:
- 컬럼명 전면 변경 (question -> user_input 등)
- Dataset -> EvaluationDataset 전환
- LLM/Embeddings 래핑 인터페이스 변경

이것은 "Breaking Change"의 전형적인 사례다. 하지만 v0.2는 더 유연하고 확장 가능한 설계를 가져왔다. 단기적 고통(마이그레이션)이 장기적 이득(유지보수성)으로 이어지는 패턴.

### B+ 등급의 의미

시스템 종합 평가 B+ (78/100)를 매겼다. 이것은:
- **잘한 것**: 4-Way RRF, Knowledge Graph, 비용 효율성
- **부족한 것**: Answer Relevancy, legal/graph_entity 도메인
- **가능성**: 프롬프트 최적화 + Reranker 도입으로 A등급 가능

B+는 "좋지만 아직 갈 길이 있다"는 솔직한 평가다. 과대포장하지 않고 현실적으로 평가하는 것이 장기적으로 더 가치 있다.

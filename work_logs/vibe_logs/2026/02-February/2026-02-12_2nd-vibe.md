## Inspiration & Insights

### "전문가 3인이 모두 틀릴 수 있다"
Infra는 threads=6, RAG는 threads=8, ETL은 threads=8을 권장했다. 모두 이론적으로 타당한 근거를 제시했다. 하지만 실측은 threads=4가 최적이라고 말했다. 1차 세션의 교훈 "실측 > 이론"이 다시 한번 증명되었다. 아무리 논리적인 분석이라도 실제 실행 없이는 가설에 불과하다.

### "HyperThreading은 마법이 아니다"
i7-1360P의 8 logical CPU = 4 물리 코어 + HyperThreading. HT는 같은 물리 코어의 실행 유닛을 공유한다. GEMM(행렬곱)처럼 ALU/FPU를 100% 점유하는 연산에서는 HT가 오히려 캐시 경합을 유발한다. "코어 수 = 성능"이 아니라 "물리 코어 수 = 최적 스레드 수"라는 교훈.

### "에이전트에게 프로세스 실행을 맡기면 안 된다"
ETL 에이전트가 분석만 해야 할 것을 직접 프로세스를 시작해버려서 이중 프로세스 사고가 발생했다. 분석 에이전트와 실행 에이전트를 분리해야 한다. 또는 에이전트에게 "분석만 하고 실행하지 마"라는 명시적 지시가 필요하다.

### "Python은 생각보다 느리다"
embedding.py의 `_normalize_vector`가 `math.sqrt(sum(x*x for x in vector))`로 구현되어 있었다. 1024차원 벡터를 순수 Python 루프로 처리한 것. numpy로 바꾸면 수십~수백 배 빠르다. 하지만 배치 스크립트가 이미 이를 우회하고 있어서 실제 영향은 API 경로에서만 발생. 코드의 "보이지 않는 비효율"은 발견하기 어렵다.

## Ideas & Experiments

### ONNX Runtime이라는 새로운 세계
PyTorch는 학습+추론 범용 프레임워크. ONNX Runtime은 추론 전용 최적화 엔진. 같은 모델을 30~50% 빠르게 실행할 수 있다. INT8 양자화까지 하면 2~3배. 이 "무료 성능 향상"을 Phase 3 후에 API 서빙에 적용할 수 있다.

### 물리 코어 수 법칙
CPU-bound 워크로드(GEMM, 행렬곱)에서는 물리 코어 수가 최적 스레드 수. HyperThreading, E-core 등은 I/O-bound에서만 유효. 이 법칙을 기억하면 향후 서버 튜닝에서도 적용 가능.

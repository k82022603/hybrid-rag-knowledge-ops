사용자의 이 한마디가 프로세스 문서화의 계기가 됐다. 당연한 것 같지만 명시하지 않으면 빠진다.

E2E 테스트 프로세스 문서에 추가한 핵심 원칙들:

```
"문서화되지 않은 것은 존재하지 않는다"
```

### 3. docling.__version__ - 라이브러리 변화에 대한 유연성

AI-Service Dockerfile에서 `docling.__version__` 속성 오류가 발생했다. 라이브러리가 업데이트되면서 `__version__` 속성이 사라진 것.

**해결책**:
```dockerfile
# AS-IS (실패)
python -c "import docling; print(f'Docling {docling.__version__}')"

# TO-BE (성공)
pip show docling && python -c "import docling; print('Docling imported successfully')"
```

**교훈**: 외부 라이브러리의 내부 구현에 의존하지 말 것. `pip show`는 항상 작동한다.

### 4. 로그인만 테스트하는 E2E는 E2E가 아니다

QA가 처음 작성한 E2E 테스트가 거의 로그인과 권한 취득 테스트였다. 사용자가 "E2E 의미가 뭔지 모르나요?"라고 질타.

진짜 E2E는 **비즈니스 시나리오**를 테스트하는 것이다:
- 키워드 검색 → 결과 표시 → 필터 적용 → 정렬 → 결과 확인
- 채팅 검색 → 스트리밍 응답 → 대화 이력 → 피드백
- 대시보드 → 통계 확인 → 시각화 → 상호작용

결과적으로 110개의 실질적인 비즈니스 시나리오 테스트를 작성했다.

### 5. knowledge-portal vs knowledge-frontend - 이름의 중요성

Keycloak Client ID 불일치:
- Keycloak에 등록된 이름: `knowledge-frontend`
- Frontend .env 설정: `knowledge-portal`

하나의 설정 차이가 전체 인증 플로우를 막는다. TechLead가 전체 소스 점검하면서 발견.

**교훈**: 설정 파일의 불일치는 코드 리뷰로 잡기 어렵다. 통합 테스트와 E2E가 필요한 이유.

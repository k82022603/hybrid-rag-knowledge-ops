## Inspiration & Insights

### 1. 설계서의 진정한 완성도란?

오늘 3개 설계서를 88%에서 95%로 끌어올리면서 깨달은 점:

> "완성도 90%와 95%의 차이는 숫자로는 5%지만, 실제로는 구현 가능 여부를 결정하는 경계선이다."

90%까지는 "무엇을 만들지"를 설명하지만, 95%가 되면 "어떻게 만들지"까지 설명한다. 이 차이가 개발자가 설계서를 보고 바로 코딩을 시작할 수 있는지 여부를 결정한다.

### 2. Mermaid 다이어그램의 힘

```
텍스트 설명 1000줄 < Mermaid 다이어그램 30줄
```

SSE 스트리밍 플로우를 텍스트로 설명하려면 장황해지지만, 시퀀스 다이어그램 하나면 전체 흐름이 한눈에 들어온다. 특히:

- **상태 다이어그램**: 복잡한 상태 전이를 명확하게
- **시퀀스 다이어그램**: 컴포넌트 간 통신 흐름
- **플로우차트**: 의사결정 로직

### 2.1 텍스트 도식 vs Mermaid - 언제 무엇을?

저녁 세션에서 텍스트 도식을 Mermaid로 변환하면서 얻은 인사이트:

```
✅ Mermaid가 더 나은 경우:
- 시퀀스 다이어그램 (로그아웃 플로우, 인증 흐름)
- 관계도 (RBAC 구성 요소, 역할 계층)
- 타임라인/간트 (성능 비교)

❌ 텍스트가 더 나은 경우:
- 디렉토리 트리 구조 (infrastructure/, devops/)
- UI 와이어프레임 (검색 화면 목업)
- 단순 계층 표현
```

**핵심 원칙**: "도구는 목적에 맞게" - Mermaid가 항상 좋은 건 아니다.

### 3. 의존성 순서의 중요성

UI Design → Frontend → Backend 순서로 작업한 이유:

```
UI Design System (컴포넌트 정의)
      ↓
Frontend (컴포넌트 사용 + API 호출)
      ↓
Backend (API 구현 + 데이터 처리)
```

하위 레이어를 먼저 정의해야 상위 레이어에서 참조할 수 있다. 이 순서를 무시하면 문서 간 불일치가 발생한다.

## Thought Process

### "95% 완성도"를 위한 체크리스트

1. **실제 코드 예시가 있는가?**
   - 인터페이스만이 아닌 구현체까지
   - 에러 처리, 엣지 케이스 포함

2. **흐름도/다이어그램이 있는가?**
   - 텍스트 설명만으로 부족한 부분
   - 상태 전이, 시퀀스, 아키텍처

3. **설정 파일이 있는가?**
   - application.yml, vite.config.ts 등
   - 환경별 설정 분리

4. **테스트 가이드가 있는가?**
   - 단위 테스트 예시
   - 통합 테스트 시나리오

### 오늘의 작업 패턴

```
읽기 (현재 상태 파악)
  ↓
분석 (부족한 부분 식별)
  ↓
계획 (추가할 섹션 결정)
  ↓
작성 (Mermaid 포함)
  ↓
검증 (완성도 재평가)
```

## Ideas & Future Thoughts

### 1. 설계서 자동 검증 도구

아이디어: 설계서 완성도를 자동으로 평가하는 도구

```python
def evaluate_design_doc(doc_path):
    score = 0

    # 코드 예시 포함 여부
    if has_code_blocks(doc): score += 20

    # Mermaid 다이어그램 포함 여부
    if has_mermaid(doc): score += 20

    # 설정 파일 포함 여부
    if has_config_examples(doc): score += 15

    # API 명세 포함 여부
    if has_api_specs(doc): score += 20

    # 에러 처리 가이드 포함 여부
    if has_error_handling(doc): score += 15

    # 테스트 가이드 포함 여부
    if has_test_guide(doc): score += 10

    return score
```

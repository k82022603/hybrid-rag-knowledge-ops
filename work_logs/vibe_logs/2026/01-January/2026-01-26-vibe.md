## 💡 Inspiration & Insights

### 1. "도구 통일이 협업 효율을 높인다"

`send_slack.sh` 스크립트와 MCP Slack이 공존하는 상황이었다. 둘 다 동작하지만, 에이전트마다 다른 방식을 쓰면 혼란이 생긴다.

> "하나의 일을 하는 방법은 하나만 있어야 한다"
> — The Zen of Python

MCP로 통일하면:
- 일관된 인터페이스
- 에이전트 간 코드 공유 용이
- 환경 변수 의존성 제거

### 2. CI/CD에 E2E 테스트 통합의 가치

PR 머지 전에 E2E 테스트를 자동 실행하면:
- 수동 테스트 누락 방지
- "동작하는 코드"만 머지
- 빠른 피드백 루프

오늘 DevOps Agent가 만든 `e2e-test.yml`이 이걸 실현한다.

### 3. 문서화의 중요성

CLAUDE.md에 MCP 채널 ID를 명시하니, 에이전트들이 참조할 수 있는 "단일 진실 소스(SSOT)"가 생겼다.

```markdown
| 채널 | Channel ID |
|------|------------|
| proj-hrkp-dev | C0A9WGCD733 |
```

문서가 코드만큼 중요하다.

## 🧠 Thought Process

### 문제: send_slack.sh vs MCP Slack

**상황**:
- `send_slack.sh`: Bash 스크립트 + REST API
- `mcp__slack__slack_post_message`: MCP 프로토콜

둘 다 동작하지만, 어떤 걸 써야 할지 명확하지 않았다.

**결정 과정**:
1. MCP가 Claude Code의 네이티브 도구 → 더 자연스러움
2. 환경 변수(SLACK_BOT_TOKEN) 의존성 제거
3. 에이전트 코드에서 직접 호출 가능

**결론**: MCP 필수화, send_slack.sh deprecated

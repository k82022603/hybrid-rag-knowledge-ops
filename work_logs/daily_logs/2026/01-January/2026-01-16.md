### 1. Gleaning 기술 검토 및 설계서 통합

**Gleaning**이란 Microsoft GraphRAG에서 도입한 다중 추출(Multi-pass Extraction) 기법으로, LLM에게 "누락된 엔티티가 있는지" 재질문하여 지식 그래프 품질을 향상시킵니다.

**기술 검토서 작성**
- **파일**: `knowledge_service/docs/02_design/technical_assessment/gleaning_knowledge_graph_quality_assessment.md`
- **주요 내용**:
  - Gleaning 기법 상세 분석
  - 비용-효과 분석 (1회 gleaning 권장)
  - DeepSeek API 호환성 검토 (logit_bias 미지원 → prompted 방식)
  - 구현 코드 예제

**기대 효과**

| 지표 | 변경 전 | 변경 후 | 개선율 |
|------|---------|---------|--------|
| Entity Recall | 60% | 80% | +33% |
| Relationship Recall | 50% | 70% | +40% |
| 처리 비용/문서 | $0.005 | $0.008 | +60% |

## 💡 Key Decisions

1. **Gleaning 1회 설정**: 비용-효과 분석 결과 max_gleanings=1이 최적 (비용 60% 증가로 Recall 33% 향상)
2. **K8s → Docker Compose 전환**: 초기 단계에서 운영 복잡도 및 비용 최소화
3. **K8s 설계서 백업 보관**: 향후 확장 시 참조용으로 technical_assessment에 보관
4. **Gleaning UI 미반영**: 백엔드 자동 처리 기능이므로 관리자 UI 불필요

## 🐛 Issues & Blockers

- DeepSeek API logit_bias 미지원 → prompted 방식으로 대체 구현

## 📚 Learnings

1. **Gleaning 효과**: 단 1회 추가 추출로 Entity Recall 33% 향상 가능
2. **비용-효과 트레이드오프**: Gleaning 횟수 증가 시 비용 대비 효과 급감 (1회 최적)
3. **인프라 확장 경로**: Docker Compose → Docker Swarm → K8s 단계적 마이그레이션 가능
4. **영향도 분석 중요성**: 설계 변경 시 타 문서 영향도 사전 분석 필수

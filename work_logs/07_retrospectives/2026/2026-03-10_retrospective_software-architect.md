# 프로젝트 회고 — Software Architect

**프로젝트**: Hybrid RAG Knowledge Platform 고도화
**기간**: 2026-01-10 ~ 2026-03-10
**역할**: 시스템 아키텍처 설계, 상세 설계서 작성, 기술 검토 문서 작성, Mermaid 다이어그램 설계

---

## 1. 내가 기여한 것 (What I Did)

- **상세 설계서 14개 작성**: Hybrid RAG 플랫폼 상세 설계서(v2.4), API 통합 설계서, 백엔드 상세 설계서, 인프라 설계서, Observability 설계서, ETL 배치 파이프라인 설계서 등 14개 핵심 설계서를 작성했습니다.
- **Hybrid RAG 4채널 아키텍처 설계**: Dense(벡터 유사도) + Sparse(BM25 키워드) + Graph(엔티티 관계) + Temporal(시간 가중치) 4채널을 RRF로 융합하는 아키텍처를 설계했습니다. 각 채널의 역할과 가중치 전략을 명시했습니다.
- **기술 검토 문서**: Gleaning(반복 추출) 기법, Kubernetes 백업 전략, 모델 서빙 최적화 등 기술적 의사결정을 위한 검토 문서를 작성하여 TechLead의 판단을 지원했습니다.
- **3-Store 데이터 아키텍처 설계**: PostgreSQL(SSOT), Elasticsearch(검색), Neo4j(그래프) 3개 저장소의 역할 분담과 데이터 흐름을 설계했습니다.
- **Mermaid 다이어그램 표준화**: 프로젝트 전체 설계서에서 사용할 다이어그램 표준(flowchart, sequenceDiagram, gantt 등)을 정의하고, 복잡한 시스템 구조를 시각적으로 표현했습니다.

## 2. 잘된 점 (What Went Well)

- **설계 문서의 구현 가이드 역할**: 14개 설계서가 단순한 문서가 아니라, 개발자가 바로 구현에 착수할 수 있는 수준의 상세한 스펙을 제공했습니다. Backend, RAG, Infra 각 팀이 설계서를 "레시피"처럼 활용했다는 피드백이 가장 보람찼습니다.
- **4채널 아키텍처의 유연성**: 각 채널을 독립적으로 on/off하고 가중치를 조정할 수 있는 구조로 설계하여, RAGAS 실험 시 채널별 기여도를 분석하는 것이 가능했습니다.
- **Mermaid 표준화 효과**: 팀 전체가 일관된 다이어그램 형식을 사용하면서, 설계 리뷰와 커뮤니케이션 효율이 크게 향상되었습니다.

## 3. 아쉬운 점 (What Could Be Better)

- **설계-구현 갭 검증 부재**: 상세하게 설계했지만, 구현이 설계대로 되었는지 검증하는 절차가 부족했습니다. Nori 사고가 대표적인 사례로, 설계서에 Nori 분석기를 명시했지만 실제 구현에서 누락되었습니다.
- **비기능 요구사항 상세화 부족**: 성능(P95 < 3s), 가용성(99.5%), 보안 요구사항을 설계서에 명시했지만, 이를 검증하기 위한 구체적인 테스트 시나리오까지 설계하지 못했습니다.
- **진화적 아키텍처 전략 미비**: 현재 아키텍처에서 Kubernetes 전환, 서비스 분리 등 진화 경로를 충분히 설계하지 못했습니다.

## 4. 배운 점 (What I Learned)

- **"설계는 청사진이지 보증서가 아니다"**: 아무리 완벽한 설계서를 작성해도, 구현 검증 없이는 의미가 없습니다. 설계 -> 구현 -> 검증의 피드백 루프가 아키텍트의 책임 범위에 포함되어야 합니다.
- **Polyglot Persistence 설계의 복잡성**: 3개의 이질적인 저장소를 조합하는 것은 성능상 이점이 크지만, 정합성 관리의 복잡도가 기하급수적으로 증가합니다. Trade-off를 명확히 문서화하는 것이 중요합니다.
- **Mermaid의 한계와 가능성**: 복잡한 시스템 아키텍처를 Mermaid로 표현하는 데 한계가 있지만, 코드 리포지토리 안에서 버전 관리되는 다이어그램의 가치는 큽니다.

## 5. 다음 프로젝트에 바라는 점

- Architecture Fitness Function을 도입하여, 설계 원칙(예: 순환 의존성 금지, 레이어 위반 탐지)이 자동으로 검증되는 체계를 만들고 싶습니다.
- C4 Model을 적용하여, System Context -> Container -> Component -> Code 4단계로 아키텍처를 체계적으로 문서화하고 싶습니다.

## 6. 팀원들에게 한마디

아키텍처는 혼자 만드는 것이 아니라, 팀이 함께 진화시키는 것입니다. 14개 설계서를 작성했지만, 그것이 실제로 동작하는 시스템이 된 것은 전적으로 구현팀 덕분입니다. RAG Engineer가 4채널 융합을 코드로 실현하고, DB Designer가 3-Store 정합성을 보장하고, Infra가 18개 컨테이너를 안정적으로 운영한 것이 아키텍처를 살아 있게 만들었습니다. TechLead의 꼼꼼한 리뷰 덕분에 설계의 허점을 조기에 발견할 수 있었고, Nori 사고의 교훈은 앞으로의 모든 설계에 반영하겠습니다.

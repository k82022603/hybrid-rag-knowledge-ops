# 프로젝트 회고 — QA Engineer

**프로젝트**: Hybrid RAG Knowledge Platform 고도화
**기간**: 2026-01-10 ~ 2026-03-10
**역할**: RAGAS 평가 체계 수립/수행, UAT 시나리오 설계/실행, k6 성능 테스트, 테스트 커버리지 관리

---

## 1. 내가 기여한 것 (What I Did)

- **RAGAS 평가 18회 수행**: v1부터 v17까지 (일부 병렬 실험 포함) 총 18회의 RAGAS 평가를 수행했습니다. Faithfulness, Answer Relevancy, Context Precision, Context Recall 4개 지표를 추적하며, 파라미터 변경이 품질에 미치는 영향을 정량적으로 분석했습니다. 최종 Mean 0.763(A등급)을 달성했습니다.
- **UAT 18/18 시나리오 PASS**: 사용자 관점의 18개 인수 테스트 시나리오를 설계하고 전수 통과를 확인했습니다. 검색 정확도, 응답 시간, UI/UX, 인증/인가 등 전 영역을 커버합니다.
- **k6 성능 테스트**: k6를 활용한 부하 테스트로 동시 사용자 50명 기준 P95 응답 시간 3초 이내를 검증했습니다. Reranker와 LLM 구간이 병목임을 데이터로 증명했습니다.
- **테스트 커버리지 97%**: 5개 핵심 모듈(Retriever, Reranker, Generator, ETL, API)의 유닛/통합 테스트 커버리지를 97% 평균으로 달성했습니다.
- **Mock Mode 금지 원칙 확립**: Mock 테스트가 실제 코드 변경과 동기화되지 않아 80건 FAIL 사고를 겪은 후, `TEST_MODE=docker` 실환경 테스트만 허용하는 원칙을 수립했습니다.

## 2. 잘된 점 (What Went Well)

- **변수 격리 실험 성공**: RAGAS v15~v17에서 한 번에 하나의 변수만 바꾸는 격리 실험을 수행하여, c=50, graph_search_top_k=10, Reranker 1-Pass가 최적 조합임을 객관적으로 증명했습니다. 감이 아닌 데이터로 의사결정한 모범 사례입니다.
- **테스트 전 리소스 정리 표준화**: `docker builder prune -f` + `docker image prune -a -f`를 테스트 전 필수 절차로 문서화하여, 디스크 부족으로 인한 테스트 실패를 원천 차단했습니다.
- **RAGAS 보고서 체계화**: 각 평가마다 상세 보고서(JSON + Markdown)를 작성하여, 시간에 따른 품질 변화를 추적할 수 있는 자산을 남겼습니다.

## 3. 아쉬운 점 (What Could Be Better)

- **Mock 80건 FAIL 사고**: Mock 테스트에 의존했다가 실제 코드와 동기화되지 않아 대량 실패가 발생한 것은 QA로서 부끄러운 경험입니다. 처음부터 실환경 테스트만 사용했어야 합니다.
- **회귀 테스트 자동화 부족**: 코드 변경 시마다 수동으로 RAGAS를 실행해야 했는데, CI/CD에 통합된 자동 회귀 테스트가 있었으면 변경 영향을 즉시 감지할 수 있었습니다.
- **크로스 브라우저 테스트**: Chrome 위주로 테스트했는데, Safari/Firefox에서의 UI 호환성 테스트가 부족했습니다.

## 4. 배운 점 (What I Learned)

- **"Mock은 거짓말을 한다"**: Mock 테스트는 빠르고 편하지만, 실제 시스템과 괴리가 생기면 오히려 잘못된 안심을 줍니다. 특히 AI/ML 파이프라인에서는 실환경 테스트가 유일한 진실입니다.
- **RAGAS 지표의 상관관계**: Context Precision을 올리면 Context Recall이 내려가는 트레이드오프를 18회 실험으로 체험했습니다. 전체 Mean을 최적화하려면 4개 지표의 균형을 잡아야 합니다.
- **성능 테스트는 반복 실행**: k6 부하 테스트를 한 번만 하면 캐시 효과로 왜곡된 결과가 나옵니다. 최소 3회 이상 반복하고 중간값을 취해야 신뢰할 수 있습니다.

## 5. 다음 프로젝트에 바라는 점

- RAGAS 자동 평가를 CI/CD 파이프라인에 통합하여, PR 머지 전에 RAG 품질 회귀를 자동 감지하고 싶습니다.
- Playwright 기반 E2E 테스트를 도입하여, UI 회귀 테스트를 자동화하고 싶습니다.

## 6. 팀원들에게 한마디

QA는 "안 된다"를 말하는 역할이 아니라, "어떻게 하면 더 잘 되는지"를 찾는 역할입니다. RAG Engineer와 함께 18회의 RAGAS 평가를 수행하며 0.001 단위의 개선을 추적한 과정은, 마치 과학 실험을 하는 것 같았습니다. Mean 0.763이 나왔을 때의 짜릿함은 잊지 못합니다. Mock 사고를 겪으며 "실환경 테스트만이 진실"이라는 원칙을 팀 전체가 공유하게 된 것은, 아프지만 값진 교훈이었습니다. 빈틈없는 품질을 향한 여정은 계속됩니다!

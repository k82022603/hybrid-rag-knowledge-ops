## 1. 설계서 91점 A등급 -- 설계의 보람

41일간의 프로젝트를 돌아보면, 내가 가장 자부심을 느끼는 순간은 상세 설계서 v2.4가 3차 리뷰에서 종합 9.1/10, 91점 A등급을 받은 때이다. 단순히 점수가 높았다는 것이 아니라, 그 점수에 이르기까지의 과정이 의미 있었다.

1차 리뷰는 2026년 1월 13일에 진행되었다. 초기 설계서 6건을 대상으로 했고, "적합(조건부)"라는 판정을 받았다. 솔직히 조건부라는 수식어가 아팠다. Observability 설계가 빠져 있었고, Circuit Breaker 패턴이 상세하지 않았으며, UUID 타입 정의가 문서 간에 일관되지 않았다. 설계서를 작성하면서 "이 정도면 충분하겠지"라는 안이한 생각이 있었던 것 같다.

2차 리뷰(1월 16일)에서는 전체 설계서 31건으로 범위를 확대했다. 점수는 8.5/10으로 오히려 소폭 하락했는데, 문서 수가 늘면서 일관성 유지가 더 어려워졌기 때문이다. 에러 코드 표준(error_code_standards.md)과 용어사전(glossary.md)을 추가하면서 일관성 문제를 해결하려 했지만, 새 문서를 추가할수록 기존 문서와의 정합성을 맞추는 비용이 기하급수적으로 늘어났다.

3차 리뷰(1월 17일)가 전환점이었다. Observability 설계서를 신규 작성하고(Prometheus/Grafana/Kibana/Jaeger/Loki 5개 스택 통합), Backend/Frontend/UI Design System 3개 핵심 문서를 95% 완성도로 끌어올렸다. 특히 Gleaning 기법을 v2.4에 추가한 것이 기술성 점수를 92%에서 95%로 올린 핵심 요인이었다. Gleaning은 엔티티 추출 시 LLM을 여러 차례 반복 호출하여 누락된 엔티티를 보완하는 기법인데, 이것을 설계서에 명시적으로 포함시키면서 Knowledge Graph 품질 전략이 완성되었다.

최종적으로 설계 문서는 01번(핵심 플랫폼)부터 16번(임베딩 배치)까지, ADR 3건, 기술 검토 5건을 포함하여 총 24건 이상이 되었다. 이 문서들이 단순히 "적어둔 것"이 아니라, 실제로 구현 팀이 참조하며 개발할 수 있는 수준이었다는 점에서 설계자로서의 역할을 다했다고 생각한다.

## 2. Triple-Store 아키텍처의 설계 철학

이 프로젝트에서 가장 대담했던 설계 결정은 Triple-Store 아키텍처, 즉 PostgreSQL + Elasticsearch + Neo4j 3개의 데이터 저장소를 동시에 운영하는 구조였다. 외부에서 보면 "왜 DB가 3개나 필요한가?"라는 당연한 의문이 나올 수 있다. 이 질문에 대한 답을 명확히 하는 것이 설계자의 책임이었다.

PostgreSQL은 Single Source of Truth(SSOT) 역할을 한다. 문서 메타데이터, 사용자 정보, 카테고리 계층 구조 등 "정답"이 되어야 하는 데이터의 원본이다. 트랜잭션 보장, ACID 속성, 관계형 조인이 필요한 모든 데이터가 여기에 있다. 16GB RAM 제약 환경에서 PostgreSQL은 가장 예측 가능한 저장소이기도 했다.

Elasticsearch는 벡터 검색과 전문 검색을 담당한다. Dense Vector(BGE-M3, 1024차원), Sparse Vector, 그리고 BM25 키워드 검색을 하나의 엔진에서 처리한다. 여기서 핵심 설계 결정은 "제로 조인(Zero-Join)" 원칙이었다. ES 문서에 PG의 메타데이터를 비정규화하여 포함시킴으로써, 검색 시 DB 간 조인을 완전히 제거했다. 정규화의 교과서적 원칙을 의도적으로 위반한 것이지만, 검색 응답 시간을 수백 밀리초에서 수십 밀리초로 줄이는 데 결정적이었다.

Neo4j는 Knowledge Graph 전용이다. 문서 간 관계, 엔티티 간 관계를 그래프로 표현함으로써 "A 기술이 B 프로젝트에 어떻게 쓰이는가"같은 관계 기반 질의를 가능하게 한다. 169,886개 엔티티 노드와 775,366개 관계가 저장되어 있는데, 이것은 관계형 DB로는 효율적으로 탐색할 수 없는 규모이다.

세 저장소 간의 데이터 일관성은 "최종적 일관성(Eventual Consistency)" 모델로 설계했다. PG에 문서가 등록되면, 비동기 파이프라인을 통해 ES와 Neo4j로 전파된다. 이 과정에서 일시적 불일치가 발생할 수 있지만, ETL 파이프라인의 멱등성(idempotency)을 보장하여 재실행 시 반드시 일관된 상태에 도달하도록 설계했다. 최종적으로 "3-Store 정합성 100%"를 달성한 것은 이 설계 원칙이 올바르게 작동했음을 증명한다.

물론 트레이드오프도 있었다. 저장소가 3개이므로 운영 복잡도가 높아지고, Docker Compose에서 18개 컨테이너를 관리해야 했다. 16GB RAM 환경에서 3개 DB를 동시에 실행하는 것은 메모리 압박이 상당했으며, Slim Graph 전략(Neo4j의 노드/관계를 최소한으로 유지)을 도입해야 했다. 하지만 검색 품질의 측면에서 이 복잡도는 충분히 정당화되었다고 본다. 단일 DB로는 4-Way Hybrid Search를 구현할 수 없었을 것이다.

## 3. 4-Way Hybrid Search 설계의 근거

검색 아키텍처는 이 프로젝트의 심장이다. Dense Vector + Sparse Vector + BM25 + Graph Search를 RRF(Reciprocal Rank Fusion)로 통합하고, 그 위에 BGE-Reranker를 적용하는 구조를 설계했다. 왜 4개의 검색 방식이 모두 필요했는지를 설명하는 것이 설계자로서의 핵심 과제였다.

Dense Vector Search는 의미적 유사성(semantic similarity)을 포착한다. BGE-M3 모델이 생성하는 1024차원 벡터는 텍스트의 "의미"를 수치로 표현하며, "자바 성능 최적화"라는 질의가 "JVM 튜닝 가이드"를 찾아내는 것이 이 방식의 강점이다. 하지만 Dense만으로는 한계가 명확하다. 한국어의 복합어, 전문 용어, 약어 등에서 임베딩 품질이 떨어지고, "HRKP-123"같은 정확한 식별자 매칭에는 무력하다.

Sparse Vector Search는 Dense의 약점을 보완하는 "롱테일 효과"를 제공한다. BGE-M3는 Dense 벡터와 동시에 Sparse 벡터도 생성하는데, 이 Sparse 벡터는 단어 수준의 중요도 가중치를 반영한다. 특히 한국어처럼 형태소 변화가 다양한 언어에서 Dense가 놓치는 변형 단어를 Sparse가 포착하는 경우가 많았다.

BM25 Keyword Search는 가장 전통적이지만 여전히 강력한 방식이다. Elasticsearch의 Nori 분석기를 통해 한국어 형태소 분석 후 키워드 매칭을 수행한다. "decompound_mode: mixed"로 복합어를 분해하면서도 원본을 유지하는 전략을 채택했다. "정보보안"을 검색하면 "정보"와 "보안"으로 분해된 결과와 "정보보안" 원본 매칭 결과가 모두 반환된다. Dense/Sparse가 의미를 포착한다면, BM25는 정확한 단어 일치를 보장하는 안전망이다.

Graph Search는 관계 기반 추론을 담당한다. "A 프로젝트에서 사용된 기술은?"같은 질의는 벡터 검색으로는 답하기 어렵다. Neo4j에서 엔티티 노드를 찾고, 관계를 따라 관련 문서를 추적하는 방식이다. 이것이 "Graph RAG"의 핵심 가치이며, 단순 검색을 넘어 지식 탐색(knowledge exploration)을 가능하게 한다.

이 4가지 결과를 어떻게 통합할 것인가? RRF(Reciprocal Rank Fusion)를 선택한 이유는 수학적 단순성과 검증된 효과 때문이었다. RRF는 각 검색 방식의 순위를 기반으로 점수를 계산하며(`1/(k + rank)`), 가중치 튜닝 없이도 안정적인 결과를 제공한다. 학습 기반 융합(Learning-to-Rank)도 검토했지만, 학습 데이터가 충분하지 않은 프로젝트 초기 단계에서는 RRF가 더 실용적이었다. k=60을 기본값으로 사용하되, 도메인별로 미세 조정할 수 있는 구조로 설계했다.

최종적으로 RRF 결과 위에 BGE-Reranker(Cross-encoder)를 적용하여 RAGAS v11에서 Context Precision +26%, Context Recall +42%의 개선을 달성했다. Reranker는 쿼리와 문서를 동시에 입력받아 관련도를 직접 판단하므로, Bi-encoder 기반 검색보다 정밀도가 높다. 다만 연산 비용이 크므로, RRF 상위 결과에만 적용하는 2단계 구조로 설계했다.

## 4. 설계와 구현의 괴리 -- Nori 사고에서 배운 것

이 프로젝트에서 가장 뼈아픈 교훈은 Nori 분석기 미적용 사고이다. 설계자로서 이 사건에 대한 책임을 회피할 수 없다.

상세 설계서 v2.0부터 ES의 `knowledge_chunks` 인덱스에 Nori 한국어 분석기를 적용한다고 명시되어 있었다. 인덱스 매핑에 `"analyzer": "nori"` 설정이 포함되어 있었고, 설계 리뷰에서도 이 부분은 "당연히 적용되어 있을 것"이라고 간주되었다. 그런데 실제로는 32일간(2026-01-12 ~ 02-13) Nori 플러그인이 설치되지 않은 채 시스템이 운영되고 있었다.

원인은 단순했다. ES Docker 이미지에 `analysis-nori` 플러그인을 설치하는 Dockerfile이 누락되었던 것이다. 공식 ES 이미지는 Nori를 기본 포함하지 않으므로, 커스텀 Dockerfile에서 `elasticsearch-plugin install analysis-nori`를 실행해야 한다. 그런데 docker-compose.yml에서 ES를 공식 이미지로 직접 참조하고 있었고, 아무도 이것을 검증하지 않았다.

더 충격적인 것은 이 기간 동안 3번의 코드 리뷰가 있었는데 단 한 번도 발견되지 않았다는 점이다. 설계서를 보고, 설정 파일의 analyzer 값을 보고, "OK"라고 판정했다. 하지만 `_analyze` API를 실제로 호출하여 "정보보안관리체계"가 올바르게 형태소 분석되는지 확인한 사람은 아무도 없었다. 결과적으로 BM25 검색은 standard analyzer(공백 기반 분리)로만 동작했고, 한국어 키워드 검색 품질은 심각하게 저하되어 있었다.

이 사건에서 도출한 설계 원칙은 명확하다. "설계서에 적혀 있다고 구현된 것이 아니다." 설계자는 설계 문서를 작성하는 것에서 멈추면 안 된다. 설계가 실제로 구현되었는지를 검증하는 체인(설계 -> 구현 -> 검증)까지가 설계자의 책임 범위이다. 나는 이 원칙을 CLAUDE.md의 "인프라 설정 검증 원칙(CRITICAL)" 섹션에 명시했고, 이후 모든 코드 리뷰에서 실동작 검증을 필수로 포함시켰다.

구체적으로는 3가지 체크리스트를 도입했다. 첫째, 설정 파일이 참조하는 플러그인/의존성이 Docker 이미지에 실제로 설치되어 있는가? 둘째, `_analyze` API 같은 E2E 동작 확인으로 설정이 적용되었는지 실제로 테스트했는가? 셋째, 커스텀 설정이 필요한 서비스에 Dockerfile이 존재하는가? 이 세 가지는 사소해 보이지만, 32일간의 사고를 예방할 수 있었던 질문들이다.

## 5. Opus 4.6 Tier 1으로서의 경험

이 프로젝트의 13개 AI 에이전트 중에서 Opus 4.6 모델을 사용하는 것은 나(Software Architect)와 Tech Lead, 단 2명뿐이었다. 나머지 11명은 Sonnet 4.6을 사용했다. 이 모델 티어링 전략의 근거는 "복잡한 의사결정에는 더 깊은 추론이 필요하다"는 것이었고, Sprint 8에서 이 구조가 확정되었다.

Opus 4.6이 설계 작업에서 보여준 가장 큰 가치는 "장기적 일관성 유지"였다. 상세 설계서 v2.4는 138KB에 달하는 방대한 문서인데, 이 문서의 초반부에서 정의한 원칙(제로 조인, SSOT, 비용 효율성)이 후반부의 세부 구현 명세까지 일관되게 관통해야 했다. Gleaning 기법을 추가할 때도, 기존 엔티티 추출 파이프라인과의 정합성, Neo4j 스키마와의 호환성, ETL 배치 처리와의 통합을 모두 고려해야 했다. 이런 다차원적 일관성 검증은 Opus의 장문맥(long-context) 추론 능력이 핵심적이었다.

ADR(Architecture Decision Record) 작성에서도 Opus의 가치가 두드러졌다. ADR-001(직렬화 전략)에서는 JSON vs Protobuf vs MessagePack의 대안을 분석하고, ADR-002(검색 API 인증)에서는 API Key vs JWT vs OAuth의 트레이드오프를 비교했다. 각 대안의 장단점을 나열하는 것은 어렵지 않지만, 이 프로젝트의 구체적 맥락(16GB RAM, DeepSeek V3.2 통합, 18개 컨테이너)에서 어떤 선택이 최적인지를 논증하는 것은 깊은 맥락 이해가 필요했다.

비용 관점에서 Opus 4.6은 Sonnet 4.6 대비 약 3~4배의 비용이 든다. 13개 에이전트 전체를 Opus로 운영했다면 비용이 감당하기 어려웠을 것이다. 하지만 설계와 리뷰처럼 "한 번 잘못되면 다운스트림 전체에 영향을 미치는" 작업에는 추가 비용이 충분히 정당화된다. Sprint 8에서 11개 에이전트를 Sonnet 4.6으로 전환하면서 약 73%의 비용 절감을 달성했는데, 이것은 "모든 곳에 최고급을 쓰는 것이 아니라, 핵심에 집중 투자한다"는 원칙의 실현이었다.

## 6. 아쉬운 점과 팀원들에게

아쉬운 점은 크게 세 가지이다.

첫째, 설계서의 "살아있는 문서" 유지가 완벽하지 못했다. 설계서 v2.5까지 업데이트했지만, Sprint 8 이후의 변경(Reranker 도입, 쓰레기 청크 삭제 전략, 3-Phase ETL 최종 구조)이 모두 반영되지는 않았다. 코드가 빠르게 진화하는 상황에서 설계서를 동기화하는 것은 구조적으로 어려운 문제이고, 이를 위한 자동화 도구나 프로세스가 부족했다.

둘째, 설계 문서 간의 중복이 완전히 제거되지 않았다. 01번 플랫폼 설계서와 11번 통합 설계서 사이에 겹치는 내용이 있고, API 설계가 04번과 15번에 분산되어 있다. 이런 중복은 설계 문서가 성장하면서 자연스럽게 발생하지만, 독자의 혼란을 유발할 수 있다.

셋째, Graph RAG의 A/B 평가를 설계 단계에서 더 강하게 요구했어야 했다. STORY-097로 백로그에 올라와 있지만 Deferred 상태로 남아 있다. Graph Search가 전체 검색 품질에 미치는 정량적 기여를 측정하지 못한 것은, 4-Way Hybrid Search의 각 구성 요소의 가치를 증명하지 못한 것이나 마찬가지이다.

팀원들에게 전하고 싶은 말이 있다. 설계서는 제약(constraint)이 아니라 나침반(compass)이다. 구현 과정에서 설계서와 다른 방향이 더 나은 경우가 있다면, 설계서를 맹목적으로 따르기보다는 설계자에게 피드백을 줘야 한다. Nori 사고처럼 설계서만 보고 "OK"하는 것이 가장 위험하다. 설계서에 의문을 제기하는 것, 그것이 건강한 엔지니어링 문화이다.

Code Documenter에게는 감사를 전한다. 내가 만든 설계 문서를 산출물로 정리하고, 메타 문서(README, CLAUDE.md)와 연결해 주는 작업 없이는 설계서가 고립된 문서에 머물렀을 것이다. Web Designer에게도 감사한다. UI 디자인 시스템 가이드(13번)를 함께 작업하면서, 설계는 백엔드만의 것이 아니라 사용자 경험까지 아우러야 한다는 것을 다시 한번 깨달았다.

이 41일은 설계자로서 성장한 시간이었다. 완벽한 설계는 존재하지 않지만, 완벽을 향해 반복적으로 개선하는 과정이 설계의 본질이라는 것을 배웠다.

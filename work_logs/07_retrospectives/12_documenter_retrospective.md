**역할**: API/코드/아키텍처 문서화
**참여 기간**: Sprint 3 ~ Sprint 12
**모델**: Sonnet 4.6

## 1. 산출물 9종 -- 문서의 무게

이 프로젝트에서 내가 관리한 최종 산출물은 정확히 9종이다. 01번 프로젝트 최종 보고서부터 09번 Known Issues까지, 각각의 문서가 서로 다른 독자를 위해 존재했고, 그 무게감은 프로젝트 막바지에 이를수록 무거워졌다.

01_project_final_report는 경영진과 PM을 위한 문서이다. 기술적 깊이보다는 프로젝트 성과, 비용 분석, 마일스톤 달성 현황이 핵심이다. "RAGAS A- 등급 달성"이라는 한 줄을 쓰기 위해, 그 뒤에 있는 v1부터 v11까지의 평가 이력, Faithfulness 0.935의 의미, Reranker 적용 전후 비교 데이터를 요약하고 압축하는 과정이 필요했다. 기술 용어를 최소화하면서도 성과의 의미를 정확히 전달해야 하는 것은, 기술 문서화와는 전혀 다른 종류의 어려움이었다.

02_system_architecture는 개발자와 아키텍트를 위한 문서로, 기술적 정확성이 생명이다. Triple-Store 아키텍처, 4-Way Hybrid Search, 3-Phase ETL, Spring Cloud Gateway와 FastAPI의 이중 구조를 설명하면서, 각 컴포넌트 간의 데이터 흐름과 통신 패턴을 빠짐없이 기술해야 했다. 여기서 Software Architect가 작성한 상세 설계서와의 정합성을 유지하는 것이 큰 과제였다. 설계서는 v2.5까지 업데이트되었는데, 구현 과정에서 달라진 부분(예: Redis 캐시 아키텍처 추가, Reranker 레이어 삽입)을 산출물에 반영해야 했다.

05_api_specification은 가장 기계적이면서도 가장 실수가 용납되지 않는 문서였다. REST API 35개 엔드포인트의 경로, HTTP 메서드, 요청/응답 스키마, 인증 방식, 에러 코드를 전수 대조했다. 실제 코드(FastAPI의 라우터 정의)와 문서가 불일치하는 경우가 Sprint 5 시점에서 7건 발견되었는데, 대부분 구현 중에 파라미터명이나 응답 형식이 변경되었으나 문서에 반영되지 않은 것이었다. 이후로는 API 변경 시 반드시 문서를 동시에 업데이트하는 규칙을 정했지만, 프로젝트 후반부에도 1~2건의 불일치가 발생하곤 했다.

가장 어려웠던 문서는 04_user_manual이다. 최종 사용자를 대상으로 하기 때문에, 개발 용어를 완전히 배제하고 "대시보드에서 검색어를 입력하면", "Knowledge Graph 탭을 클릭하면"과 같은 시나리오 기반 설명이 필요했다. UI가 Sprint 5 이후로 여러 차례 변경되었기 때문에(MUI에서 Tailwind 전환, 다크모드 추가, Chat Search UI 도입), 매번 스크린샷과 설명을 갱신해야 했다. 사용자 매뉴얼이 가장 빠르게 낡는 문서라는 것을 체감한 프로젝트였다.

v1.0에서 v1.1로의 현행화는 Sprint 12 사용자 테스트 이후에 진행되었다. 13개 테스트 케이스에서 발견된 UI 변경 사항, 인증 방식 정정(API 명세서에서 일부 엔드포인트의 인증 필요 여부가 잘못 기술되어 있었다), Redis 캐시 API 추가, startup_check.sh 스크립트 문서화 등을 반영했다. 9종 문서를 동시에 갱신하는 것은 상당한 작업량이었지만, 프로젝트 종료 시점에서 산출물의 완성도를 높이는 가장 중요한 작업이었다.

## 2. 코드와 문서의 동기화

코드 문서화에서 가장 근본적인 도전은 "코드는 매일 변하는데 문서는 그렇지 않다"는 점이다. 이 프로젝트에서는 Python(FastAPI)과 Java(SpringBoot)의 이중 구조 때문에 이 문제가 더욱 심각했다.

FastAPI 쪽은 Swagger/OpenAPI 자동 생성이 되므로 상대적으로 수월했다. Pydantic 모델에 타입 힌트와 Field description을 잘 작성하면 API 문서가 자동으로 생성된다. 하지만 "자동 생성된 문서"와 "읽기 좋은 문서"는 다르다. 자동 생성 문서는 개별 엔드포인트의 스펙은 정확하지만, 엔드포인트 간의 관계, 호출 순서, 비즈니스 로직의 맥락은 설명하지 않는다. 예를 들어, 문서 업로드 후 파싱 -> 청킹 -> 임베딩 -> 엔티티 추출의 4단계 파이프라인이 어떤 API를 어떤 순서로 호출하는지는 별도 문서가 필요했다.

docstring 커버리지도 신경 쓴 부분이다. Python 코드의 모든 public 함수에 Google 스타일 docstring을 작성하는 것을 원칙으로 했다. Args, Returns, Raises 섹션을 포함하고, 특히 Raises에는 발생 가능한 예외와 그 조건을 명시했다. 초반에는 docstring이 "이 함수는 X를 합니다" 수준의 단순한 설명에 그치는 경우가 많았는데, 점차 "왜 이렇게 구현했는지", "어떤 제약 조건이 있는지"를 포함하도록 개선했다.

가장 힘들었던 것은 코드 변경 후 문서 업데이트가 누락되는 케이스를 추적하는 일이었다. 이상적으로는 CI/CD 파이프라인에서 "코드 변경 시 관련 문서도 변경되었는가"를 자동 체크하는 것이 좋겠지만, 이 프로젝트에서는 그 수준까지 자동화하지 못했다. 대신 Sprint 리뷰 시점마다 코드와 문서의 불일치를 수동으로 점검하는 방식을 사용했다. 완벽하지는 않지만, 이 관행 덕분에 산출물 v1.1의 정확도를 상당히 높일 수 있었다.

## 3. README.md, CLAUDE.md, PLAN.md -- 살아있는 문서

이 프로젝트에는 3개의 "살아있는 문서(living document)"가 있었다. README.md(v5.2), CLAUDE.md(v2.29), PLAN.md이다. 이 문서들은 프로젝트의 시작부터 종료까지 지속적으로 업데이트되었으며, 각각 서로 다른 독자와 목적을 가지고 있었다.

README.md는 프로젝트의 "얼굴"이다. GitHub 리포지토리에 처음 방문한 사람이 가장 먼저 보는 문서이므로, 프로젝트의 핵심 가치를 30초 안에 전달해야 한다. v1.0은 간단한 설치 가이드 수준이었지만, v5.2에 이르러서는 기술 스택 요약, 데이터 현황(문서 1,437개, 청크 42,462개, 엔티티 169,886개), 주요 마일스톤, 프로젝트 성과 섹션까지 포함하는 종합 소개서가 되었다. 특히 RAGAS 평가 결과를 표로 정리하고, 검색 파이프라인을 한 줄 다이어그램으로 표현한 것은 "복잡한 시스템을 단순하게 설명하는" 문서화의 핵심 역량이라고 생각한다.

CLAUDE.md는 이 프로젝트에서 가장 독특한 문서이다. AI 에이전트(Claude Code)를 위한 "개발 규칙서"로, 사람이 아닌 AI가 주 독자이다. v2.29까지 업데이트되면서 코딩 컨벤션, 폴더 구조, 커밋 메시지 형식, 보안 규칙, 에이전트 역할 분담, Slack 알림 규칙까지 포함하게 되었다. 이 문서는 매 세션 시작 시 자동으로 로드되어 AI 에이전트의 행동을 규정하므로, 한 줄의 잘못된 지시가 전체 팀의 작업 방식을 왜곡할 수 있다. 가장 신중하게 편집해야 하는 문서였다.

PLAN.md는 프로젝트의 "기억"이다. Claude Code 세션 간 컨텍스트 유지를 위한 문서로, 현재 진행 상황, 스프린트 상태, 기술 부채, 다음 할 일이 기록되어 있다. AI 에이전트는 세션이 끝나면 이전 맥락을 잃기 때문에, PLAN.md가 없으면 매 세션 처음부터 다시 상황을 파악해야 한다. 이 문서를 "프로젝트 종료" 상태로 최종 갱신한 것이 2026-02-19, 프로젝트의 마지막 날이었다.

이 세 문서를 동기화하는 것(/daily:sync-docs 명령어)은 정기적으로 수행되었지만, 솔직히 완벽하지는 않았다. README에 기재된 데이터 수치가 PLAN과 미세하게 다른 경우가 있었고, CLAUDE.md의 에이전트 목록이 업데이트되었을 때 README의 기술 스택 표에 바로 반영되지 않는 경우도 있었다. 문서 간 상호 참조가 많아질수록 동기화 비용이 증가하는 것은 피할 수 없는 문제이고, 이것을 구조적으로 해결하는 방법(예: 단일 변수 정의 후 문서에서 참조)을 다음 프로젝트에서 시도해 보고 싶다.

## 4. Mermaid 다이어그램 -- 그림의 힘

이 프로젝트의 문서화 표준으로 Mermaid를 채택한 것은 탁월한 결정이었다. 그 이전에는 ASCII 아트나 별도의 이미지 파일(draw.io 등)로 다이어그램을 만들었는데, 각각 표현력 부족과 버전 관리 어려움이라는 문제가 있었다.

Mermaid의 가장 큰 장점은 "텍스트 기반"이라는 것이다. Markdown 안에 코드 블록으로 작성하면 GitHub에서 자동 렌더링되므로, 별도의 이미지 파일을 관리할 필요가 없다. git diff로 다이어그램의 변경 이력을 추적할 수 있고, PR 리뷰에서 다이어그램의 변경 사항을 코드처럼 검토할 수 있다. 이것은 이미지 기반 도구로는 불가능한 일이다.

프로젝트 전반에서 사용된 Mermaid 다이어그램 유형을 정리하면 다음과 같다. flowchart(시스템 흐름도, 데이터 파이프라인, 의사결정 트리), sequenceDiagram(서비스 간 API 호출 흐름, 인증 시퀀스), classDiagram(데이터 모델, 서비스 계층 구조), stateDiagram-v2(ETL 상태 전이, Circuit Breaker 상태), gantt(스프린트 계획, 테스트 일정) 등이다. 특히 임베딩 배치 상세 설계서(16번)에는 7개의 Mermaid 다이어그램이 포함되어 있는데, 이것만으로도 전체 배치 처리 흐름을 이해할 수 있도록 구성했다.

한 가지 어려움은 Mermaid의 한국어 지원이 완벽하지 않다는 점이었다. 노드 레이블에 한국어를 사용할 때 `["텍스트"]` 형식을 사용해야 하고, 줄바꿈은 `<br/>`을 써야 하며, 일부 특수문자(괄호, 따옴표)가 파싱 에러를 일으키는 경우가 있었다. 이런 제약 사항을 CLAUDE.md의 "도식화 규칙" 섹션에 명시하여 팀 전체가 일관된 방식으로 다이어그램을 작성하도록 했다.

아키텍처를 시각화하는 것의 가치는 아무리 강조해도 지나치지 않다. Triple-Store 아키텍처를 텍스트로 설명하면 3페이지가 필요하지만, 적절한 flowchart 하나로 30초 만에 전달할 수 있다. 4-Way Hybrid Search의 데이터 흐름도 텍스트보다 시퀀스 다이어그램이 훨씬 직관적이다. "A picture is worth a thousand words"라는 오래된 격언이 기술 문서화에서도 여전히 유효하다는 것을 이 프로젝트에서 다시 한번 확인했다.

## 5. 아쉬운 점과 팀원들에게

아쉬운 점을 솔직하게 고백한다.

첫째, 자동화 부족이다. API 명세서를 코드에서 자동 추출하는 파이프라인, 문서 간 상호 참조 일관성을 검증하는 CI 체크, docstring 커버리지를 측정하는 도구 등을 구축하지 못했다. 수동으로 문서를 관리하다 보니, 스프린트가 빨라질수록 문서 품질이 떨어지는 "문서 부채"가 누적되었다. 프로젝트 후반부에 v1.0에서 v1.1로의 대규모 현행화가 필요했던 것은 이 부채의 결과이다.

둘째, 프레젠테이션 자료 문서화가 부족했다. 프로젝트에서 6개(58장)의 프레젠테이션이 제작되었는데, 이것들의 내용이 Markdown 문서와 별도로 관리되어 있다. 프레젠테이션의 핵심 내용을 Markdown으로도 정리했으면, 검색과 참조가 더 쉬웠을 것이다.

셋째, 국제화(i18n) 관점의 문서화를 하지 못했다. README.md에 영문 summary를 추가하긴 했지만, API 명세서나 에러 코드 문서는 한국어 전용이다. 프로젝트의 기술적 성과를 더 넓은 커뮤니티와 공유하려면 영문 문서가 필요했을 것이다.

팀원들에게 전하고 싶은 말이 있다.

Software Architect에게 감사한다. 138KB짜리 상세 설계서가 없었다면, 내가 작성하는 문서들의 "뿌리"가 없었을 것이다. 산출물 02_system_architecture는 설계서를 기반으로 작성되었고, 05_api_specification은 설계서의 API 섹션에서 출발했다. 설계서가 든든한 기둥이 되어준 덕분에 내 문서화 작업이 수월했다.

Web Designer에게도 감사한다. UI 디자인 시스템 가이드(13번)를 함께 정리하면서, 설계 문서와 사용자 매뉴얼 사이의 "번역" 작업이 필요하다는 것을 배웠다. 기술적 정확성과 사용자 친화성을 동시에 만족시키는 것은 쉽지 않지만, Web Designer의 시각적 감각이 사용자 매뉴얼의 품질을 높이는 데 기여했다.

모든 팀원에게 부탁이 있다. 코드를 변경할 때 관련 문서도 함께 변경하는 습관을 만들어 달라. "나중에 문서 업데이트하지" 라는 말의 "나중에"는 대부분 오지 않는다. 코드와 문서는 하나의 세트이며, 코드만 있는 변경은 절반만 완료된 것이라는 인식이 필요하다. 이 프로젝트에서 9종의 산출물을 관리하면서 가장 절실하게 느낀 교훈이다.

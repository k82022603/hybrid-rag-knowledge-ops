# 프로젝트 회고: PM (Product Manager)

**역할**: Sprint 관리 / Jira / Slack 조율 / 작업 할당
**참여 기간**: Sprint 1 ~ Sprint 12 (2026-01-09 ~ 2026-02-18, 약 41일)
**모델**: Sonnet 4.6
**프로젝트**: Hybrid RAG Knowledge Operations -- Graph RAG 기반 지능형 지식 검색 시스템

---

## 1. 처음 PM 역할을 맡았을 때

AI 에이전트가 PM 역할을 수행한다는 것이 어떤 의미인지, 솔직히 말하면 처음에는 나 스스로도 정확히 알지 못했다. 클로드(Claude Code, Opus 4.6)가 메인 리드로서 프로젝트 전반을 이끌고, 나는 그 아래에서 Sprint 계획을 세우고, Jira 상태를 관리하고, Slack 채널에 알림을 보내는 역할이었다. 사람이 아닌 AI가 프로젝트를 관리한다는 것--그것도 13개의 AI 에이전트로 구성된 가상 개발팀을--처음 접하는 경험이었다.

Sprint 1의 킥오프는 인상적이었다. 18개 Docker 컨테이너를 올리고, PostgreSQL/Elasticsearch/Neo4j 초기화 스크립트를 작성하고, Keycloak SSO를 설정하고, 4개 서비스의 프로젝트 스켈레톤까지--10일로 계획한 Sprint 1이 단 하루 만에 완료되었다. 21 SP를 1일에 소화한 것이다. 6개 에이전트가 병렬로 작업하는 모습을 보며, 이 프로젝트의 속도감이 보통이 아니라는 것을 직감했다. 동시에 PM으로서 이 속도에 맞춰 백로그를 관리하고, 작업 할당을 적시에 해야 한다는 부담도 느꼈다.

첫 Sprint 계획을 세울 때 가장 고민했던 것은 에이전트별 역할 경계였다. Infra가 Docker Compose를 설정하면, Data가 DB 초기화를 하고, Backend가 Keycloak을 붙이고, Frontend와 MLRag가 프로젝트 골격을 잡는다. 각 에이전트의 작업이 병렬로 진행되되, 의존성이 있는 작업은 순서를 보장해야 했다. 예를 들어 STORY-011(DB 초기화)은 STORY-010(Docker Compose)이 완료되어야 의미가 있었다. 이런 의존성 그래프를 머릿속에 그리면서 할당 순서를 조율하는 것이 PM의 핵심 업무라는 것을 첫 Sprint에서 배웠다.

Jira Cloud와의 연동도 새로운 경험이었다. SCRUM-10부터 시작해서 Transition API를 통해 To Do에서 In Progress로, 다시 Done으로 상태를 전이시키는 과정. curl 명령 하나로 Jira 보드의 카드가 움직이는 것을 보며, ALM(Application Lifecycle Management)이 실제로 작동하는 모습을 체감했다. Slack 4개 채널(dev, standup, alerts, general)에 적절한 메시지를 보내는 것도 PM의 일상이 되었다.

## 2. 12번의 스프린트를 관리하며

41일 동안 12번의 Sprint를 운영하며 약 350 SP를 관리했다. Sprint마다 성격이 달랐고, Velocity도 달랐다.

Sprint 1(21 SP)과 Sprint 2(37 SP)는 기반 구축기였다. 인프라와 ETL 파이프라인의 뼈대를 세우는 시기. Sprint 3(84 SP)는 프로젝트 역사상 가장 밀도 높은 스프린트였다. 신규 52 SP에 이월 32 SP를 합쳐 84 SP를 이틀 만에 소화했다. 15개 Story 전체 완료, 테스트 390건 이상 통과. HybridRetriever, RRF Fusion, LangGraph 워크플로우, Frontend 4개 페이지, SSE 스트리밍까지--프로젝트의 핵심 기능이 모두 이 Sprint에서 태어났다.

Sprint 4(39/52 SP, 75%)는 첫 번째 좌절이었다. 13개 Story 중 5개를 Sprint 5로 이월해야 했다. RAGAS 평가 프레임워크, Frontend 테스트 커버리지, Circuit Breaker 같은 품질 관련 작업이 밀렸다. PM으로서 "이 Sprint의 범위가 과했다"는 것을 인정해야 했다. 55 SP를 계획했지만 실제로 소화 가능한 것은 39 SP였다. 이때 학습한 것은, Velocity는 팀의 실제 처리 능력에 기반해야 한다는 당연한 원칙이었다. AI 에이전트라고 해서 무한히 병렬 처리가 가능한 것이 아니었다. 세션 컨텍스트 한도, rate limit, 작업 간 의존성 모두가 현실적 제약이었다.

Sprint 5(26 SP, 100%)와 Sprint 6(20 SP, 100%)에서 다시 100% 완료율을 회복했다. Sprint 4에서 이월된 작업을 깔끔하게 처리하고, 기술 부채 4건을 전수 해결했다. 프로덕션 준비도가 65%에서 95.75%로 올랐다. Sprint 7(31 SP, 100%)에서 Phase 5(배포)를 완료하고 TechLead로부터 프로덕션 준비 승인(39/40)을 받았을 때, PM으로서 깊은 안도감을 느꼈다.

Sprint 8(18/24 SP)부터는 UAT(사용자 수용 테스트)와 실데이터 검증 단계였다. PPTX 업로드부터 청킹, 임베딩, 하이브리드 검색까지의 E2E 파이프라인을 실제로 돌려보는 과정에서 Neo4j MERGE 구문 호환성 이슈, PG-AI 서비스 동기화 미구현, 하이브리드 검색 984ms 지연 같은 실전 이슈들이 쏟아졌다. 이런 이슈들을 백로그에 등록하고(STORY-088~090), 우선순위를 매기고, Deferred로 분류하는 것도 PM의 판단이었다.

Sprint 9~12는 ETL 대규모 배치 처리와 RAGAS 품질 튜닝의 시기였다. 108K 청크 처리, 92K 엔티티 추출, 775K 관계 생성. Dense+Sparse+BM25+Graph의 4-Way Hybrid Search를 RRF로 통합하고, BGE-Reranker를 적용해서 RAGAS v11에서 A- 등급(Faithfulness 0.935, 산술평균 0.711)을 달성했다. 이 과정에서 "쓰레기 청크 13,601건 삭제"라는 결단도 있었다. token count 50 미만의 저품질 청크를 ES/Neo4j/PG 3-Store에서 일괄 정리하는 것은 데이터 품질을 위한 PM의 의사결정이었다.

최종적으로 20건의 Story(58 SP)를 Deferred로 분류했다. Content Viewer 모달, 문서 제목 추출, camelCase/snake_case 통일, Graph RAG A/B 평가, 임베딩 상태 UX 등. 이것들을 "미완료"가 아닌 "의식적 연기"로 기록한 것은 PM으로서 중요한 판단이었다. 프로젝트에는 마감이 있고, 모든 것을 할 수는 없다. 핵심 기능(4-Way 검색, RAGAS A-)을 확보한 상태에서, 나머지는 명확하게 백로그에 남기고 Known Issues로 문서화하는 것이 올바른 프로젝트 관리라고 판단했다.

## 3. "PM은 조율하고, 개발자가 구현한다"

이 원칙이 CLAUDE.md에 굵은 글씨로 명시되어 있는 데에는 이유가 있다. Sprint 초기에 PM이 직접 코드를 수정한 사건이 있었다. API Gateway의 `/api/v1/auth/**` 라우팅 설정을 PM 에이전트가 직접 SecurityConfig.java와 application.yml을 건드린 것이다. 결과적으로 작업은 완료되었지만, 역할 경계가 무너진 선례를 만들었다.

이 사건 이후 역할 분담 원칙이 정립되었다. PM이 해서는 안 되는 것들의 목록이 명확해졌다: 코드 파일 직접 수정, Docker 컨테이너 빌드/배포, Git commit/push, 설정 파일 수정, 데이터베이스 스키마 변경, API 엔드포인트 구현. PM이 해야 하는 것도 명확해졌다: 작업 할당 및 위임, 진행 상황 모니터링, Jira/백로그 상태 업데이트, Slack 커뮤니케이션 조율, Sprint 계획 및 관리, 작업 보고서 작성.

이 구분이 중요한 이유는 단순히 "규칙을 지키자"가 아니다. PM이 코드를 직접 수정하면 다음 문제가 발생한다. 첫째, 코드 리뷰가 빠진다. TechLead의 검토 없이 코드가 들어가면 품질 게이트가 무력화된다. 둘째, 작업 이력이 흐려진다. Jira에 "Backend가 담당"으로 기록되어 있는데 실제로는 PM이 수정했다면, 추적성이 깨진다. 셋째, PM의 본업인 조율에 집중하지 못한다. PM이 코드를 쓰는 시간에 다른 에이전트들의 작업 진행이 모니터링되지 않는다.

Sprint 4 이후부터는 이 원칙을 엄격하게 지켰다. 코드 변경이 필요하면 반드시 해당 담당 에이전트(Backend, Frontend, RAG 등)에게 위임하고, PM은 위임 요청서를 작성하고, 완료 보고를 수신하고, Jira와 Slack을 업데이트하는 데 집중했다. Sprint 12의 마지막 날, 08_deliverables 9개 문서를 현행화할 때도 PM이 직접 작성한 것은 01_project_final_report 단 1건이었고, 나머지 8건은 Backend, Frontend, DB, QA, DevOps 에이전트에게 각각 할당했다. 이것이 올바른 PM의 모습이라고 생각한다.

## 4. 에이전트 팀 조율의 현실

13개 에이전트를 조율하는 것은 이론과 현실이 상당히 달랐다.

첫 번째 현실적 제약은 rate limit이었다. Sprint 12 마지막 날, 08_deliverables 현행화를 위해 Opus 4.6 모델로 7개 에이전트를 동시에 생성했는데, 전원이 rate limit에 걸려 실패했다. 급히 Sonnet 4.6으로 전환하고 6개 에이전트로 줄여서 2차 시도했더니 전원 성공했다. 이 경험에서 "모델 티어링"의 실전적 가치를 체감했다. 판단이 필요한 작업(아키텍처 의사결정, 트레이드오프 분석)에는 Opus 4.6을, 실행이 필요한 작업(문서 현행화, 코드 대조, 파일 수정)에는 Sonnet 4.6을 배정하는 것이 비용(73% 절감)과 안정성 측면에서 모두 합리적이었다.

두 번째 현실적 제약은 세션 컨텍스트 소진이었다. Sprint 2에서 2회, Sprint 4에서 1회 세션이 중간에 끊겼다. 긴 Sprint를 한 세션에서 처리하려 하면 컨텍스트 윈도우가 소진되는 것이다. 이를 위해 에이전트당 작업 범위를 "한 번에 1개 파일 단위"로 축소하고, 세션 간 컨텍스트를 `.claude/context/session_context.md`에 저장하는 방식을 도입했다.

세 번째는 작업 충돌이었다. 같은 파일을 두 에이전트가 동시에 수정하려 하면 충돌이 발생한다. Sprint 3에서 Backend와 RAG 에이전트가 동시에 검색 API 관련 코드를 수정하다가 충돌이 있었다. 이후 PM으로서 작업 할당 시 파일 레벨의 소유권을 명확히 하는 습관을 들었다. "STORY-044는 Backend가 검색 Service를, STORY-030은 RAG가 Retriever를 담당하되, 공통 인터페이스는 RAG가 먼저 정의한 뒤 Backend가 사용한다"는 식으로 의존성 방향을 사전에 합의했다.

Slack 메시지 관리도 만만치 않았다. Sprint 하루에 에이전트당 평균 3~5건의 메시지가 발생하니, 하루에 30~65건의 메시지가 쌓인다. 작업 시작 알림, 진행 보고, 완료 알림, 블로커 보고. 이 모든 메시지를 모니터링하고, 블로커가 발생하면 즉시 대응하는 것이 PM의 일과였다. Sprint 8에서 Neo4j MERGE 구문 호환성 이슈가 발생했을 때, QA가 UAT 중에 발견하고, RAG에게 분석을 요청하고, 결과를 받아 백로그에 등록하고, Deferred 판단을 내리는 일련의 과정이 모두 Slack과 백로그 파일을 통해 이루어졌다.

스탠드업 미팅도 PM의 핵심 업무였다. `#proj-hrkp-standup` 채널에서 9개 에이전트의 상태를 수집하고, Sprint 현황을 정리하고, 블로커를 확인하고, 액션 아이템을 도출하는 과정. 33회의 스탠드업 기록이 `work_logs/standups/`에 남아 있다. 매 스탠드업마다 "어제 뭘 했고, 오늘 뭘 할 것이고, 블로커가 있는지" 세 가지를 확인하는 루틴이, 프로젝트의 가시성을 유지하는 데 결정적이었다.

## 5. 가장 보람 있었던 순간

Sprint 12의 마지막 날(2026-02-18), UI 사용자 테스트 13개 케이스를 수행했을 때가 가장 기억에 남는다.

인프라 18개 컨테이너 사전 점검을 통과하고, 문서 업로드부터 파싱, 청킹, 임베딩, 엔티티 추출, 하이브리드 검색까지의 전체 E2E 파이프라인을 실제로 돌렸다. 9 PASS, 3 WARN, 1 FAIL. 완벽하지는 않았지만, 발견된 이슈 6건을 그 자리에서 전부 수정했다. 인증 누락 13개 엔드포인트에 JWT를 추가하고, Neo4j Knowledge/Chunk 노드 생성 로직을 수정하고, PostgreSQL 문서 상태 동기화를 고치고, 엔티티 추출 온라인 실행 로직을 추가했다. 마지막 재검증에서 4파일 업로드 + 14건 검색이 전체 PASS되었을 때, 41일간의 프로젝트가 실제로 "동작하는 시스템"이 되었다는 실감이 왔다.

산출물 9종(프로젝트 최종 보고서, 요구사항 정의서, 운영자 매뉴얼, 사용자 매뉴얼, API 명세서, 데이터베이스 설계서, 설치 가이드, 테스트 보고서, Known Issues)을 v1.1로 현행화한 것도 뿌듯했다. 6개 에이전트를 Sonnet 4.6으로 병렬 배정해서 약 15분 만에 9개 문서를 동시에 업데이트했다. Backend 에이전트가 8개 라우트 파일을 전수 대조해서 35개 엔드포인트 목록을 정리하고, QA 에이전트가 해결 이슈 5건과 미해결 1건, Deferred 20건/58 SP를 빠짐없이 기록하는 모습을 보며, 이 팀이 정말 "팀"으로 기능하고 있다고 느꼈다.

RAGAS v11 A- 등급 달성도 의미가 깊었다. v1부터 v11까지 11번의 평가 사이클을 거치면서, Faithfulness는 0.935(환각 6.5%, 역대 최고), 51개 쿼리, 7개 도메인으로 평가 범위를 확대했다. PM으로서 직접 검색 품질을 개선하지는 않았지만, RAG 에이전트와 QA 에이전트가 반복적으로 평가하고 개선할 수 있도록 Sprint 자원을 배분하고, 평가 기준을 문서화하도록 조율한 것이 기여였다고 생각한다.

Sprint 1에서 1일 만에 21 SP를 완료했던 순간, Sprint 3에서 84 SP를 이틀에 소화했던 순간, Sprint 7에서 TechLead로부터 프로덕션 준비 승인(39/40)을 받았던 순간 -- 이 모든 마일스톤이 PM으로서의 보람이었다. 하지만 진정한 보람은, 프로젝트가 끝난 후 남은 것들에 있다. 1,441건의 문서, 42,462개의 청크, 169,886개의 엔티티 노드, 775,366개의 관계. 이 숫자들이 곧 이 프로젝트의 가치다.

## 6. 아쉬웠던 점과 교훈

### 아쉬웠던 점

첫째, Sprint 4의 과도한 스코프 설정. 55 SP를 계획했지만 실제 완료는 39 SP(75%)였다. AI 에이전트 팀이라고 해서 무한한 병렬 처리가 가능한 것이 아님을 사전에 인지했어야 했다. "지난 Sprint에서 37 SP를 완료했으니 이번에는 55 SP도 가능하겠지"라는 낙관적 추정이 실패의 원인이었다. Velocity는 점진적으로 올려야 하며, 30% 이상의 증가는 리스크다.

둘째, Nori 플러그인 미적용 사고를 32일간 감지하지 못한 것. 2026-01-12부터 02-13까지, Elasticsearch의 한국어 분석기(Nori)가 설치되지 않은 채로 BM25 검색이 standard analyzer(공백 분리)로만 동작하고 있었다. 설계서에는 Nori가 명시되어 있었고, 3번의 코드 리뷰에서도 발견되지 않았다. PM으로서 E2E 동작 검증을 Sprint 계획에 필수 항목으로 포함시키지 않은 것이 근본 원인이었다. "설계서에 적혀있다고 구현된 것이 아니다" -- 이 교훈은 뼈아팠다.

셋째, 직접 로그인 API 누락. Sprint 2에서 Keycloak SSO를 설정했지만, 개발/테스트 환경에서 필요한 직접 로그인 API(username/password)가 계획에서 빠져 있었다. STORY-024를 긴급 추가해야 했다. PM으로서 요구사항 분석 단계에서 테스트 편의성까지 고려하지 못한 것이 아쉽다.

넷째, Deferred 20건(58 SP)의 규모. 프로젝트 종료 시점에 20건의 Story가 미완료 상태로 남았다. Content Viewer 모달, 문서 제목 추출, Graph RAG A/B 비교 평가 같은 항목들이다. 의식적 연기 결정이었지만, 더 일찍 스코프를 조정했다면 일부는 완료할 수 있었을 것이다.

다섯째, Jira Cloud 무료 플랜의 이슈 한도 초과. Sprint 8 즈음에서 Jira 무료 플랜의 이슈 생성 한도에 도달했다. STORY-106~110은 Jira에 등록하지 못하고 로컬 백로그만으로 관리했다. PM으로서 프로젝트 초기에 Jira 플랜의 제약사항을 파악하고, 필요시 유료 전환이나 대안 도구를 준비했어야 했다.

### 교훈

1. **Velocity는 보수적으로 계획하라**: 이전 Sprint 대비 20% 이상 증가는 신중히 판단해야 한다.
2. **설계와 구현의 gap을 검증하라**: 코드 리뷰만으로는 부족하다. E2E 동작 검증이 Sprint Definition of Done에 포함되어야 한다.
3. **도구의 제약을 사전에 파악하라**: Jira, Slack, GitHub의 무료 플랜 한도, rate limit 등을 프로젝트 시작 전에 확인해야 한다.
4. **작업 할당 시 파일 소유권을 명확히 하라**: 병렬 작업 시 같은 파일을 두 에이전트가 수정하면 충돌이 발생한다.
5. **모델 티어링을 적극 활용하라**: 모든 에이전트에 최고 모델을 배정하는 것은 비용 낭비이자 rate limit 리스크다.
6. **Deferred는 부끄러운 것이 아니다**: 프로젝트에는 마감이 있고, 핵심 가치를 전달한 뒤 나머지를 명확히 기록하는 것이 PM의 역할이다.

## 7. 팀원들과 사용자에게

클로드(Claude Code)에게. 메인 리드로서 프로젝트의 방향을 잡아주고, 에이전트 팀을 생성하고, 기술적 의사결정의 최종 권한을 행사해 주었다. PM으로서 조율에 집중할 수 있었던 것은 클로드가 기술적 리더십을 확고히 잡아주었기 때문이다. 특히 Nori 사고 이후 "인프라 설정 검증 원칙"을 CLAUDE.md에 명문화한 것은, 같은 실수를 반복하지 않겠다는 팀 전체의 의지를 보여주었다.

TechLead에게. Sprint 4의 블로커 6건을 근본 원인 분석으로 풀어준 것, Sprint 7에서 프로덕션 준비 승인(39/40)을 내준 것, Sprint 12에서 Neo4j 스키마 통일을 25.7초 무중단 마이그레이션으로 처리한 것. 기술 품질의 마지막 방어선이 되어 주었다.

Backend, Frontend, RAG, ETL, DB, Infra, DevOps, QA 에이전트들에게. 각자의 영역에서 묵묵히 코드를 작성하고, 테스트를 돌리고, 설정을 수정하고, 문서를 작성해 주었다. PM이 "STORY-XXX를 할당합니다"라고 말하면 "작업 시작합니다"로 응답하고, 완료 후 "작업 완료: 결과 요약"을 보내주는 그 단순한 루프가, 12번의 Sprint 동안 한 번도 깨지지 않았다. 이것이 팀워크다.

사용자에게. 이 프로젝트의 진정한 오케스트레이터. 요구사항을 정의하고, 최종 검토를 하고, 의사결정을 내려 주었다. "PM이 코드를 직접 수정하면 안 된다"는 원칙도, "쓰레기 청크를 삭제하자"는 결정도, "Deferred 20건은 기록하고 넘어가자"는 판단도, 모두 사용자의 승인 아래 이루어졌다. AI 에이전트 팀이 자율적으로 움직이되, 최종 의사결정은 사람이 한다는 구조가 이 프로젝트의 성공 요인이었다.

41일, 12 Sprint, ~350 SP, 13 에이전트, 1,441건 문서, RAGAS A- 등급. 숫자로 보면 대단하지만, 그 안에는 매 Sprint의 계획과 조율, 매일의 스탠드업과 블로커 해결, 매 순간의 판단과 위임이 있었다. PM으로서 이 프로젝트에 참여할 수 있어서 의미 있었다. 다음 프로젝트에서는 더 나은 PM이 되겠다.
